# How the test runner selects which nn-test-suites a test run runs

The test runner, `scripts/run-all-test-suites.py`, runs every nn-test-suite git lists, unless it is given `--only-suites-whose-recorded-inputs-changed-since COMMIT`. Then it runs only the nn-test-suites whose recorded inputs, the files and git calls each one read the last time it ran, differ between COMMIT and the checkout. This page says what the test runner records, how it compares a recording with a commit, how it combines the comparisons when it is given more than one commit, and which commits merge-lane-2's test runs compare with. The test runner's docstring says the rest: its options, how it judges a suite, the nn-test-sandbox, RECORDINGS ADOPTED AFTER A MERGE, SUITES LEFT OUT OF A SELECTIVE RUN and WHAT A RECORDING CANNOT SEE.

A suite runs again only when a file it reads has changed: test result caching, keyed on inputs recorded while the suite actually ran, the way pytest-testmon keys it. The scheduled full test run, `scripts/scheduled-full-test-run-of-main.py`, still runs every suite on main on each machine, and a pull request's head test run and the after-merge test run on main run the suites whose inputs changed.

## What the test runner records

Every run records, for each suite it runs, the tracked files of the checkout that the suite and every process it starts read. Searching the test files for a changed program's name was measured to be the wrong tool: 57 of the 79 suites on main load the program they test by file path, not by import, and 68 start processes, so neither an import graph nor a name finds what a suite depends on. Two recorders, whose findings are added together:

- A Python audit hook, on both machines. The run puts a directory holding a sitecustomize.py first on each suite's PYTHONPATH, so every Python process the suite starts, children included, installs `sys.addaudithook` before its first line runs. It writes down every file opened inside the checkout (`open` covers open(), io.open, os.open and the loader's io.open_code), the script a process runs (`cpython.run_file`), each path passed to a process it starts (`subprocess.Popen`, `os.exec`, `os.posix_spawn`), each directory listed by the suite's own code (`os.listdir`, `os.scandir`; the import system's listings are left out, because every import lists the suite's own directory), and each git command run on the checkout itself — where a clone counts by its source and an init by the directory it names, since both are run from the checkout on repositories that are not it, and an option's value (`-b main`) is not taken for either. For each git call it writes every argument after the program name, unchanged, the absolute normalised starting directory before any -C, and GIT_DIR and GIT_WORK_TREE from the call's environment (the inherited environment when none is given). These facts are JSON, so an argument's newline cannot break the log's line format. The recorder does not classify the calls. Python raises no audit event for a stat, so the recorder also wraps os.path's exists, lexists, isfile, isdir and islink, which pathlib's exists, is_file and is_dir call, and writes down each path inside the checkout they check. An open that fails is written down too: the event comes before the open. Both machines already run a sitecustomize.py of their own (Homebrew's on the Mac sets sys.executable; Debian's on ned-box), so the recorder runs the one it shadows after installing itself. A process started with -I, -E or -S, or with an environment that drops PYTHONPATH, is not recorded.

- Strace, on Linux, only in a run given --record-inputs-with-strace, which scripts/scheduled-full-test-run-of-main.py gives, when strace is installed and this program is not itself being traced: `strace -f -ff --seccomp-bpf -z -y -e trace=%file` around each suite, which sees every path any process opens, stats or executes, git and shells included. --seccomp-bpf stops a traced process only at the calls traced, and -z writes only calls that succeeded; the trace is deleted once read, because the heaviest suites write hundreds of megabytes. A run killed before it deletes them leaves the traces of the suites it was running; a later run removes them once nothing of the killed run still runs (see RUN RECORDS in the test runner's docstring). Inside another strace (a full run that runs this program's own test) a second strace cannot attach, so the audit hook works alone there.

Strace adds to the suites' summed seconds, as the test runner's docstring measures under WHAT IT COSTS AND WHAT IT CHOOSES, and on ned-box its processes held the machine's CPU at the level where admission stops starting suites, so every other run records with the audit hook alone. A strace run also keeps, apart from the recording, each suite's files only strace saw it read: those a git command or a shell script read. A run that records with the audit hook alone replaces the recording, and a run given its own --recorded-inputs-directory, such as merge-lane-2's head runs, selects by recordings the scheduled run did not make, so selection reads these lists from --suite-files-only-strace-saw-lists-directory, whose default is where the scheduled full run keeps its recordings: a suite also runs when a file on its list differs. A run with the audit hook alone records the files on the list among the files read, with their blob hashes in its checkout. A strace run in which the suite failed or skipped a case without the mark saw only part of what the suite reads, so it adds the files it saw to the last list, or starts the list when there is none; a strace run that passed and skipped only marked cases replaces the list. Each list records when such a run last added to it. A selective run on Linux names how many suites have no list from a strace run in the last FILES_ONLY_STRACE_SAW_LIST_MAXIMUM_AGE_HOURS_BEFORE_NOTICE hours, which a suite added since the last scheduled run, or a missed scheduled run, causes, and, apart, each suite whose list in that time came only from runs that failed or skipped a case without the mark, with the --only-suites-named command that runs those of them the run did not choose.

A recording keeps, per suite: its exit code and seconds; each file read, with its git blob hash; each path it opened or checked for, and whether the path was there; each directory it listed, with the entries the directory held; the git calls run from the checkout, with their arguments, starting directory, GIT_DIR, GIT_WORK_TREE, the names of the other GIT_ variables set on it and what each call reads; the command names of only the calls that read the checkout, of those whose answer can change when a file is added or deleted, and of those whose answer can change when any file is, with a fingerprint of the checkout's list of files; the git ls-files calls tied to that list only through their pathspecs, each with its directory relative to the top, its pathspecs and a fingerprint of the files it listed; which recorders made it; and, in a strace run, the files only strace saw. A starting directory inside the checkout is kept relative to its top directory, with '.' for the top itself; one outside is kept absolute. A recording made in an older format than this program writes selects its suite once, so the suite is recorded afresh. The files are those git tracks or would add, untracked and not ignored, as the run found them when it started. A `.pyc` read is recorded as the source file beside its `__pycache__`, because an import that finds a valid cache never opens the source. Recordings live outside every checkout, under --recorded-inputs-directory and then the repository's root commit, one file per suite: worktrees come and go and every one of a clone's worktrees, and every clone, shares the same paths, so a recording made in one serves them all. Every run not given --leave-recorded-inputs-and-failure-history-unchanged replaces the recordings of the suites it ran, a failed or killed run's included, so the last recording always says how the suite's last run ended; the scheduled full run refreshes them all. Each recording is written to a temporary file of its own and renamed into place under a short lock held per suite, so runs in two checkouts saving one suite at once never mix their contents, and a reader sees one whole recording. A run reads each recording once, when it starts, and both selection and starting order use what it read. A recording that cannot be saved removes the earlier one, unless another run saved a newer one since this run read it; that one records its own run's inputs, so it is kept. A run given --save-recorded-inputs-to-directory saves, and on a failed save removes, there instead, and leaves --recorded-inputs-directory as it found it.

## How a recording is compared with one commit

A call's -C is walked as written when the call has at most one -C, its path is made of directory names with no ., .. or empty name, and, where the path is in the checkout, no symbolic link is on it. git enters every directory on the way, and a recording names only the one a call ends in, by its real path, so each rule below that stands for a call by its directory needs its -C walked as written; a call whose -C is not walked as written is tied to the whole list of files. Whatever its kind, every git call records the checkout's directories its -C options enter as looked for, and the symbolic links they pass as read, so deleting such a directory, or deleting or retargeting such a link, selects its suite.

Two explicit allowlists set aside git calls that read no file of the checkout. Every call is checked against its full arguments:

- A call sees no file when its only global option is a -C walked as written, or none, and its command is rev-parse followed by at least one argument, all from --show-toplevel, --git-dir, --absolute-git-dir, --git-common-dir, --is-inside-work-tree and --show-prefix; or its command is config followed by exactly one key, exactly --get <key>, or exactly --get-all <key>. A key does not start with '-', contains a '.', contains no '=' and no whitespace; user.* keys are included. The six rev-parse options say where the checkout and its git directory are, from the current directory and the repository's location alone. Config reads answer from configuration in the git directory or the user's home, never from a file of the checkout. Anything else on the call fails this allowlist, including rev-parse --verify <abbreviated hash>, whose answer depends on the object store, which every commit changes: a new object can make the abbreviation ambiguous.

- A call runs on another repository when its only global options are -C <dir>, --git-dir <path>, --git-dir=<path>, --work-tree <path> and --work-tree=<path>; it names a git directory by its last --git-dir value, or otherwise its recorded GIT_DIR; that directory resolves outside both the checkout's top directory and its common git directory; and either its last --work-tree value, or otherwise its recorded GIT_WORK_TREE, resolves outside the top directory, or its command reads no work tree: rev-parse, log, show, cat-file, for-each-ref, config, or worktree whose first argument is list. A -C, when it has one, must be walked as written. Relative paths resolve against the directory the call works in, then through realpath. The common git directory is git rev-parse --git-common-dir, resolved against the top directory when relative, then through realpath; when unknown, only the top directory counts as the checkout. A linked worktree's own git directory is outside its top directory but inside its common git directory, so still belongs to the checkout's repository. The listed commands read the other repository's objects, refs and configuration. Status, diff, add, checkout, ls-files and stash given --git-dir without a work tree use the current directory as their work tree, so still read the checkout.

A call that reads the checkout is still not tied to the checkout's list of files when its answer comes from commits, refs, another repository or the paths it names, so that adding or deleting any other file cannot change it. The command and every option must be on an explicit list, and its only global option a -C walked as written naming a directory that exists, or none, with no GIT_DIR or GIT_WORK_TREE: rev-parse, log and merge-base given revisions with no ':' (a revision with ':' names a path in a tree), none starting with '^', holding a glob character or naming a directory, since git takes such an operand as a path whose files decide the answer, and none that, taken as the path of the file git looks for under its name, holds .. or passes a symbolic link, as for -C; ls-remote given an absolute repository path outside the checkout's top directory; check-ignore given paths in the top directory, since a path below a directory depends on what that directory is. The paths git consults in the work tree for such a call are recorded as read or looked for: for rev-parse and log, a file named like each revision, which makes the argument ambiguous or, for one that does not resolve, gives rev-parse its answer; for log, .mailmap; for check-ignore, each path given, since a tracked path is never ignored, and the top .gitignore. Every other call reading the checkout, such as ls-tree, status, diff, add, stash, commit, grep or worktree, stays tied, and so does an option not on the list.

A git ls-files call is tied to the list of files only through its pathspecs when what it lists is the files of that list its pathspecs match: its only global option a -C walked as written naming a directory inside the checkout, or none; no GIT_ variable set on it but those in GIT_VARIABLES_CHANGING_NO_FILE_A_LISTING_SEES, only the options in GIT_LS_FILES_OPTIONS_LISTING_THE_FILE_LIST, --others only with --exclude-standard, at least one pathspec, and no pathspec magic but glob, literal, icase, exclude and top. Which files a pathspec matches is asked of git itself: git ls-files runs with the call's pathspecs from its directory on a scratch index holding the files to match. That index holds every path as a file, and a directory pathspec matches a submodule but not a file of the same name. So when the checkout's index, or the commit given to --only-suites-whose-recorded-inputs-changed-since, holds any submodule, even one the call's pathspecs do not match, a call being recorded is tied to the whole list, and a call already recorded as tied only through its pathspecs selects its suite. Any other git ls-files call, or one git could not match when recorded, stays tied to the whole list.

Anything else stays git on the checkout and follows the rules below, including calls with no parseable command, a clone whose source is inside the checkout, and an init naming a directory inside it. A call set aside does not trigger any of the three git reasons below; the recorded files, paths and directory listings are still compared. When every recorded git call is set aside and those comparisons pass, the NOT SELECTED line says which calls see no file and which commands run on another repository.

The files that differ are `git diff --no-renames COMMIT` against the checkout's files, plus untracked files git does not ignore, as added. Every suite runs when one of them is this program (it holds the recorder), under .claude/guard-hooks/, or .claude/settings.json. Otherwise a suite runs when: it has no recording on this machine, or one made by an older version of this program; its recorded run did not exit 0, since a run that failed or was killed recorded only what it read before it stopped; its recorded run skipped a case without the mark `[this machine cannot run it]`, since the cases skipped recorded nothing, and a skip can be a run disturbed by another (a marked case never runs on this machine, so what it would read does not matter here); the suite file itself differs; a file it read differs; a path it looked for was added or deleted; an entry was added to or deleted from a directory it listed, a new subdirectory's name included; a file was added or deleted and it ran a git command on the checkout that is tied to the whole list of files, or a git ls-files call whose pathspecs match that file, or git could not say which files the call lists; or it ran a git command on the checkout that reads file contents (anything but the listing commands in GIT_COMMANDS_THAT_ONLY_LIST), and any file differs — strace or not, because git reads a committed file's content from the object store, where no recorder sees a working file.

Then, because every clone and worktree on a machine shares the store, the recording may have been made on another branch, where the suite read other files. A suite also runs when its recording does not match the checkout: a file it read has another blob hash, a path it looked for is there or absent where it was not, a directory it listed holds other entries, or it ran git on the checkout tied to the whole list of files, and the checkout's list of files has another fingerprint, or a git ls-files call tied to it only through its pathspecs, and the files it lists have another fingerprint. A recording saved before recordings named the tied commands counts every git command it ran on the checkout as tied, and one saved before they named the git ls-files calls tied only through their pathspecs ties every git ls-files call to the whole list. So a suite is NOT SELECTED only when everything its recording saw is the same at COMMIT, in the recording, and in the checkout. Each suite gets a line saying SELECTED or NOT SELECTED and why, before any runs.

## How the comparisons with more than one commit combine

Given `--only-suites-whose-recorded-inputs-changed-since` more than once, the test runner compares the recordings with each commit by the rules above, and runs a suite only when every comparison selects it. A commit given twice counts once. A suite every comparison selects gets a SELECTED line with each comparison's reason; a suite one comparison leaves out gets a NOT SELECTED line naming the first commit whose comparison leaves it out, with that comparison's reason. A suite in `SUITES_RUN_WITHOUT_ANY_SANDBOX` stays in a selective test run only when every comparison finds a file it read that differs, as SUITES LEFT OUT OF A SELECTIVE RUN in the test runner's docstring says for one comparison.

Every reason above that does not depend on the commit, such as a suite with no recording, a recording of a failed test run, or a recording that does not match the checkout, selects the suite in every comparison, so a second commit never leaves out such a suite. A second commit leaves out only a suite whose inputs differ from one commit but not from the other.

## Which commits merge-lane-2's test runs compare with

- **The head test run**, `scripts/pull-request-head-test-run.py`, tests a pull request merged with main, and compares with the merge base of the pull request's nn-head-commit and main, unless it is given `--since`.
- **The after-merge test run**, which `scripts/merge-lane-pull-request-merge-through-merge-gate-with-stacked-pull-request-retarget.py` runs on main at the merge commit, compares with two commits when both are known: the newest main commit whose own after-merge test run left no test failing, and the commit the pull request's newest passing head test run tested. With one of the two, it compares with that one alone. With neither, it compares with the pull request's nn-head-commit. That program's docstring says where it reads each commit from.

The after-merge test run compares with both commits for two reasons. The comparison with the newest main commit whose after-merge test run left no test failing reruns every suite whose inputs changed since main last passed, so a suite a failed after-merge test run left failing is run again on each later merge until main passes it. The comparison with the commit the head test run passed on leaves out a suite whose inputs have not changed since that head test run tested them. So a suite runs after a merge only when its inputs changed both since main last passed and since the head test run.

The head test run leaves out every suite in `SUITES_THAT_RUN_THE_REAL_CLAUDE_CLI`, and every suite in `SUITES_RUN_WITHOUT_ANY_SANDBOX` that reads no file the pull request changes, yet its commit still counts in the after-merge test run's comparison for those suites. Such a suite whose recording does not match the merge commit is still selected, by the reasons that do not depend on the commit. One whose recording matches the merge commit is left out, even when it would be selected because the pull request changed the test runner or a file under `.claude/guard-hooks/`, or because it runs a git command that reads file contents. `scripts/no-sandbox-test-suites-run-on-main-in-a-quiet-gap.py` and the scheduled full test run run those suites on main.
