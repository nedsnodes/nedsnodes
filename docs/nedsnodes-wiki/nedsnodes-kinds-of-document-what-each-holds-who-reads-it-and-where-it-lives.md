# Kinds of document in this project: what each holds, who reads it, and where it lives

This page lets an agent decide which kind of document holds a fact about this project, so that the agent knows where to look for the fact and where to write it. Each fact has one canonical location; every other document that needs the fact links there instead of restating it. A one-sentence summary beside its link, such as an overview's line for a component, is not a restatement. A text whose reader is not expected to follow links, such as a tool-message-to-agent, carries what its reader needs to act.

Each kind's entry names its text-intended-reader-category: who the document is written for, and so how its cold read or its test checks it, as that category's entry in `docs/nedsnodes-wiki/nedsnodes-glossary.md` says. A part of a document that a program reads, such as frontmatter, a hashtag line or a heading a script parses, is machine-readable as well and gets both categories' checks, as the glossary entry machine-readable says. A kind has rules of its own, on this page or in its type definition, only where its work needs them, such as the `#root_cause` line of a pull request description; every other kind is written for its text-intended-reader-category's reader and checked as that category's entry says, and has no rules of its own.

A kind's type definition is the document that says what the kind contains, what it leaves out and how long it is. Where one exists, the kind's entry names it after "Defined in:", and this page does not define the kind again; an entry with no "Defined in:" is the kind's only definition. [GHI 1080, Type definitions for the project's kinds of markdown: what each contains, leaves out, and how long it runs](https://github.com/nedsnodes/nedsnodes/issues/1080) is writing the ones still missing; an entry cites it by the name of its item in `docs/issues/1080-type-definitions-for-the-project-s-kinds-of.md`. A kind's file name pattern and directory, where the naming standards give one, are in `docs/nedsnodes-wiki/nedsnodes-file-naming-and-location-standards.md`, and a kind named by a project-term or system-term has that term's entry in its glossary.

## The kinds are a flat list

Every document is one kind; a document that fits no other kind is miscellaneous, as the section "A document that fits no kind, or two" says. An entry that names two documents, such as walk-document and walk-minutes, is one kind. A `-draft` or `-candidate` file, as the naming standards' section "Filename suffixes" defines the two suffixes, is the kind it will be, and its suffix marks only its stage; while it is written it lives in a queue directory or `docs/drafts/`, as the naming standards say, or, for an approval-walk's draft, in `docs/walk/`, as the /walk-me-through skill says, and then in the log-store. A GHI-MD that is a design is a design, as the naming standards' entry "Design document, including a GHI-MD that is a design" says.

A program's file holds its docstring, or its header comment in a language without docstrings, which is a document; the tool-messages-to-agent it prints or hands an agent, which are documents of that kind; and its code, comments included, which is not a document. The code is listed below with the documents only because it is the canonical location of what the system does. A project-term that groups several kinds, such as agent-instructions or standing-agent-instructions, names a group, not a kind; its glossary entry says which kinds it groups.

A document is split when it has parts that each, on their own, fit a different kind: each such part moves to a document of its kind, and the document links it. The move needs whatever approval the files it changes need, as the naming standards' section "Files the user reviews" says. A document, or a part of one, that fits the description of two kinds, so that an agent cannot tell which kind it is, goes to the user, as the section "A document that fits no kind, or two" says.

## The code, and the documents that describe the system

- **The code and its tests.** Holds: what the system does, in full; a test says what must keep passing. Reader category: machine-readable; its comments are agent-readable. Read by: any agent that changes the system, and any agent checking what a document claims. Lives in: `nn-systems/`, `scripts/`, `.claude/guard-hooks/` and the other code directories the naming standards give.
- **A program's docstring and `--help`.** Holds: what one program does, how to run it, its options, exit codes and failure behaviour, what it does not handle, and what a person or agent does just before and after running it. A hook and a -common module have the docstring alone, with no `--help`; the docstring of a test, or of a test helper, says what it covers. Reader category: human-and-agent-readable. Read by: an agent or the user about to run the program, and an agent about to change it. Lives in: the top of the program's file; every program a person or agent runs answers `--help`, as `scripts/every-repository-program-help-option-test.py` tests. Defined in: for a -hack file, the glossary entry nn-hack.
- **nn-architecture-overview.** Holds: the facts about a system that no single file states, in the sections its type definition gives. [GHI 4653, Replace every architecture overview with a guide-agent for each system under `nn-systems/`, and remove the overviews and everything that writes, checks or refreshes them](https://github.com/nedsnodes/nedsnodes/issues/4653) removes this kind; until it merges, an agent changes an existing overview only to keep it true and writes no new one. Reader category: human-and-agent-readable. Read by: an agent about to change, debug or review a system, mostly by searching it for one fact and then reading the code. Lives in: `docs/nedsnodes-wiki/nedsnodes-<system>-architecture-overview.md`, for a system that has one; `docs/nedsnodes-wiki/nedsnodes-project-architecture-overview.md` lists the systems and links each overview that exists. Defined in: the glossary and `docs/nedsnodes-wiki/nedsnodes-how-to-write-an-architecture-overview.md`.
- **Design.** Holds: before its code is built, what to build and why; once built, only what the code cannot say: the user-rulings and their reasons, the alternatives turned down, the facts about outside programs the design rests on, its known holes and its deferred-decisions. Reader category: human-and-agent-readable. Read by: an agent that builds the design, changes it, or checks a change against a user-ruling; the user, when he rules on it. Lives in: where the naming standards' entry "Design document, including a GHI-MD that is a design" says. Defined in: GHI 1080, item "Designs" (not yet written).
- **Test-design and design-contract.** Hold: what the glossary entries test-design and design-contract say. Reader category: human-and-agent-readable. Read by: the agent that builds or tests the design, and the user, to whom design-to-main brings them. Lives in: beside their design, as the naming standards' entry "Tests, test-designs, design-contracts" says. Defined in: the glossary.
- **Runbook.** Holds: the fixed steps of one operation that spans several programs or machines, such as restarting a handoff-supervisor or setting up a machine, each with the machine it runs on: in order, with what to look at before going on, or, where each case needs a different program, which one to run in which case. An operation that one program does, with what the agent does just before and after, belongs to that program's docstring, not to a runbook. Reader category: human-and-agent-readable. Read by: the agent or the user carrying out the operation. Lives in: `docs/nedsnodes-wiki/nedsnodes-<operation>.md`, such as `docs/nedsnodes-wiki/nedsnodes-handoff-supervisor-restart-onto-main-code-when-it-will-not-restart-itself.md`. Defined in: this entry, until GHI 1080's item "Wiki pages other than overviews" defines it.
- **Glossary.** Holds: one definition of each project-term or system-term, with a link to more detail where there is more. Reader category: human-and-agent-readable. Read by: an agent that meets a term it does not know, as `CLAUDE.md` says, and the user. Lives in: `docs/nedsnodes-wiki/nedsnodes-glossary.md` and the system glossaries it lists. Defined in: the project glossary's opening paragraphs; GHI 1080, item "Project glossary entries" (not yet written).
- **Rules page.** Holds: the rules an agent applies to one kind of work across the project, such as naming, word choice, which changes need the user's approval, or how to write a tool-message-to-agent. Reader category: human-and-agent-readable. Read by: an agent doing that work, sent there by `CLAUDE.md`, a skill or a hook, and the user, who approves the page. Lives in: `docs/nedsnodes-wiki/`. Defined in: GHI 1080, item "Wiki pages other than overviews" (not yet written).
- **Explanation page.** Holds: a description, which no one system owns, of how part of the project works, which an agent needs in order to judge a case no rule covers, such as `docs/nedsnodes-wiki/nedsnodes-agent-seat-model.md` or `docs/nedsnodes-wiki/nedsnodes-fleet-git-worktree-working-model.md`. Reader category: human-and-agent-readable. Read by: an agent facing such a case, and the user. Lives in: `docs/nedsnodes-wiki/`. Defined in: GHI 1080, item "Wiki pages other than overviews" (not yet written).
- **README.** Holds: what a directory is for, for a person who opens it first. Reader category: human-and-agent-readable. Read by: the user or an agent new to the repository or the directory. Lives in: the directory it describes, as `README.md`.

## Documents that instruct agents

- **`CLAUDE.md`.** Holds: the rules every agent follows in every agent-session; `AGENTS.md` points Codex at it. Reader category: human-and-agent-readable. Read by: every Claude Code agent, which loads it at start; a Codex agent, which `AGENTS.md` sends to it; and the user, who approves it. Lives in: the repository's root.
- **Seat-brief.** Holds: one agent-seat's job, what it owns and where its work goes. Reader category: human-and-agent-readable. Read by: every agent-session of that agent-seat, and the user, who approves it. Lives in: where the glossary entry seat-brief says. Defined in: GHI 1080, item "Seat-briefs" (not yet written).
- **Skill.** Holds: the procedure an agent follows for recurring work that needs judgment, loaded when the task that the `description` field of its `SKILL.md` frontmatter names comes up, or when the user types its name. A skill differs from a runbook in that its steps need judgment and it is loaded when its task comes up; a runbook's steps are fixed, and whoever carries out the operation opens it. Reader category: human-and-agent-readable. Read by: the agent doing that work, and the user, who approves it. Lives in: `.claude/skills/<skill name>/SKILL.md`; its programs, prompts and other files under `nn-systems/skills/<skill name>/`, each of its own kind.
- **Agent definition.** Holds: one kind of subagent's description, which Claude Code shows an agent choosing a subagent, the tools it gets, and its instructions. Reader category: human-and-agent-readable. Read by: the agent choosing a subagent, the subagent it starts, and the user, who approves it. Lives in: `.claude/agents/<agent name>.md`.
- **Prompt.** Holds: agent-instructions handed to an agent: a `-prompt.md` or `-instructions.md` file a program hands an agent, initial-agent-instructions or text a program appends to a system prompt included; or a one-off-prompt, such as the subagent's prompt an agent writes when it starts a subagent. Reader category: human-and-agent-readable for a `-prompt.md` or `-instructions.md` file; agent-readable for a one-off-prompt. Read by: the agent that is handed it; for a file, also the user, who approves it. Lives in: where the naming standards' entries "Skill prompt" and "agent-instructions" say; a one-off-prompt where the glossary entry one-off-prompt says.
- **tool-message-to-agent.** Holds: what the glossary entry tool-message-to-agent and `CLAUDE.md`'s bullet on tool-messages-to-agent say. Reader category: agent-readable. Read by: the agent the program reports to. Lives in: the program's source. Defined in: the glossary, `CLAUDE.md` and `docs/nedsnodes-wiki/nedsnodes-how-to-write-a-tool-message-to-agent-such-as-a-hook-refusal-or-script-error.md`.

## Documents that track work and decisions

- **GHI-MD.** Holds: one GitHub issue's subject, why it matters, what the user has decided about it, its open questions and its next action, and, once done, its outcome. Reader category: human-and-agent-readable. Read by: the agent that takes up the work, ghi-guide-agent, reviewers and the user. Lives in: `docs/issues/`; a GHI-MD that is a design moves as the naming standards' entry "Design document, including a GHI-MD that is a design" says. Defined in: the /ghi-write skill; GHI 1080, item "GHI-MDs" (not yet written).
- **Walk-document and walk-minutes.** Hold: the walk-document, the items of one approval-walk as shown to the user; the walk-minutes, what he answered to each and where the approval-walk stands. Reader category: human-and-agent-readable. Read by: the user, the agent running the approval-walk and its successor, and agents searching for a user-ruling. Lives in: `docs/walk/` of the checkout the approval-walk runs in while it is open, then the log-store's `walk/` once shipped. Defined in: the /walk-me-through skill.
- **Build-slice plan.** Holds: a design's numbered build-slices, and which are built, being built or planned. Reader category: human-and-agent-readable. Read by: the agent building the next build-slice, and the user. Lives in: `docs/issues/`, such as `docs/issues/3-main-gatekeeper-build-slice-plan.md`.
- **Pull request review.** Holds: a reviewer's findings on one pull request, one finding per comment. Reader category: agent-readable. Read by: the pull request's author and the merge-lanes. Lives in: GitHub. Defined in: the /pull-request-review-write skill and `docs/agents/pr-reviewer-instructions.md`.
- **Commit message and pull request description.** Hold: what one change did and why, and the history and citations behind it. Reader category: agent-readable. Read by: reviewers, the merge-lanes, and an agent tracing why the code is as it is. Lives in: the commit message in git; the pull request description on GitHub. Rule of its own: a pull request description carries a `#root_cause`, `#root_cause_not_fixed` or `#no_defect_fixed` line, as `scripts/merge-gate.sh` requires; step 1 of `docs/agents/pr-reviewer-instructions.md` says when a `#root_cause` or `#root_cause_not_fixed` line is due.
- **proposed-improvements-or-changes-file.** Holds: reviewers' proposed changes to a document or to what the document describes, as the glossary entry proposed-improvements-or-changes-file says. Reader category: agent-readable. Read by: the agent that settles them. Lives in: where that glossary entry says.

## Records of agent-sessions and work

- **Session-handoff and conversation-tail.** Hold: the session-handoff, what a successor agent-session needs to continue; the conversation-tail, the verbatim tail of the dialog. Reader category: agent-readable. Read by: the successor, at its start. Lives in: `~/.claude/handoffs/` on the agent-seat's machine, never committed. Defined in: the glossary; GHI 1080, item "Handoff next-step files", which covers the session-handoff (not yet written).
- **Log-store records.** Hold: logs, reports, captures and analyses, named by the suffixes the naming standards' section "Filename suffixes" lists, and cold-read-records. Reader category: agent-readable for reports, analyses and captures, and for the reports in a cold-read-record; machine-readable for logs; a frozen-copy keeps the category of the document it copies. Read by: the agent that asked for the work, the user, and agents searching the past with the /find-info skill. Lives in: the log-store; a cold-read-record first in the checkout's `cold-read-records/`, as the glossary entry cold-read-record says.

## Where each fact lives

| The fact | Its kind |
|---|---|
| How to run one program, its options, exit codes and failures | that program's docstring and `--help` |
| What the code does, in detail | the code and its tests |
| A rule several components keep that no single file states | nn-architecture-overview, Invariants, for a system that has one; otherwise the system's design |
| What a component is for, and where it is | nn-architecture-overview, Components, in one sentence, for a system that has one; otherwise the component's docstring |
| A rule an agent applies to one kind of work across the project | rules page |
| How a part of the project that no one system owns works | explanation page |
| Why a system is built as it is; a user-ruling about it and its reason | design |
| The fixed steps of one operation across several programs or machines | runbook |
| The steps an agent follows, with judgment, each time a kind of work recurs | skill |
| What a project-term or system-term means | its glossary |
| What every agent does in every agent-session | `CLAUDE.md` |
| One agent-seat's job | seat-brief |
| Work not yet done, and its open questions | GHI-MD, or the agent-seat's task list, as the /ghi-write skill decides |
| How a change came to be: dates, incidents, review rounds | its commit message and pull request description |
| What the user answered in an approval-walk, and when | walk-minutes |

## Kinds this page leaves out

Settings and data files, such as `.claude/settings.json` or `nn-systems/general-tools/scheduled-jobs-on-each-machine.json`, are machine-readable and are not documents, so this page gives them no kind. Prose that a program reads as data, such as the word table of `docs/nedsnodes-wiki/nedsnodes-style-guide.md`, is part of the kind of the document it sits in, and is machine-readable as well; the naming standards' entry "Prose a program reads as its data" says where such a file lives.

## A document that fits no kind, or two

A document that fits no other kind on this page is miscellaneous, such as the research notes under `docs/cross-project/`. A miscellaneous document says in its opening lines which text-intended-reader-category it is written for, and is written and checked for that category; an agent does not ask the user what kind it is. A miscellaneous document on main that does not yet say its category gains that line at its next edit. Claude Code's memory files, under `~/.claude/projects/<project>/memory/`, are miscellaneous and human-and-agent-readable, and need not say so.

A document, or a part of one, that fits the description of two kinds, so that an agent cannot tell which kind it is, goes to the user in an approval-walk: he decides whether it belongs to one of them, should be split, or is a new kind, and until he rules the document stays as it is. A new kind is added to this page only once he approves it.
