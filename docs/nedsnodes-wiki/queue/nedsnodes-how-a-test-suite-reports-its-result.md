# How a test suite reports its result

This page says how an nn-test-suite in this repository tells the test runner, `scripts/run-all-test-suites.py`, whether it passed, and what the test runner prints. Read it before you write an nn-test-suite, or a program that reads the test runner's output. The test runner's module docstring, at the top of the file, holds its rules; this page is the short version of the parts an nn-test-suite's author needs, and a program that reads the test runner's output needs the docstring's OUTPUT and EXIT sections as well. The last section, on canary tests, describes rules the user has decided for programs not yet built; the test runner's docstring does not cover those rules.

The project glossary, `docs/nedsnodes-wiki/nedsnodes-glossary.md`, defines an nn-test-suite. On this page a test case is one test inside an nn-test-suite.

## What counts as an nn-test-suite

The test runner runs only files that git tracks, so commit a new `-test.py` or `-test.sh` file, or `git add` it, before you expect it to run. A full test run, which is the test runner started without `--only-suites-whose-recorded-inputs-changed-since` or `--only-suites-named`, runs every nn-test-suite, except one that gets a `NOT RUN` line, unless the test run is stopped or ends early, as the last paragraph of the next section says; `--stop-at-first-failing-suite` stops it once an nn-test-suite fails, and `--run-time-limit-seconds-not-counting-admission-waits` once the test run's time limit has passed. Run with `--only-suites-whose-recorded-inputs-changed-since <commit>`, as the test run at a pull request's nn-head-commit is, the test runner runs only the nn-test-suites its docstring's selection rules pick, and prints a `SELECTED` or `NOT SELECTED` line for each nn-test-suite it considered: every nn-test-suite, or, when `--only-suites-named` is given as well, the ones named, with the one exception the next sentence gives. Where nn-test-suites run in nn-test-sandboxes, on Linux with bwrap, such a test run without `--only-suites-named` also leaves out each picked nn-test-suite that `SUITES_RUN_WITHOUT_ANY_SANDBOX`, a dict in `scripts/run-all-test-suites.py`, lists, and prints for it, in place of its `SELECTED` line, a line opening `NO-SANDBOX SUITE LEFT OUT OF SELECTIVE TEST RUN` with the command that runs it by hand.

The test runner runs each nn-test-suite as a script, `<python> -u <path>` or `sh <path>`. It does not run pytest or unittest's test discovery. So an nn-test-suite that uses Python's `unittest` must itself run its test cases and exit nonzero when one fails: `unittest.main()` does both, while after `unittest.main(exit=False)` or `unittest.TextTestRunner().run()` the nn-test-suite must exit nonzero itself; a file that only defines `test_` functions for pytest runs none of them and exits 0, which the test runner reports as a pass. No nn-test-suite in the repository uses pytest.

## Pass or fail: the exit code, not the output

An nn-test-suite passes when its process exits with code 0, unless the memory ceiling case below fails it. It fails when it exits with any other code, when a signal kills it, when the test runner kills it at its per-suite time limit, which the docstring's PER-SUITE TIMEOUT section sets, or, where nn-test-suites run in cgroup scopes, when the kernel kills one of its processes at its memory ceiling, even if the nn-test-suite then exits 0; the docstring's MEMORY CEILING section says where that is. Three ways of ending without exit code 0 are exceptions, and count as neither a pass nor a fail. An nn-test-suite killed because the test run was stopped counts as stopped: the line the test runner prints for it opens `FAIL` and says `killed when the run was stopped by`, and in a test run that reaches its `SUMMARY:` line it is left out of the list of failed nn-test-suites and counted as stopped. An nn-test-suite whose bwrap failed after the test runner started it, before the nn-test-suite started, gets a `NOT RUN` line, as the last paragraph of this section says, and so does an nn-test-suite that exits 75, the constant `NN_TEST_SUITE_EXIT_CODE_FOR_NOT_RUN_BECAUSE_A_CAUSE_OUTSIDE_THIS_REPOSITORY_STOPPED_ITS_CASES` of the module the next section names, because a cause outside this repository, such as claude's usage limit, kept its test cases from running: the last line of its output names that cause, and the `NOT RUN` line repeats it. An nn-test-suite exits 1, not 75, when any of its test cases failed.

The test runner reads no text an nn-test-suite prints to decide whether it passed. On Linux it reads each test case line, a line that opens with the word `PASS`, `FAIL` or `ok` after any whitespace, only to time that test case and, where nn-test-suites run in nn-test-sandboxes and the test run reaches its `SUMMARY:` line, to record that time; a line that opens `PASSED`, or `OK` in capitals, is not a test case line. nn-test-suites print success in several wordings, such as "all cases passed" or "OK", so no wording can be trusted. An nn-test-suite that finds a failure must exit nonzero: printing its own "FAIL" and exiting 0 is reported as a pass.

The exit-code page, `docs/nedsnodes-wiki/nedsnodes-how-a-program-reports-success-failure-and-findings-with-its-exit-code.md`, asks more of a test file than the test runner checks today: exit 1 when a test case fails and 2 when it could not run, and print a verdict line as the last line of standard output. An nn-test-suite's verdict line is the END line, the last line of its standard output, which `nn-systems/general-tools/nn-test-suite-start-time-line-and-end-results-line-print-common.py` prints; the module needs Python 3.12 or later. Every Python nn-test-suite loads that module by path, with `importlib.util.spec_from_file_location`, and calls its `nn_test_suite_start_time_line_print_now_and_end_results_line_print_at_normal_exit_register()` right after its docstring: copy the lines that do both from the top of `scripts/run-all-test-suites-test.py`, and change the `1` in its `parents[1]` to the number of directories between the repository's root and the new file, such as `3` for a file in `nn-systems/<system>/tests/`. A shell nn-test-suite runs `python3 nn-systems/general-tools/nn-test-suite-start-time-line-and-end-results-line-print-common.py start` first, keeps its own counts of passed and failed test cases, and runs `... end <passed> <failed> <exit code>` as its last command, which prints the END line and exits with the code the verdict gives: 0 for exit code 0, 1 for any other. A shell nn-test-suite that could not run, because something it needs is missing, runs `... end 0 0 1`, since a shell nn-test-suite cannot give the could-not-run verdict; one stopped by a cause outside this repository prints the line naming the cause and exits 75 without running `... end`. A shell nn-test-suite that stops before that command, as one under `set -e` does when a command fails, prints no END line. The module's own nn-test-suite, `nn-systems/general-tools/tests/nn-test-suite-start-time-line-and-end-results-line-print-common-test.py`, fails when a tracked `-test.py` file does not contain the call, or a tracked `-test.sh` file does not name the module. No canary test exists yet; the pull request that commits the first one decides how a canary test, whose name also ends `-test.py`, relates to this call.

The call prints `START <UTC time>` at once. When a Python nn-test-suite ends by returning or by `sys.exit`, the module prints, last, `END <UTC time> passed=<N> failed=<M>`, where `<N>` and `<M>` count the lines the nn-test-suite itself printed through `sys.stdout` that open with the word `PASS` or `ok`, and `FAIL`, after any whitespace, so unittest's own result lines, which go to standard error, are not counted; then one verdict hashtag: `#nc_test_suite_pass` with exit 0, `#nc_test_suite_fail` with exit 1, or `#nc_test_suite_could_not_run` with exit 2. Example: `END 2026-11-24T23:10:02Z passed=12 failed=1 #nc_test_suite_fail`. The verdict comes from the exit code. Exit 0 passes, even after a `FAIL` line, such as a child nn-test-suite's that the nn-test-suite passes on. A Python nn-test-suite that stops before testing anything, such as one missing a program it needs, calls the module's `nn_test_suite_could_not_run_exit(reason)` before it prints any `PASS`, `ok` or `FAIL` line; the call prints the reason on standard error and exits 2. Exit 75 keeps its code and gets no END line, so the line naming the outside cause stays last. Every other exit fails, and the module then exits 1, even when the nn-test-suite exited 2 itself, or called `nn_test_suite_could_not_run_exit` after a `PASS`, `ok` or `FAIL` line. An nn-test-suite run on its own that an uncaught exception, a signal or `os._exit` ends prints no END line, and neither does one killed when the test run was stopped, so the test runner reads a missing END line as the nn-test-suite having stopped partway. The module prints neither line when a Python nn-test-suite's file is loaded as a module rather than run, or when the environment variable `NN_TEST_SUITE_CHILD_RUN_PRINTS_NO_START_OR_END_LINE` is `1`: a Python nn-test-suite that runs itself as a child program and compares that child's output sets it for the child. A canary test prints its own hashtags, as this page's section "Canary tests: decided, not yet built" says.

Where nn-test-suites run in nn-test-sandboxes, the test runner writes a `junit.xml` file in its log directory, and reads the END line only to write there the `ran_to_the_end` attribute of each nn-test-suite. It is true when the last non-blank line of the nn-test-suite's log, which holds its standard output and standard error together, so that a line written to standard error after the END line makes it false, is an END line with `#nc_test_suite_pass` and exit 0, or with `#nc_test_suite_fail` and exit 1. It says only that the nn-test-suite ended on its own: one that exits 1 after its first failing test case, before its later test cases, ran to the end too. One with `#nc_test_suite_could_not_run` tested nothing, so it did not run to the end. One that gets a `NOT RUN` line, such as one that exited 75, has no verdict of its own: its entry in `junit.xml` says `judged="false"`, and the merge program below reads nothing from it. `scripts/merge-lane-pull-request-merge-through-merge-gate-with-stacked-pull-request-retarget.py` reads the attribute: after it merges a pull request, it reads the test run of the merge commit, and, on the list of test cases failing on main that `scripts/merge-lane-failed-after-merge-test-suites-on-main-record.py` keeps, it keeps each test case of an nn-test-suite that did not run to the end and printed nothing for that test case, rather than removing it, and prints a `STOP:` line telling the author and the user which nn-test-suite did not run to the end. The verdict hashtag does not decide pass or fail: the test runner judges each nn-test-suite as this section's first paragraph says, so exit 2 fails an nn-test-suite just as exit 1 does.

The test runner prints a line opening `PASS`, `FAIL` or `NOT RUN` as each nn-test-suite finishes and, when the test run gets that far, a last line opening `SUMMARY:`. A `NOT RUN` line is for an nn-test-suite whose nn-test-sandbox did not start, or that exited 75: it counts as neither a pass nor a fail. A test run that is stopped or ends early may print no `SUMMARY:` line. The test runner's docstring gives the output under OUTPUT and the exit codes under EXIT.

## Skipped test cases: the `SKIP` line

An nn-test-suite sometimes cannot run one of its test cases, for example because a tool the test case needs is not installed. It then prints one line for that test case and goes on with the other test cases. Print a line that opens with `SKIP` and a space, then gives the test case and the reason; the test runner checks only that `SKIP` is followed by a whitespace character, such as a space or a tab, so the second space and the colon in the example below are optional. A line that opens any other way, such as `SKIP:`, is not counted, and neither is a skip made with unittest's own skip. `scripts/test-suites-source-scan-for-skipped-case-prints-run-all-test-suites-cannot-count-test.py` fails on the text `.skipTest(`, `unittest.skip(`, `unittest.skipIf(` or `unittest.skipUnless(`, even in a comment, though not on `raise unittest.SkipTest(...)` or a `skip` imported from `unittest`, and on a `print(`, `echo` or `printf` followed directly by text that opens `SKIP` without a space right after it, even where the printed line would be counted, as with `print("SKIP\tcase")` or `print("SKIP", name)`, though not on such text after a Python string prefix other than `f`, such as `r`, after a triple quote, or after a shell flag such as `-e`. It scans only the files git tracks whose names end `-test.py` or `-test.sh`, so a `SKIP` line printed by a file an nn-test-suite imports or runs, or printed any other way, such as through `sys.stdout.write`, it does not see. When the machine itself is the cause, its platform or what is installed on it, put `[this machine cannot run it]` right after `SKIP` and its spaces; the test runner reads the mark only there, and its docstring says what the mark changes. Print one line per skipped test case. Example: `SKIP  [this machine cannot run it] the hand-run command's lock case: /usr/bin/flock is missing; it exists on Linux only`.

The test runner counts every line of an nn-test-suite's output that matches the regular expression `^SKIP\s`, and shows a count that is not 0 on the line it prints for the nn-test-suite. A test run that reaches its `SUMMARY:` line also prints each counted line again, with its nn-test-suite, near the end of its output, and the sum on the `SUMMARY:` line. A skipped test case never changes whether the nn-test-suite passed: an nn-test-suite that skips every test case and exits 0 is reported as a pass. A test case skipped with a `SKIP` line does not make an nn-test-suite exit 2: an nn-test-suite exits 0 and prints `#nc_test_suite_pass` when no test case failed, even when it skipped every test case, and exits 2 only when it stopped before its test cases, such as when its own setup failed. The test runner counts lines, so a line that names several test cases counts as one.

GHI [The daily full test runs tell the user about failures and about test cases that run nowhere or lack a tool, and every test suite prints a skipped test case in one format](https://github.com/nedschorus/nedschorus/issues/1206) proposes replacing the `SKIP` line with `SKIPPED test case "<name>"; reason: <reason>`, printed by one shared function, in which a test case that cannot apply on this machine gets a reason opening `not on this platform:` rather than the mark `[this machine cannot run it]`, and changing the test runner's pattern to match. Under that format a missing tool is not a platform cause: such a skip gets a plain reason, which GHI 1206's report brings to the user. Until that change is merged, print the `SKIP` line, with the mark where the machine is the cause.

## Where the report and the logs are kept

A test run writes its whole report to `test-run-report.txt` in its log directory, which the first line of the report names after `; logs in `, beside one log file per nn-test-suite it started; a test run that could not start, and ended before the first line of its report, writes neither. Unless `--log-dir` names another directory, the log directory is under the system temp directory, and on Linux a later test run may delete it once two days have passed, as the docstring's RUN RECORDS section says; copy anything you need to cite within those two days.

`scripts/scheduled-full-test-run-of-main.py` runs every nn-test-suite on main once a day on each machine, ned-box and the Mac, at the times `nn-systems/general-tools/scheduled-jobs-on-each-machine.json` gives; a Mac run missed while the Mac sleeps starts when it wakes. It writes one record per machine and day to `nedlern@ned-box:/home/nedlern/nedsnodes-logs/scheduled-full-test-runs-of-main/<machine>/<YYYY-MM-DD>.txt`, where `<machine>` is `ned-box` or `mac` and the date is the date in America/Los_Angeles when the run started. The record holds the run's failures and, from a test run that reaches its `SUMMARY:` line, its counted `SKIP` lines; the docstring of `scripts/scheduled-full-test-run-of-main.py` lists all it holds. The whole report, `test-run-report.txt`, and the nn-test-suites' log files stay on the machine that ran them, in `<system temp directory>/nedschorus-scheduled-full-test-run-of-main/logs`, which the record names and each scheduled full test run replaces.

## An nn-test-suite that measures something

An nn-test-suite that measures something, such as a duration or how often a hook's reminder is right, prints the number and the threshold, and passes or fails against the threshold, which its author may set by judgement, saying why in a comment beside it. Work whose result is a number with no pass or fail is not an nn-test-suite; it is a program that does work, and reports as the section "A program that does work" of the exit-code page, `docs/nedsnodes-wiki/nedsnodes-how-a-program-reports-success-failure-and-findings-with-its-exit-code.md`, says.

## Canary tests: decided, not yet built

A canary test runs a real outside program that the project does not write, such as `codex` or `gh`, to check that it still behaves the way our code relies on. It is a kind of contract test; it is not a canary release, the software-engineering sense of "canary". The user decided the rules below in approval-walks (user-ruled 2026-10-19 to 2026-10-26). No canary test, and no canary runner, the program that will run one, exists yet.

A scheduled canary test is kept in the repository and runs in the scheduled full test run; a one-shot canary test answers one question for a single change, and is not kept in the repository. A scheduled canary test lives in the `tests/` directory of the nn-system whose code relies on the outside program's behaviour, or in `scripts/` when a program there relies on it, and is named `<outside program>-<behaviour>-canary-test.py` (user-ruled 2026-10-20).

A canary test is one Python file. Its last line of standard output is exactly `#canary_pass`, and it exits 0, when the outside program behaved as relied on; or exactly `#canary_fail`, and it exits 1, when the outside program did not. The third result, `#canary_no_answer`, means the canary test could not tell: the canary test prints it and exits 2 when it finds it cannot check, for example because the outside program is logged out; the canary runner gives it when the last line of standard output is none of `#canary_pass`, `#canary_fail` and `#canary_no_answer`, when the exit code does not match the line, or when the canary test runs past its time limit and the canary runner kills its whole process group. The canary runner logs standard output and standard error together, but takes the result from standard output alone (user-ruled 2026-10-23).

The last line is what tells `#canary_fail` apart from a crash: Python exits 1 on an exception nothing catches, the same code as `#canary_fail`.

The canary runner exits 0 for `#canary_pass` and 1 for `#canary_fail`; it exits 2, saying why, for `#canary_no_answer`, and also when it could not write to the log-store or delete its run directory, the directory it makes for each run to hold a throwaway home directory with planted fake credential files, even after a pass or a fail (user-ruled 2026-10-19). It starts the canary test with `HOME` and `TMPDIR` inside that run directory; the canary test's own code opens no credential file except the planted files, and the outside program it runs, such as Codex or Claude Code, reads its own real sign-in, as it does in real use, because the canary runner sets `CODEX_HOME` and `CLAUDE_CONFIG_DIR` to the real directories (user-ruled 2026-10-19). In the scheduled full test run's record, a `FAIL` line for a canary test gives the canary runner's exit code: exit 1 is `#canary_fail`, and exit 2 says nothing about the outside program (user-ruled 2026-10-25).

The canary runner writes the log of every run of a scheduled canary test, whether the scheduled full test run starts it or it is run by name before a merge, to `nedlern@ned-box:/home/nedlern/nedsnodes-logs/canaries/scheduled/<machine>/<YYYY-MM-DD>T<HHMMSS>-<suite path with each / as __>.txt`, where `<machine>` is the machine that ran it, with the date and time in America/Los_Angeles at the run's start, and the full hash of the commit it ran at as the log's first line (user-ruled 2026-10-26). Each scheduled canary test runs on the machines its file declares in a constant, and on any other machine the test runner skips it, saying so (user-ruled 2026-11-19). A one-shot canary test's Python file, run log and result go to `nedlern@ned-box:/home/nedlern/nedsnodes-logs/canaries/one-shot/<YYYY-MM-DD>-<subject>/`, where `<subject>` names what the canary test checks, the date is the date in America/Los_Angeles at the run's start, and a second run with the same date and subject adds `-2`, a third `-3` (user-ruled 2026-10-19 and 2026-10-20). Each scheduled canary test's log, and each one-shot canary test's directory, is deleted once more than 30 days have passed since its date (user-ruled 2026-10-20 and 2026-10-26).

Today's test runner judges every file it runs by its exit code, as above, and on ned-box, in its nn-test-sandbox, an outside program such as `gh` or `codex` has no login and, by default, no network. The test runner is to start each file whose name ends `-canary-test.py` through the canary runner, outside the nn-test-sandbox, one at a time, under the time limit the file declares in a constant (user-ruled 2026-10-26). That change to the test runner is made in the pull request that commits the first scheduled canary test, and no canary test is committed before it (user-ruled 2026-10-20).
