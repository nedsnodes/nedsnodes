# Bubblewrap sandboxes on ned-box

Read this page before you write a program that starts a bubblewrap sandbox (`bwrap`) on ned-box, or before you run one program inside the sandbox of another, such as the test runner `scripts/run-all-test-suites.py` inside a sandbox that another program starts around an agent, like the one the pilot of GHI [A pilot of three past bug fixes, redone by agents on the code as it stood before each fix, to learn whether a benchmark of agent-instructions and hooks can be built from the project's history](https://github.com/nedsnodes/nedsnodes/issues/1505) plans for `claude -p`. It shows that a second bubblewrap sandbox cannot start inside a first on ned-box, though not which kernel check refuses it; how the test runner copes with that; and, for each program the searches under "Programs on main that start a sandbox" found, what its sandbox shows, what it hides and, where an agent runs inside, how that agent reaches its login file.

## A second bubblewrap sandbox cannot start inside a first

- **Observed** (observation 1): `sysctl kernel.apparmor_restrict_unprivileged_userns kernel.unprivileged_userns_clone` prints `kernel.apparmor_restrict_unprivileged_userns = 1` and `kernel.unprivileged_userns_clone = 1`. bubblewrap is version 0.11.1, at `/usr/bin/bwrap`, and is not setuid; the AppArmor profile `/etc/apparmor.d/bwrap-userns-restrict` exists for it.
- **Observed** (observations 2 and 3): `bwrap --ro-bind / / --dev /dev --proc /proc -- sh -c 'echo single-ok'` prints `single-ok` and exits 0. The same command with a second `bwrap` inside the first prints `bwrap: No permissions to create a new namespace, likely because the kernel does not allow non-privileged user namespaces` and exits 1.
- **Documented**: that AppArmor profile's header comment says bwrap may use user namespaces but "its children do not have capabilities, blocking bwrap from being able to be used to arbitrarily by-pass the user namespace restrictions"; the rules at lines 68 and 79 of the profile give its children the profile `unpriv_bwrap`, which allows `userns` and denies every capability. Which kernel check refuses the second sandbox was not established; turning the sysctl off to test it needs root and was not tried. The limit this page relies on is the observed one: on ned-box, as it is set up, a bwrap started inside a bwrap fails.
- **Observed** on 2026-10-10 (`nedlern@ned-box:/home/nedlern/nedsnodes-logs/seats/prime-intellect/benchmark-sandbox-nesting-probe-2026-10-10.md`): bwrap run inside a Docker container on ned-box also failed, with a different message, `bwrap: Creating new namespace failed: Operation not permitted`, both with Docker's defaults and with `--security-opt apparmor=unconfined --security-opt seccomp=unconfined`. A container started with `--privileged` was not tried, so whether some container is a way around the limit is open; whether the same kernel setting causes the failure in a container was not shown.
- **Observed** (observation 6): Codex's own sandbox hits the same limit. With codex-cli 0.159.3, `codex sandbox -- sh -c 'echo codex-sandbox-ok; cat /proc/1/comm'`, run from `/tmp`, prints `codex-sandbox-ok` and `codex` and exits 0; inside `bwrap --ro-bind / / --dev /dev --proc /proc --tmpfs /tmp` the same command prints a warning that it could not create PATH aliases, then the same "No permissions to create a new namespace" line, and exits 1. That was bare `codex sandbox`, not one of this project's Codex launchers below. **Inferred** from this observation and from the **Documented** fact, under "The Codex launchers", that Codex runs each of the model's commands through `bwrap`: inside another bubblewrap sandbox, each command a Codex launcher's model runs fails this way; the launcher's run itself can still end and write its report, since Codex writes the model's last message outside that sandbox.

**Inferred** from the bullets above: on ned-box a program that itself starts a bubblewrap sandbox fails, or fails in part, when it runs inside another program's bubblewrap sandbox. The test runner, and the two programs that use its nc-test-sandbox, `scripts/run-suite-in-signal-sandbox.py` and `scripts/mutation-testing-changed-lines-quick-or-full-pass-survivors.py`, can be told that they already run inside one, as the next section says. The agy cold-read-cell launcher (`nn-systems/cold-read/cold-read-agy-cell.py`), the Gemini task launcher (`scripts/run-gemini-task-from-brief.py`, which runs agy) and the agy launcher for one prompt (`nn-systems/general-tools/agy-print-prompt-run-in-empty-home-sandbox.py`) cannot be told so, and neither can the sandbox Codex starts for each of the model's commands; run each of them outside any bubblewrap sandbox.

## The test runner inside another program's sandbox

- **Code**: the test runner reads the environment variable `RUN_ALL_TEST_SUITES_INSIDE_SIGNAL_SANDBOX`, whose name is its constant `SIGNAL_SANDBOX_INSIDE_VARIABLE` (`scripts/run-all-test-suites.py:980`); the code's "signal sandbox" names, such as this one, name the nc-test-sandbox. When the variable has a non-empty value, `signal_sandbox()` returns an empty command prefix, and `None` in place of the reason it otherwise gives for running the nc-test-suites outside any sandbox (`scripts/run-all-test-suites.py:3106-3107`): the test runner starts no sandbox, checks nothing about the sandbox it is in, and runs every nc-test-suite inside whatever sandbox the test runner itself was started in. An empty value counts as unset.
- **Code**: the test runner sets the variable to `1` inside every nc-test-sandbox it starts (`scripts/run-all-test-suites.py:3116-3117`), so a test runner that an nc-test-suite starts inherits it and does not try to nest, unless the nc-test-suite removes the variable from the child's environment. `scripts/run-all-test-suites-cleanup-after-killed-runs-real-process-test.py` does so on purpose, for the test runners it starts (lines 184 and 258) and for its own trial of the nc-test-sandbox (lines 269-276).
- **Code**: without the variable, and with `bwrap` on PATH, the test runner tries `bwrap ... true` once before any nc-test-suite runs, and when that fails raises `SignalSandboxCouldNotStart` (`scripts/run-all-test-suites.py:3116-3127`); the test runner then stops with exit 2 rather than run the nc-test-suites outside any sandbox. With no `bwrap` on PATH it runs the nc-test-suites outside any sandbox and the report says why (`scripts/run-all-test-suites.py:3113-3115`).
- **Code**: `scripts/run-suite-in-signal-sandbox.py`, which runs one nc-test-suite or one mutant, is stricter. Started inside another sandbox, it runs the nc-test-suite only when process 1 there is `bwrap` itself, as `/proc/1/comm` shows (`scripts/run-suite-in-signal-sandbox.py:141-146` and `183-186`), and the variable is exactly `1` (`scripts/run-suite-in-signal-sandbox.py:189-192`); otherwise it refuses. A sandbox started with `bwrap --unshare-pid --proc /proc` meets the first condition. A PID namespace whose process 1 is another program does not: inside Codex's sandbox process 1 is `codex` (observation 6).
- **Code**: `scripts/mutation-testing-changed-lines-quick-or-full-pass-survivors.py` calls the same `signal_sandbox()` (`scripts/mutation-testing-changed-lines-quick-or-full-pass-survivors.py:2037-2040`) to check that the sandbox starts, to print the test runner's sandbox line and to decide whether mutants may run in parallel (lines 2050-2053), and runs the nc-test-suites through `scripts/run-all-test-suites.py` as a child process (line 795); so the variable stops it, too, from trying to nest. What else it does inside another sandbox was not checked in its code for this page.
- **Observed** (observation 7): `signal_sandbox()`, called inside `bwrap --dev-bind / / --unshare-pid --proc /proc`, raised `SignalSandboxCouldNotStart` with bwrap's "No permissions to create a new namespace" text; inside the same bwrap with `--setenv RUN_ALL_TEST_SUITES_INSIDE_SIGNAL_SANDBOX 1` it returned the empty prefix.
- **Observed** on 2026-10-10 (the 2026-10-10 record cited above), with the test runner of that date, before the nc-test-sandbox and the test runner's admission control merged on 2026-10-15: the test runner, started with `--only-suites-whose-recorded-inputs-changed-since HEAD~1` and a private lock file inside one bwrap with `--unshare-pid --die-with-parent --proc /proc --setenv RUN_ALL_TEST_SUITES_INSIDE_SIGNAL_SANDBOX 1`, printed "SUMMARY: 15 passed, 0 failed, 15 total; 5 cases skipped in 3 suites" and exited 0. The test runner at the pinned commit has not been run nested this way.

A program that starts a bubblewrap sandbox and runs the test runner inside it must therefore do three things:

- Set `RUN_ALL_TEST_SUITES_INSIDE_SIGNAL_SANDBOX=1` in that sandbox. **Code**: none of the agent launchers under "Programs on main that start a sandbox" below sets it in its sandbox, so a model that runs the test runner inside the sandbox of the agy cold-read-cell launcher, the Gemini task launcher or a Codex launcher gets exit 2, unless its own command sets the variable, as in `RUN_ALL_TEST_SUITES_INSIDE_SIGNAL_SANDBOX=1 python3 scripts/run-all-test-suites.py --lock-file <path> ...`; the third bullet below says why that command also needs `--lock-file`. The agy launcher for one prompt shows no checkout, so there is no test runner to run there.
- Give that sandbox a PID namespace of its own whose process 1 is bwrap, and a private `/proc` (`bwrap --unshare-pid --proc /proc`), so that the nn-test-suites' signals stay inside it. **Code**: the test runner itself does not check for this and runs without it; `scripts/run-suite-in-signal-sandbox.py`, run inside, refuses without it, as the bullets above say. **Documented** (`scripts/run-all-test-suites.py:138-143`): the test runner's own nc-test-sandbox puts each nc-test-suite in a PID namespace so that an nc-test-suite's signals reach only the processes it started, never the agent-seats, which run as the same account. **Inferred**: with the variable set, the outer sandbox is all that confines the nc-test-suites. Its PID namespace keeps their signals from the processes outside it, but not from the agent, the nested test runner and the other nc-test-suites inside it; and the nc-test-suites share the outer sandbox's home directory, `/tmp` and network, which an nc-test-sandbox would give each one privately. **Documented** (`scripts/run-all-test-suites.py:23-26`): such a test runner runs as many nc-test-suites at once as `-j` says, by default the machine's core count; whether they collide when they share one home directory and `/tmp` was not checked.
- Give the nested test runner a lock file of its own with `--lock-file`, in a directory outside the checkout under test that only that sandbox sees and can write. **Code**: the default is `~/.claude/.run-all-test-suites.lock` (`scripts/run-all-test-suites.py:1164`). A test run on ned-box whose nc-test-suites run in nc-test-sandboxes takes no lock, but keeps its run record in the directory `<lock file>.runs` and its admission control in the directory `<lock file>.test-suite-admission`, beside that path, which every test run naming the path shares (docstring, `scripts/run-all-test-suites.py:31-35`; code, `scripts/run-all-test-suites.py:1071`, `1165` and `2109-2112`); a nested test run takes the lock (`scripts/run-all-test-suites.py:4992-5014`; **Documented** in the bullet "The machine lock" of the Outcome of GHI [Each test suite on ned-box runs in its own throwaway test environment, and suites start by free CPU and memory instead of waiting for a machine-wide lock](https://github.com/nedsnodes/nedsnodes/issues/1374), `docs/issues/1374-each-test-suite-on-ned-box-runs-in.md:65`). **Code**: before it runs, each test run removes what ended runs named in those run records left behind, and counts a run as ended when its process IDs are no longer running as `/proc` shows them (`remove_leftovers_of_ended_runs_named_in_run_records()` and `process_alive()`, `scripts/run-all-test-suites.py:2226-2253` and `2137-2144`). **Inferred**: inside a PID namespace of its own, a nested test run that shares those directories with the rest of ned-box sees every test run outside as ended, and can remove the strace traces of a run that is still going. In a sandbox that shows the real `~/.claude` read-only, the default path also fails, because the test runner must create its run-record directory beside the lock file.

## nc-test-suites that cannot run in an nc-test-sandbox

**Code**: the dict `SUITES_RUN_WITHOUT_ANY_SANDBOX` (`scripts/run-all-test-suites.py:1006-1027`) maps each nc-test-suite that cannot do its job inside its nc-test-sandbox to the reason. The test runner reads it from the checkout under test, and from its own file only when that checkout has none (`suite_sandbox_lists_read_from_checkout_under_test()`, `scripts/run-all-test-suites.py:1834`). When the test runner starts the nc-test-sandboxes itself, it runs these nc-test-suites outside any sandbox and names each in its report with the reason. When the test runner runs inside another program's sandbox with `RUN_ALL_TEST_SUITES_INSIDE_SIGNAL_SANDBOX` set, it has no outside to put them in, so these nc-test-suites run inside that sandbox like every other nc-test-suite. At the pinned commit the dict names eight nc-test-suites:

- Five cannot do their job because bwrap cannot start inside bwrap, in any bubblewrap sandbox. `nn-systems/cold-read/tests/cold-read-agy-cell-real-sandbox-test.py` and `nn-systems/general-tools/tests/agy-print-prompt-run-in-empty-home-sandbox-real-sandbox-test.py` start the real bwrap of the program each tests; `scripts/run-all-test-suites-test-sandbox-escape-test.py` builds nc-test-sandboxes itself; `scripts/run-all-test-suites-cleanup-after-killed-runs-real-process-test.py` and `scripts/run-all-test-suites-overlapping-runs-real-process-test.py` start a second test runner and need it to run its own nc-test-suites in bwrap.
- `scripts/mac-request-from-ned-box-forced-command-test.py` runs the real `ssh`, which refuses its root-owned configuration files because inside a bubblewrap sandbox's user namespace they show as owned by nobody. **Observed** (observations 4 and 5): inside `bwrap --ro-bind / / --dev /dev --proc /proc`, `stat` shows `/etc/ssh/ssh_config` as owned by `nobody` (outside, `root`), and `ssh -G localhost` prints `Bad owner or permissions on /etc/ssh/ssh_config.d/20-systemd-ssh-proxy.conf` and exits 255; outside, it exits 0.
- `scripts/recover-crashed-seats-started-tmux-server-lands-in-user-systemd-manager-cgroup-without-xdg-runtime-dir-real-process-test.py` starts a tmux server in a scope of the user's systemd, whose D-Bus session bus, under `/run/user/<uid>`, the nc-test-sandbox hides: its `/run` is an empty tmpfs holding only an empty tmpfs at `/run/user/<uid>` (`scripts/run-all-test-suites.py:964-968`). An outer sandbox that shows the machine's `/run` does not hide the bus.
- `nn-systems/general-tools/tests/agent-seat-worktree-create-with-owner-file-claude-code-worktree-create-hook-real-claude-code-test.py` runs the real `claude`, which needs the real home directory it is logged in from; the nc-test-sandbox's home directory is empty.

**Code**: inside another program's sandbox, some of these nc-test-suites print SKIP instead of failing. `scripts/run-all-test-suites-test-sandbox-escape-test.py:390-393` skips every case when `signal_sandbox()` returns an empty prefix, as it does with the variable set; `scripts/run-all-test-suites-overlapping-runs-real-process-test.py:113` and `scripts/recover-crashed-seats-started-tmux-server-lands-in-user-systemd-manager-cgroup-without-xdg-runtime-dir-real-process-test.py:41` skip every case when the variable is set. `scripts/run-all-test-suites-cleanup-after-killed-runs-real-process-test.py:491-493` skips its cases that kill a real test runner when bwrap cannot start, and still runs its other cases, those from line 279 to line 489, which have not been run inside another sandbox. The two agy nc-test-suites that start a real bwrap, the ssh nc-test-suite and the `claude` nc-test-suite have no such skip, so a nested test runner that runs any of them is expected to report it failed and exit 1. No flag of the test runner leaves out exactly these nc-test-suites in a nested test run. A caller that wants a nested test run without them names the nc-test-suites it wants with `--only-suites-named`; `--leave-out-suites-that-run-the-real-claude-cli` leaves out the `claude` nc-test-suite (docstring, `scripts/run-all-test-suites.py:86-90`); and `--only-suites-whose-recorded-inputs-changed-since` runs only the nc-test-suites whose recorded inputs changed, these among them when they did. None of these nc-test-suites was run inside another sandbox for this page.

**Code**: a test run given `--only-suites-whose-recorded-inputs-changed-since` without `--only-suites-named`, where the test runner starts the nc-test-sandboxes itself, runs a selected one of these nc-test-suites only when the change edits a file that nc-test-suite reads, and leaves out each other one it selected, printing the command that runs it by hand (docstring, `scripts/run-all-test-suites.py:784-799`; code, `scripts/run-all-test-suites.py:5100-5104`). Inside another program's sandbox that rule does not apply, and such a test run selects these nc-test-suites like any other.

The list above is the dict at the pinned commit; read the dict in the checkout under test for the current nc-test-suites and reasons.

## Programs on main that start a sandbox

The programs below were found at the pinned commit by `git grep` for `bwrap` in files other than nc-test-suites and documents, by the callers of `signal_sandbox()`, and by the callers of `codex_credential_denying_permission_profile_arguments()`, the one builder of the Codex launchers' permission profiles; `scripts/merge-lane-code-review-codex-cell-run-on-pull-request-head.py` is listed because it runs one of them. The nc-test-suites that start bwrap are in the section above. A program that starts a sandbox some other way, or that main took after the pinned commit, would not have been found.

### The test runner, and the programs that use its nc-test-sandbox

- **Paths**: `scripts/run-all-test-suites.py` builds the nc-test-sandbox. `scripts/run-suite-in-signal-sandbox.py` and `scripts/mutation-testing-changed-lines-quick-or-full-pass-survivors.py` call its `signal_sandbox()` (`scripts/run-suite-in-signal-sandbox.py:541`, `scripts/mutation-testing-changed-lines-quick-or-full-pass-survivors.py:2037`).
- **Where the sandbox settings are**: the bwrap arguments every nc-test-suite shares are `TEST_SANDBOX_BWRAP_ARGUMENTS_SHARED_BY_EVERY_SUITE` (`scripts/run-all-test-suites.py:960-979`); `bwrap_arguments_for_one_suites_test_sandbox()` (`scripts/run-all-test-suites.py:3329`) adds each nc-test-suite's own, among them the checkout under test as a copy-on-write overlay. Three dicts say which sandbox an nc-test-suite gets: `SUITES_RUN_WITHOUT_ANY_SANDBOX`, `SUITES_GIVEN_A_COPY_ON_WRITE_OVERLAY_OF_THE_REPOSITORY_GIT_DIRECTORY` and `SUITES_WHOSE_TEST_SANDBOX_SHARES_THE_MACHINE_NETWORK` (`scripts/run-all-test-suites.py:1006`, `1037` and `1045`). **Documented** (`scripts/run-all-test-suites.py:209-216`): the test runner reads them from the checkout under test. **Code**: `scripts/run-suite-in-signal-sandbox.py` reads all three from the `scripts/run-all-test-suites.py` beside itself (`scripts/run-suite-in-signal-sandbox.py:101-111`), not from the checkout it is given.
- **What the sandbox shows and hides**: the sandbox is the nc-test-suite's nc-test-sandbox. The glossary's entry for that term points to the test runner's docstring under "THE SIGNAL SANDBOX IS ALSO EACH SUITE'S NC-TEST-SANDBOX" (`scripts/run-all-test-suites.py:145-200`), which says what an nc-test-suite sees. **Observed** (observation 8), inside the command prefix `signal_sandbox()` returns, which is the shared arguments plus the variable set to `1`, without each nc-test-suite's additions: process 1 is `bwrap`; `find ~ -maxdepth 3` lists only `~/.gitconfig`, `~/.local/bin/ruff`, `~/.local/lib` and what lies under it to that depth, and the first directories of the path to the one log-store file the nc-test-suites read, a file of labelled replies under `nedsnodes-logs/seats/ned-box-helper/`, as `TEST_SANDBOX_HOME_PATHS_SHOWN_READ_ONLY` (`scripts/run-all-test-suites.py:918-926`) lists them; `/run` holds only `user`, in which the shared arguments mount an empty tmpfs at `/run/user/<uid>` (`scripts/run-all-test-suites.py:964-968`); and `RUN_ALL_TEST_SUITES_INSIDE_SIGNAL_SANDBOX` is 1. A real nc-test-suite's sandbox also shows the checkout under test and the other paths each nc-test-suite's additions bind.
- **Login file**: **Documented** (`scripts/run-all-test-suites.py:153-163`): no agent runs inside, and no login file is there. The home directory is an empty tmpfs into which only the paths above are bound, together with the checkout under test when it lies inside the home directory and an interpreter given with `--python` from inside it; and no environment variable that `TEST_SUITE_CREDENTIAL_ENVIRONMENT_VARIABLE_PATTERNS` (`scripts/run-all-test-suites.py:951-954`) matches reaches an nc-test-suite.
- **Code**: `scripts/run-suite-in-signal-sandbox.py` refuses an nc-test-suite that `SUITES_RUN_WITHOUT_ANY_SANDBOX` names (`scripts/run-suite-in-signal-sandbox.py:528-530`).

### The agy cold-read-cell launcher

- **Path**: `nn-systems/cold-read/cold-read-agy-cell.py`.
- **Where the sandbox settings are**: `credential_sandbox_prefix()` (`nn-systems/cold-read/cold-read-agy-cell.py:238-270`), built from the lists `CREDENTIAL_DIRECTORIES` and `REVIEWER_PROGRAM_LOGIN_FILES` (`nn-systems/cold-read/cold-read-cell-common.py:63-81`).
- **What the sandbox shows and hides** (**Code**): this program calls the function without `writable_paths`, whose default is `None`, and for `None` bwrap binds the whole file system read-write (`--dev-bind / /`). It mounts an empty tmpfs over each credential directory that exists (`~/.config/nedsnodes`, `~/.config/gh`, `~/.ssh`, `~/.steam` and `~/nedsmessenger`), and binds `/dev/null` over Claude's and Codex's login files that exist at launch. It hides no other file: **Documented** (`nn-systems/cold-read/cold-read-agy-cell.py:102-106`), bwrap takes exact paths, not patterns, so on Linux a file named like a credential, such as `*.token` or `.env`, outside those directories is not covered. **Code**: it has no PID namespace of its own, and the network is shared.
- **Login file**: **Code**: agy reads its own login under `~/.gemini/`, which this sandbox leaves readable and writable. **Observed** (observation 9), inside a sandbox started with this prefix at the observations' commit: `~/.claude/.credentials.json` and `~/.codex/auth.json` read as empty, `~/.config/gh` holds no files, `~/.gemini/antigravity-cli/antigravity-oauth-token` is readable, and `~/.gemini` is writable.
- **Code**: with no `bwrap` on PATH the program refuses before agy starts (`nn-systems/cold-read/cold-read-agy-cell.py:291-299`).

### The Gemini task launcher

- **Path**: `scripts/run-gemini-task-from-brief.py`, which runs agy on a brief.
- **Where the sandbox settings are**: the same `credential_sandbox_prefix()`, called with a list of writable paths and its `network` argument, true only when the launcher is given `--network` (`scripts/run-gemini-task-from-brief.py:126-129`).
- **What the sandbox shows and hides** (**Code**): for a list, even an empty one, bwrap binds the whole file system read-only (`--ro-bind / /`), adds a private `/dev`, and binds read-write each path in the list (`nn-systems/cold-read/cold-read-agy-cell.py:255-260`). The launcher's list always holds the report file and, with `--sandbox workspace-write`, the checkout and each `--writable-root`. Without `--network` the launcher adds `--unshare-net` (`nn-systems/cold-read/cold-read-agy-cell.py:261-262`). The credential directories and login files are hidden as in the agy cold-read-cell launcher, and there is no PID namespace of its own.
- **Login file**: **Observed** (observation 9), inside a sandbox started with `credential_sandbox_prefix(writable_paths=[])`, the read-only part of the launcher's prefix without the report file and directories: the agy login file is readable, Claude's and Codex's login files read as empty, and `~/.gemini` is not writable (`touch` there is refused). What agy does when it must refresh its login and cannot write `~/.gemini` has not been observed; GHI [The Gemini task launcher's read-only `~/.gemini` stops agy from saving its refreshed Google login](https://github.com/nedsnodes/nedsnodes/issues/3902) covers it.

### The agy launcher for one prompt, in a home directory that holds only `~/.gemini`

### The Codex launchers

- **Paths**: `scripts/run-codex-task-from-brief.py`; `nn-systems/cold-read/cold-read-codex-cell.py`, the Codex cold-read-cell launcher; `scripts/code-review-codex-cell.py`, which `scripts/merge-lane-code-review-codex-cell-run-on-pull-request-head.py` runs on a pull request; and `scripts/sanity-check-adversarial-prompts.py`, which runs the sanity-check-cells of /sanity-check.

On Linux it denies no file by its name, so a `*.token` or `.env` file outside the credential directories is readable; on Linux with `:workspace` it also makes `/tmp` and `$TMPDIR` read-only. **Documented** (`scripts/code-review-codex-cell.py:162-168`): Codex runs each of the model's commands through a `codex-linux-sandbox` child process, which execs `bwrap`.
- **Login file**: **Documented** (`nn-systems/cold-read/cold-read-codex-cell.py:89-93` and the comment at `nn-systems/cold-read/cold-read-cell-common.py:73`): the codex agent-binary reads its login outside the profile, which governs only the model's commands, so denying `~/.codex/auth.json` to those commands leaves Codex logged in.
- **Observed** (observation 10): `~/.codex/config.toml` on ned-box has no line containing the word "sandbox". **Documented** (`scripts/code-review-codex-cell.py:115-118`): a `sandbox_mode` key there, as the Mac's config has, sets the sandbox Codex gives a run that carries no permission profile. That search does not rule out a permission setting under another key, and a Codex invocation with another `CODEX_HOME` reads another `config.toml`.
