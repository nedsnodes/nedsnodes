# Detect-instruct-correct

The glossary defines detect-instruct-correct (DIC). This page sets out the cases that definition covers, before the agent's act and after it, says which of them are built, and lists the detection techniques and undo techniques the project uses. DIC keeps an agent to a rule without trusting the agent to remember the rule; the [enforcement ladder](nedsnodes-enforcement-ladder.md) names the other ways, such as making the wrong act impossible, and says why a program that detects the act usually serves a rule better than another line of text.

Read this page before you add a hook, a test or a maintenance-job that answers an agent's act, and before you add a rule to standing-agent-instructions. How to word what the program says to the agent is in [How to write a tool-message-to-agent](nedsnodes-how-to-write-a-tool-message-to-agent-such-as-a-hook-refusal-or-script-error.md); this page says what the program and the agent do, not how the message is worded. Below, "the act" means what that page means by it: what the agent did, or tried to do, that the program answers, such as a tool call, a reply, a commit, or the agent's attempt to end its turn.

The work is split as code-prompt-code splits any work. Code detects what it can, at the act or soon after it. An agent, such as a pull request reviewer, reviews prose, code and logs for the faults that need judgment. Where a fault can be fixed mechanically, code should fix it, though no program on main yet undoes an agent's act on its own; an agent fixes the rest, once a program or a reviewer has told it what is wrong, why, and what to do instead. A test or review too slow or too costly to run at the act runs later, at a pull request or in a maintenance-job. What neither code nor an agent can decide goes to the user.

Each case below is marked **built**, **built in part** or **not built**; a built case names a file on main that does it.

## What the program can know

A detection is judged by what it shows about the harm the rule guards against, not only about the act. It is one of two kinds.

- **A certain detection** shows that the act surely breaks the rule, or surely will. Examples: a guarded-file whose content hash has changed with no approval recorded for the new version, against the rule that a guarded-file's new version is approved or put to the user; a `gh issue create` for this repository that the agent runs itself instead of through `scripts/ghi-issue-write.py`, found by parsing the shell command before it runs.
- **A guess** shows only that the act may break the rule. It is usually a cheap pattern, and it is often wrong. Example: a Write that replaces a whole GHI-MD surely replaces it, but whether the replacement throws away changes merged since the agent's copy was made is a guess. A guess is worth the context its message costs only if, over many firings, it leaves the work better than silence would.

What the program reads can be certain while the harm stays a guess. A file's path, its hash, or a diff against main can be read exactly, as can a parsed command. Whether that breaks the rule is certain only when the rule forbids exactly what was read: a pattern in prose is a guess when it stands in for the harm, such as words that suggest a file is missing, and certain when the rule forbids the pattern itself, such as a pull request cited in Markdown by a bare `#` and a number. A detection also sees only the routes it reads: `.claude/guard-hooks/ghi-issue-write-hand-typed-gh-command-refusal.py` does not recognise a `gh` run behind `ssh`, `sh -c`, `eval` or in a heredoc body, and no program reads inside a script file the agent runs. Where a detection is blind to a route, a second detection, later or by another means, can cover that route, as the guarded-file hook after every tool call covers the shell writes that the instruction-file guard, before an edit, does not see.

Two more things decide what the program does: the act's blast radius, and whether an undo exists and who can run it. An act's blast radius is high when the act would lose or damage work, stop work beyond the task, or go unnoticed until it does one of those, in the sense CLAUDE.md's rule for proposing a guard gives those words: harm that can be noticed and undone, or work that can simply be redone, is not lost or damaged. Otherwise it is low. Blast radius picks the row of the table under "Before the act"; who can run the undo picks the row of the table under "After the act". When no undo exists, as for a reply the user has already read, the only correction is new work on top, so an act whose harm neither an undo nor new work can repair is one to refuse before the act.

A refusal on a guess, a revert, or a second detection behind a first is a guard, and is added only as CLAUDE.md's rule for proposing a guard says. A hint or a warning that lets the act go ahead is not a guard: it is added when it pays for the context it costs, as [How often a hint fires](#how-often-a-hint-fires) says.

## Before the act

These programs run before the act, as Claude Code's PreToolUse hooks do, so they can refuse it.

| Detection | Blast radius | What the program does | What the agent does | Status and example |
|---|---|---|---|---|
| Certain | Any | Refuses the act, saying what is wrong, why, and what to do instead, such as the program that does the step right: a hard-block, or a user-block when only the user may allow the act | Does what the refusal says instead, such as running the program it names; for a user-block, asks the user and goes ahead only on his approval. When the program it names cannot do the work, or the user declines, the agent stops and tells the user, or drops the work | Built: `.claude/guard-hooks/ghi-issue-write-hand-typed-gh-command-refusal.py` refuses a `gh issue create` the agent runs itself and sends it to `scripts/ghi-issue-write.py` |
| Guess | High | Refuses the act, but lets the agent go ahead once the agent says it checked: a soft-block, cleared by the act the refusal names, such as writing a reason into a marker file | Checks; when the act is right, clears the refusal as it says and retries once, and tells the user if it is refused again; when the act is wrong, does it the right way or not at all; when checking cannot decide, does not clear the refusal and tells the user | Built: `.claude/guard-hooks/ghi-md-whole-file-replacement-soft-block.py` refuses a Write or a shell command that replaces a whole GHI-MD until the agent writes its reason into the marker file the refusal names |
| Guess | Low | Lets the act go ahead, and adds a hint ("this would be better"), a warning ("this might be a problem"), or both, paced by how often the guess is right, as [How often a hint fires](#how-often-a-hint-fires) says | Weighs the hint or warning; when it applies, corrects the work with new work on top, and acts on it at the next act of the same kind; otherwise carries on | Built: `nn-systems/general-tools/claude-code-bash-git-push-of-markdown-change-citation-checks-reminder-hook.py` reminds the agent, at a push that changes a Markdown file, to run the two citation programs, and never blocks the push |

A hint that lets the act go ahead cannot be counted on to change that act, because the act runs whether or not the agent has read it in time; the push reminder's message says "this push goes ahead now" and sends any fix to new work on top. A hint meant to affect an act before it happens arrives earlier, such as when the user's prompt arrives, or is a soft-block instead.

Every agent-action-block teaches: its tool-message-to-agent says what was stopped, why, and what to do instead, so that the agent can learn the wanted behavior and not only how to get past one refusal. The glossary's hard-block, soft-block, user-block and reminder-block say what, if anything, clears each kind. A guard such as `.claude/guard-hooks/instruction-file-guard.py` hands out more than one kind: a user-block for a change that needs the user's approval, and a soft-block for a change that needs none.

## After the act

These programs run after the act: just after a tool runs, at the end of the agent's turn, when the user's next prompt arrives, before a push or a merge of commits already made, or on a schedule. The act has happened, so they cannot stop it; they can have it corrected, or find that it was right. A program at the end of a turn, at a push or at a merge runs after the act it checks, such as an edit or a commit, and before the next act, ending the turn, the push or the merge; it may refuse that next act, and for that next act the table under "Before the act" applies.

What the agent does depends also on whether others already have the work; the four cases under "What a message says" in [How to write a tool-message-to-agent](nedsnodes-how-to-write-a-tool-message-to-agent-such-as-a-hook-refusal-or-script-error.md) say what the message tells the agent in each, and when others have the work, the correction is new work on top. Below, "does the act again the right way" means: the right way when the act had a right way, and not at all when the act itself was what the rule forbids.

| Detection | Who can put it right | What the program does | What the agent does | Status and example |
|---|---|---|---|---|
| Certain | The program, safely | Writes a copy of what the act replaced, then reverts the act, and tells the agent what it reverted, why, where the copy is, and how to do the act correctly; reports a revert that fails partway | Does the act again the right way | Not built: no program on main undoes an agent's act on its own (the enforcement ladder's rung 5) |
| Certain | The agent | Tells the agent what it detected, and how to revert the act or fix it in place | Reverts the act and does it again the right way, or fixes it in place | Built: `scripts/obsolete-file-edit-warning-hook.py`, after an edit of a file that main has since deleted, or moved and rewritten, tells the agent to drop the edit with `git checkout -- <path>` and make the change where main has the file now |
| Certain | Only the user, by deciding | Keeps every version it sees, and tells the agent to show the user the change and run the program's approve or restore command | Asks the user, with a recommendation, and does what he decides; leaves the change in place until he answers | Built: `.claude/guard-hooks/guarded-file-unapproved-change-afterward-backup-and-ask-hook.py`, after every tool call, finds a guarded-file whose new version has no recorded approval; the agent runs `--approve` when the user approves, or, when he does not, `--restore` or the `rm` the hook offers for a new file |
| Guess | The agent | Warns the agent that the act may have broken the rule and says how to check, or keeps the agent's turn open once to do so, a reminder-block | Checks; when it finds the rule broken, reverts or fixes the act, or for a reply, corrects it in its next message; when it finds the rule kept, carries on; when checking cannot decide, leaves the act in place and tells the user, or the agent that dispatched it, that it could not decide | Built: `scripts/absence-claim-locator-reminder-hook.py`, at the end of a turn whose reply says a file is missing, keeps the turn open once and sends the agent to run `scripts/locate-file-copies-across-machines.py` |
| Certain or guess | Too slow or too costly to check at the act | Checks later, at a pull request or in a maintenance-job, and reports each fault where an agent or the user will act on it; a later run that could not finish says so, and is never read as a pass | Fixes each fault the report shows, as new work on top, or shows that the report was wrong | Built: `scripts/scheduled-full-mutation-pass-of-merged-pull-requests-and-survivor-tasks-open.py` runs nn-mutation-testing each night on the pull requests merged into main since its last run, and opens a task for each line with surviving mutants |

When a certain detection finds an act that only the user may decide on, his row wins over the program's: the program does not revert it. A guess about such an act is checked by the agent first, and goes to the user only when checking finds the rule broken or cannot decide.

## When the guess is wrong

A guess is often wrong, and a certain detection can be wrong when its program has a defect. Four things limit the cost.

- **The logs can show how often each detection is right.** That rate, its precision, sets how often the rule's hint fires, or shows that its detection should be tightened. Built in part: `scripts/absence-claim-locator-reminder-hook.py` logs one line for each reply that triggers it, with the outcome, such as whether the locator had already run in that turn, and `nn-systems/general-tools/claude-code-registered-hook-rule-ids-in-both-machines-transcripts-weekly-count-and-never-seen-rules-report.py` counts, each week, each registered hook's rule ID in both machines' transcripts and lists the rules not seen since their IDs were added. Those count firings; a record of whether each firing was right, from which a detection's precision could be read, is not built.
- **A wrong soft-block is cleared by the agent after checking.** Built, as the soft-block row above says. A hard-block or a user-block cannot be cleared by the agent: when the agent believes one is wrong, it tells the user what was refused and why it believes the refusal wrong, and the defect in the program is fixed.
- **A wrong revert is undone from the kept copy.** A program that reverts an act writes a copy of what it replaced first and says where the copy is, so that an agent whose check finds the revert wrong puts the copy back. Not built, since no program reverts on its own; the guarded-file hook's versions, kept in the log-store or, for a version a commit holds, in git, are the existing model for such a copy.
- **A confirmed fault makes that rule's hints fire more often for a while**, as [How often a hint fires](#how-often-a-hint-fires) says. Not built.

## How often a hint fires

A hint costs context each time it fires, and hints that are seldom right teach the agent to skip hints, so how often a hint fires depends on how often it is right and on what the mistake it guards against would cost. A hint that guards against a costly mistake may fire each time its detection matches. A hint that is right only about 1 time in 10 fires at most once per stretch of the agent's work, such as once the agent-session's transcript has grown by 50,000 tokens since that rule's last hint. The count includes the tokens that Claude Code's compaction later summarizes away, because compaction makes the agent remember less, not more. A mistake just made is likelier to be made again soon, so after a fault is confirmed, the rule's hint fires more often for a while, then returns to its usual spacing. A fault is confirmed when a certain detection after the act finds the rule broken.

Built today, for warnings after the act rather than hints: a hook that sends the agent back once per agent-session, as `scripts/absence-claim-locator-reminder-hook.py` does; and a hook that sends its full instructions once per agent-session and again after each compaction, and a short form after that, as `scripts/bare-number-citation-in-markdown-and-agent-reply-warning-hook.py` does in the note it adds about the agent's previous reply when the user's next prompt arrives.

Not built: spacing counted in tokens, and the raised rate after a confirmed fault. The trigger-first design, `docs/issues/30-trigger-first-instruction-delivery.system.design.md`, of GHI [Trigger-first instruction delivery (moved from nedlern#1972): delivery timing as a property of every instruction — step-2 CLAUDE.md design input + carried design and scan](https://github.com/nedsnodes/nedsnodes/issues/30), holds the spacing: a setting `min_spacing_tokens`, default 50000 with a per-rule override, and a count kept per agent-session and rule, measured in the growth of the transcript's bytes, about 200 KB for 50,000 tokens, so that compaction does not reset it. Spacing tied to a hint's precision, and the raised rate after a confirmed fault, are not in that design yet.

Open questions, for whoever builds the spacing to bring to the user before building it:

- After a fault is confirmed, how much more often does the hint fire, and for how long?
- When a warning asks the agent to check and the agent finds the rule broken, does that also count as a confirmed fault? Code may read the agent's finding from its next tool calls, such as whether it ran the locator after the absence-claim reminder, rather than ask the agent to report it.
- Does 50,000 tokens stay the default? The trigger-first design's own note says roughly 50,000 to 100,000 tokens.
- How is a hint's precision measured, and how does spacing follow from it between the two cases above? That needs a record of each hint and whether it was right.
- Is a warning spaced the same way as a hint when its detection is a guess, while a correction after a certain detection fires each time?

## Detection techniques the project uses

Each technique is listed with programs on main that use it. Each line names the case the program shows; the program's docstring says what it does not cover.

- **Parsing a shell command before it runs.** `nn-systems/general-tools/shell-command-tree-sitter-bash-reader-common.py` is the shared parser; `.claude/guard-hooks/ghi-issue-write-hand-typed-gh-command-refusal.py` uses it to find a `gh issue create` the agent runs itself.
- **A path checked before an edit tool runs.** `.claude/guard-hooks/instruction-file-guard.py` refuses an Edit, Write or NotebookEdit of a guarded-file until the `.walk-approved` marker file says the change may go ahead. It does not see a shell command's writes.
- **A file's stat data, then its hash, compared after every tool call.** `.claude/guard-hooks/guarded-file-unapproved-change-afterward-backup-and-ask-hook.py` hashes a file whose stat data changed, so it sees a guarded-file that any tool, the shell included, left changed when the tool call ended.
- **A pattern in text the agent just wrote to a file.** `scripts/style-guide-word-checker-markdown-edit-hook-hack.py`, after an Edit or Write of a Markdown file, reports the words the style guide lists in the lines the edit wrote.
- **A pattern in the agent's reply, at the end of its turn.** `scripts/absence-claim-locator-reminder-hook.py`, a Stop hook, reads the turn's last reply from the transcript.
- **A pattern in the agent's previous reply, when the user's next prompt arrives.** `scripts/ned-box-path-in-agent-reply-unclickable-on-mac-warning-hook.py`, a UserPromptSubmit hook on ned-box, notes each path under `/home/nedlern/` that the reply wrote in a form the user cannot open on the Mac.
- **A diff against main.** `scripts/obsolete-file-edit-warning-hook.py`, after each Edit or Write, finds that the edited file is one the checkout's copy of origin/main has changed; `scripts/branch-reverts-a-file-to-an-older-main-version-check.py`, which the pre-push git hook runs, finds a branch that sets a whole file back to a version main has replaced.
- **What a pull request carries, before it merges.** `scripts/merge-gate.sh` refuses a merge whose description has no `#root_cause`, `#root_cause_not_fixed` or `#no_defect_fixed` line; `scripts/pull-request-head-test-run.py` runs the affected nn-test-suites at the pull request's nn-head-commit.
- **A maintenance-job.** `scripts/scheduled-full-test-run-of-main.py` runs every nn-test-suite on main once a day on each machine; `scripts/scheduled-full-mutation-pass-of-merged-pull-requests-and-survivor-tasks-open.py` runs nn-mutation-testing each night on the pull requests merged into main since its last run.
- **A count from logs.** `nn-systems/general-tools/claude-code-registered-hook-rule-ids-in-both-machines-transcripts-weekly-count-and-never-seen-rules-report.py` counts each rule ID in both machines' transcripts each week and lists the rules never seen.
- **A model's judgment.** `scripts/merge-lane-pull-request-worktrees-reviewer-brief-codex-review-and-head-tests-run-without-merge.py` runs the merge-lane steps that review a pull request, and `nn-systems/cold-read/cold-read-grid.py` runs the cold-read-cells; both have models read prose and code for faults no pattern finds.

## Undo techniques the project uses

In the first four techniques the agent puts back an earlier state, each with a program on main that keeps or finds the copy; no program on main runs an undo on its own. The fifth is for when no undo exists. Each program's docstring says what it does when the copy is missing or the undo fails.

- **Restore from the program's kept versions.** `.claude/guard-hooks/guarded-file-unapproved-change-afterward-backup-and-ask-hook.py` keeps each version of a guarded-file it sees, in the log-store or, for a version a commit holds, in git; `--restore <path> <hash>`, given the hash of the version the user declined, puts back the newest approved version, and for a new file that no approved version or main holds, the hook offers the `rm` that deletes it.
- **Revert with git, told the command.** `scripts/obsolete-file-edit-warning-hook.py`, when main has deleted the edited file, or moved and rewritten it, tells the agent to drop the edit with `git checkout -- <path>`, which drops every uncommitted change to that file.
- **Restore uncommitted work from a work-snapshot.** `scripts/uncommitted-work-snapshot-hook.py` keeps a work-snapshot of a worktree's uncommitted changes after Edit, Write, NotebookEdit and Bash calls; `python3 nn-systems/handoff/uncommitted-work-snapshots.py restore <ref> --keep <file> ...` commits the kept files' changes on a new branch.
- **Find a deleted file's copies, to restore one.** `scripts/find-deleted-path-across-backups.py` searches the Mac's local snapshots, git and its reflog, the log-store, the transcripts, Timeshift on ned-box and Time Machine on the Mac for a path no longer on disk, and copies each version it can read into a folder it names; putting one back at the original path is a separate step the agent takes.
- **Correct with new work on top**, when no undo exists or others already have the work, such as a reply the user has read or a commit pushed for review: the agent makes a new commit, or corrects its reply in its next message, as [How to write a tool-message-to-agent](nedsnodes-how-to-write-a-tool-message-to-agent-such-as-a-hook-refusal-or-script-error.md) says.

Whether Claude Code's rewind could let a program undo an agent's file edits is GHI [Find whether Claude Code's rewind can correct an agent's wrong act, triggered by a program](https://github.com/nedsnodes/nedsnodes/issues/1758).
