# Merge queue: the dead-batch check is made without holding merge-batch.lock, so a healthy merge batch can be stopped and a dead one missed, in `scripts/merge-lane-merge-queue-approved-lines-merge-in-order-until-none-left.py`

## Reproduction

The reproduction program `nedlern@ned-box:/home/nedlern/nedsnodes-logs/seats/merge-lane-1/merge-batch-start-findings-reproduce-2026-11-26/merge-batch-start-findings-reproduce.py` takes the path of a checkout as its one argument and runs that checkout's merge queue program, `scripts/merge-lane-merge-queue-approved-lines-merge-in-order-until-none-left.py`, in a fresh temporary directory, with a fake `gh`, a fake merge program and a fake follow-up program, so it reads and writes nothing on GitHub or under `/home/nedlern/nedsnodes-logs/seats/merge-lane-2/`. It injects the timing of each case. Its outputs on origin/main `157731f5a914` (PR [Merge queue checks the stop and in-progress files at every entry, passes its outputs directory both ways, and keeps each outcome where it happens](https://github.com/nedsnodes/nedsnodes/pull/4955) merged) and on origin/main `5b3c85e2b80e` (before that pull request) are `reproduce-output-origin-main-157731f5a914.txt` and `reproduce-output-origin-main-5b3c85e2b80e.txt` beside it. Each case is named by the id of the Codex review cell's finding it tests, d295caf41226, from merge-lane-1's review 6068181614 of that pull request. Both cases below print `REPRODUCED: True` on both commits.

- Case "d295caf41226": `merge-batch-start` calls `lock_held()`, which takes and releases `merge-batch.lock`. The reproduction program then starts a healthy merge batch, `merge-batch-run-in-queue-order`, which takes the lock and writes `merge-batch-merge-in-progress.txt` for its merge of pull request 1, before `start()` checks that file. `start()` prints `DIED MID-MERGE`, writes the stop file and removes the in-progress file while the healthy batch still holds the lock. The healthy batch's merge of pull request 1 ends with exit 0, its next check finds the stop file, and it ends with pull request 2 still waiting and a stopped notice saying main is untested.
- Case "d295caf41226, reverse": a running batch's queue-growth loop releases the lock with `fcntl.flock(lock, fcntl.LOCK_UN)` and reads the queue file's size again. In that gap the reproduction program writes what another batch leaves when it takes the lock and dies during a merge: its in-progress file for pull request 9, and a new queue line for pull request 2. The loop re-takes the lock, merges pull request 2 onto the main that pull request 9's merge left unchecked, then removes pull request 9's in-progress file and ends with `DONE: nothing left to merge`; no stop file is written.

## What is wrong

`died_mid_merge_stopped()`'s docstring says it is "Called only when no other merge batch holds merge-batch.lock, since a running batch holds the file through each of its merges", a precondition that only English states. Two callers break it: `start()` calls it after `lock_held()` has released the lock, so another process can take the lock in between; and `run_in_queue_order()` calls it only when it first takes the lock, not when its queue-growth loop re-takes the lock. The first wrongly stops a healthy merge batch, which merge-lane-2 then handles and resumes by hand. The second merges onto a main whose last merge and after-merge test run nobody checked, and deletes the only file that recorded the dead merge. `resume()` has the same shape, read from the code and not reproduced: it calls `lock_held()`, then removes the stop file and the in-progress file without holding the lock, so it could remove the in-progress file of a batch that took the lock in between.

## How likely, and what to do

Both reproduced cases need unusual timing: the first needs `start()` held between two adjacent statements for as long as a new batch takes to make two `gh` calls, and the second needs another batch to take the lock, start a merge and die within the loop's gap of two system calls. No record shows either happening, and the merge queue program is not in live use yet: on 2026-11-26 ned-box had no directory `/home/nedlern/nedsnodes-logs/seats/merge-lane-2/merge-queue-merge-batches`, the program's default merge batches directory, and no crontab line runs it; `ssh nedlern@ned-box 'ls -d /home/nedlern/nedsnodes-logs/seats/merge-lane-2/merge-queue-merge-batches; crontab -l | grep merge-lane-merge-queue'` checks this again.

The agent-seat overall-cleanup, which wrote this code in PR [Merge queue program merges approved lines in order until none is left](https://github.com/nedsnodes/nedsnodes/pull/4893), fixes the root cause: make the precondition structural, so the dead-batch check and the removal of the in-progress file happen only while holding `merge-batch.lock`. One way is a single helper that takes the lock and then runs the check, used at every take and re-take in `run_in_queue_order()`, with `start()` and `resume()` either holding the lock through their checks and removals or leaving them to the batch that holds it; `start()` must release the lock before the batch it starts tries to take it, or that batch exits `ALREADY RUNNING`. Turn the reproduction program's two cases into cases of `scripts/merge-lane-merge-queue-approved-lines-merge-in-order-until-none-left-test.py` that assert the defect no longer happens, and add one for `resume()`.
