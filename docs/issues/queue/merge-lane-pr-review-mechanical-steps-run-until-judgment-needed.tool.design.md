## The problem

In this design a review lane is merge-lane-1 or merge-lane-3: an agent-seat that manages the review of the pull requests the watcher, `scripts/merge-lane-open-prs-watch-and-reviewer-assign.py`, assigns it, and grades their findings, but does not merge; merge-lane-2 merges. "The lane" below always means the review lane that runs the program. A review lane follows its seat-brief by hand for each pull request: it lists its assignments, runs `scripts/pull-request-review-plan.py`, writes the brief specifications file (a JSON list of one entry, which `scripts/merge-lane-pull-request-reviewer-brief-compose-with-facts.py` turns into the reviewer's brief), takes the commissioned time, starts the review run, grades, posts, writes the merge queue line and sends messages. The commissioned time is the UTC time the lane takes just before it starts the review run; merge-lane-1's seat-brief calls it the time the review was commissioned, and the merge queue line carries it as the `reviewed-since` time that `scripts/merge-gate.sh` checks, which must be no later than the approving review. Only the four kinds of step listed under "Steps that need judgment" need judgment. Agents doing the other steps by hand have made these mistakes:

- **PR 4925.** The merge gate refused the merge because the queue line's commissioned time, 03:42:24Z, was later than the approving review's submittedAt, 03:42:19Z. It was a review at no-reviewer-tier, the tier `scripts/pull-request-review-plan.py` gives a pull request that changes only prose, which runs no review run, and the agent took the time after it posted (`nedlern@ned-box:/home/nedlern/nedsnodes-logs/seats/merge-lane-2/merge-queue-2026-11-21.txt`, lines 1616 and 1630).
- **PR 4917.** merge-lane-1 approved in review 6070885309 at 08:43:17Z, then posted a correction comment at 08:43:34Z. `scripts/merge-gate.sh` counts a comment posted after the queue line's `reviewed-since` time as new activity, so the merge needed a further `ned-review-merge` review, posted at 09:55:45Z (GitHub's review and comment lists for PR 4917).
- **Pull requests handed to a lane by hand.** The watcher assigns pull requests to the lanes by load, so a replacement pull request can go to a different lane than the one that reviewed the pull request it replaces. The assignment file gives PR 5128 to merge-lane-1 (`nedlern@ned-box:/home/nedlern/nedsnodes-logs/seats/merge-lane-2/merge-lane-pr-review-assignments.txt`, line 597), and merge-lane-1's listing shows it as WAITS-FOR-VERDICT. ## What the program is

The program is `scripts/merge-lane-pr-review-mechanical-steps-run-until-judgment-needed.py --agent-seat <merge-lane-1|merge-lane-3>`. It runs on ned-box, where every path below is a local path. Each call does every step that needs no judgment, then stops. The first line it prints is one output state from the table below, alone. Under it come the files and text that the next step needs; a SEND block, where there is one; and then every open hold of the lane with the time it was opened. The lane, or a forked subagent of the lane's agent-session, acts on that state and calls the program again. The program never decides what code alone cannot decide. The lane never does a step that the program does.

**Calls.** `--agent-seat` is required on every call; a call with a missing or wrong argument prints `FAILED` with the usage, so the first line is always an output state.
- With nothing else, a call first resumes the lane's round that has waited longest for the program, such as one whose review run has ended; then lists, without acting on them, the rounds that wait on the lane, with the state each waits in; then prints RUN-RUNNING when a review run holds the lane's run lock; and only then picks a new pull request.
- `--pull-request <n>` acts on that pull request only, when the listing gives it to this lane; otherwise it prints `FAILED` saying whose it is.
- `--written <n>` tells the program that the lane has finished the file its round waits for: the brief specifications file at WRITE-HAZARDS, or the review file at GRADE or ROUND-LIMIT. The program cannot tell a finished file from its own skeleton by looking, so it waits for this call.
- `--answer <n> RERUN` and `--answer <n> LEAVE-UNTIL-NEW-HEAD` answer RUN-FAILED for the pull request's current head; the second prints NONE-WAITING or the next pull request's state.
- `--hold-cleared <n> "<hold>"` clears one hold (see "Holds").
- `--wait-for-run <n>` blocks until the pull request's review run exits, then does what `--pull-request <n>` would.

**Two locks.** Every call holds the lane's call lock, `/home/nedlern/nedsnodes-logs/seats/<agent-seat name>/merge-lane-pr-review-mechanical-steps-call.lock`, with `flock` while it reads and writes the state file, the queue file and GitHub, because the lane, a forked subagent and a background `--wait-for-run` can call at the same time. A review run holds the lane's run lock, `/home/nedlern/nedsnodes-logs/seats/<agent-seat name>/review-run.lock`, for as long as it lasts: the detached process that runs it holds the lock with `flock`, so the lock is released when that process exits, however it exits. A call that would start a review run while the run lock is held prints RUN-RUNNING and starts nothing.

**What the program stores.** One JSON file per pull request, `/home/nedlern/nedsnodes-logs/seats/<agent-seat name>/merge-lane-pr-review-mechanical-steps-per-round-state/pr<number>.json`, holding, for each round, keyed by head: the output state last printed and when; the commissioned time; the review run's log path and exit status, and the reruns of each step; the posted review id; and each open hold with the time it was opened. It holds the posted review id and the head only to know which round a later call continues; GitHub decides. On every call the program reads afresh: the round number, the tier, the earlier reviewed head and the reviews from `scripts/pull-request-review-plan.py`; the assignment from the watcher's listing; and whether a review is already posted on the head from GitHub's review list. The per-round `review-commissioned-*.txt` files stop being written, because the state file holds the commissioned time.

## Output states and steps

| Output state (first line) | What the program did before printing it, and what it reuses | The lane's next step |
|---|---|---|
| `NONE-WAITING` | Ran `scripts/merge-lane-open-prs-watch-and-reviewer-assign.py --merge-lane-pr-review-assignments-list-for <lane>`. No pull request is WAITS-FOR-VERDICT, or each one that is waits on the lane or has a PLAN-REFUSED or LEAVE-UNTIL-NEW-HEAD answer on its current head. | Nothing. Call again when merge-lane-2 forwards an event. |
| `PLAN-REFUSED PR <n>` | Picked the pull request: one labeled `high-priority` on GitHub first, then the one waiting longest. Fetched origin and the pull request's head, `refs/pull/<n>/head`, because the plan never fetches. Ran `scripts/pull-request-review-plan.py --pull-request <n>`, which exited 1, its refusal, and printed what it said. An exit 2, a defect in the plan, prints `FAILED`; an exit 3, a plan printed with a message that has no cold-read-fast-read command, is a usable plan, and the program goes on with it, listing those messages for GRADE. | Act on what the plan said. The pull request is tried again when its head changes, or when the lane calls with `--pull-request <n>`. |
| `WRITE-HAZARDS PR <n> <brief specifications file>` | Wrote the brief specifications file with every field it can fill: `tag`, `<n>` on round 1 and `<n>r<round>` after; number and title from `gh`; author from the first commit's author name, as the watcher reads it; `head` and `main` from the fetched refs; `tests` from the plan's `test_files_to_run`; `claude_reviewer` from the tier the plan gives this round; and `overlaps`, the other open pull requests that change any of the same files, from `gh`. When the plan lists a changed Bash guard, it ran `nn-systems/general-tools/bash-guards-verdict-changes-between-git-refs-on-recorded-commands-check.py` between main and the head. On its exit 1, a verdict changed or an added guard refuses a recorded command, it put the paths of both of its full lists into `hazards`, with the seat-brief's instruction that the reviewer quote each listed command and say whether its new verdict is right; on exit 0 it added nothing; an exit 2, the replay itself failed, stops here as `FAILED`. On a fix-round it also filled `reviewed_before` and `previous_reviews` from the plan, `new_commits` from `git log` of the plan's delta range, and `answer` from those commits' messages, quoted unchanged; when the plan reviews the round whole, it leaves these four out, as on round 1. | Write the rest of `hazards`, add tests the plan did not find, then call `--written <n>`. |
| `RUN-RUNNING PR <n> <log>` | Took the run lock. Inside it, took the commissioned time with `date -u +%Y-%m-%dT%H:%M:%SZ` and recorded it. Then started, detached, a job that runs `scripts/merge-lane-pull-request-worktrees-reviewer-brief-codex-review-and-head-tests-run-without-merge.py` with `--review-tools-worktree-at-main /home/nedlern/.cache/merge-lane-review-worktrees/tools-<lane>`, and `--head-commit-reviewed-before` when the plan reviews the round by its new commits alone; and, once that has built the pull request's merged worktree, the commands merge-lane-2's seat-brief ties to the kind of file changed: each cold-read-fast-read command the plan prints, once per message, and `scripts/md-drift-lint.py` on the changed `.md` files that still exist at the head, run in the merged worktree. | Run `--wait-for-run <n>` as a background task; it prints the next output state when the job exits. |
| `RUN-FAILED PR <n> <log>` | The review run refused before any step ran (exit 2), or a step failed for a reason other than a finding. A step that ended with a finding, a failing test suite in the head tests or an exit 1 of `md-drift-lint.py`, is not a failure: it goes to GRADE as an input. The program printed the log's last lines and the failed step's own command, which the review run prints. | Answer `--answer <n> RERUN` when the log shows a transient fault, such as a network error; the program then runs only the failed step's own command, because running the review run again would post a second Claude review. Otherwise report the failure to merge-lane-2 with SendMessage, quoting the log lines, and answer `--answer <n> LEAVE-UNTIL-NEW-HEAD`. |
| `GRADE PR <n> <inputs directory> <review file to write>` | Collected the round's inputs into one directory, with a list of each input and whether it is there, was not called for by the tier, or failed: the plan, the Claude reviewer's review and note, the Codex report with the finding ids the post program computes from it, the head test result, and the cold-read-fast-read and lint outputs. Wrote a skeleton review file: empty `comments`, an empty `holds` list, and one entry `{"finding": "<id>", "grade": ""}` in `merge_lane_codex_review_finding_grades` for each Codex finding id. At no-reviewer-tier it ran no review run: it built the merged worktree, ran the cold-read-fast-read and lint commands itself, and took the commissioned time just before printing this state. | Fill in the review file, then call `--written <n>`. |
| `REVIEW-REFUSED PR <n>` | Gave the review file the verdict its comments call for, REQUEST_CHANGES when any comment is must-fix-now and APPROVE otherwise, as the post program requires, and passed it to `scripts/merge-lane-pull-request-reviewer-review-post-and-read-back.py --github-account ned-review-merge` with `GIT_AUTHOR_NAME` set to the lane's name. The post program printed "review not posted:" and the reason, which the program printed. When the post program instead says the review may have been posted, or was posted but its read-back failed or differs, the program prints `FAILED` with that message and never posts again on that head. | Fix the review file, then call `--written <n>`. |
| `ROUND-LIMIT PR <n>` | The review file has must-fix-now comments, but merge-lane-2's seat-brief allows no further round: round 3 with more than one must-fix-now finding, or round 4 or later with any. The round counts the merge account's changes-requested reviews as the fix-round author program counts them, which includes those of the pull requests this one replaces; a new head after an approval, such as a merge of main, adds none. Nothing was posted. | Grade every finding left again, at the limit, as merge-lane-2's seat-brief says, then call `--written <n>`. When a must-fix-now finding is still left, the program closes the pull request (CLOSED); otherwise it approves it (QUEUED). |
| `QUEUED PR <n>` + `SEND` block | Posted the approval. Appended the queue line under `flock` on the queue file's lock and read it back: `<n> <head> <commissioned time> <author agent-seat, or not-named> (round <r>, review <id>, merge-lane-<x>[, stacked on <m>, merge after it])`, with a `HOLD-` prefix while a hold is open. `<m>` is the open pull request whose head branch is this one's base, from `gh`. The queue file is the one merge-lane-1's seat-brief names, or another that merge-lane-2 has named. | Send the SEND block (see "Messages"). |
| `CHANGES-REQUESTED PR <n>` + `SEND` block | Posted the review and recorded that the round waits for the author's answer. The SEND block is the fix-round notice, which tells the author to run `scripts/pull-request-fix-round-author-brief-from-blocking-findings-and-one-commit-every-finding-answered-check.py <n>`. | Send the SEND block. |
| `CLOSED PR <n>` + `SEND` block | At the round limit, posted the review, which requests changes because a must-fix-now comment is left, then closed the pull request with `gh pr close` as `ned-review-merge`. The SEND block tells the author why, listing the findings left. When the close fails after the post, it prints `FAILED` saying the review was posted and what `gh pr view` shows of the pull request's state. | Send the SEND block. |
| `FAILED <what>` | A step failed in a way that has no output state of its own. It exits 1 and prints what failed and what it changed. | Report it to merge-lane-2 with SendMessage, quoting the output. |

**What the review file holds.** It has the shape the post program already takes, `verdict`, `body`, `comments` and `merge_lane_codex_review_finding_grades`, plus one key, `"holds"`: a list of `{"hold": "<a few words>", "waits_for": "user" | "author" | "fast-read"}`. The lane writes no verdict: the program sets it from the comments, as REVIEW-REFUSED says. The program removes `holds` before posting, from a copy, and checks each hold has a non-empty `hold` and a listed `waits_for`, printing REVIEW-REFUSED when one does not. When the review has comments, the program also appends to the copy's body the three closing sentences that merge-lane-2's seat-brief gives a review with findings, word for word, which it holds as a constant, so the lane does not type them. The post program already checks every `finding_category` and a grade for every Codex finding, so this program repeats neither check.

## How each case is handled

- **Fix-rounds.** A fix-round push makes the watcher's listing show the pull request as WAITS-FOR-VERDICT again, and the plan gives the earlier reviewed head and whether the round is reviewed by its new commits alone or whole, and at which tier. The next call goes to WRITE-HAZARDS with the fix-round fields filled, or, when the round's tier is no-reviewer-tier, to GRADE. A fix-round that the author ends with no commit, with the round record comment the fix-round author program posts on the same head, starts the next round when the lane calls `--pull-request <n>`, after merge-lane-2 forwards the author's message. The program decides none of the plan's choices itself.
- **Changes requested.** The program posts the review, prints the author notice and keeps the round open until the head changes or a round record names the head. The watcher listing, together with the state file, would replace the per-round task "Review PR <n> fix-round (round 2) when <author> reports it" (open question 3).
- **A head pushed during a round.** The review run reads the head once, from origin, and the post and the queue line name that head. The merge gate merges only the approved head. So a newer head is simply the next round. A head that moves while the lane writes the hazards makes the review run refuse (exit 2) because the brief specifications file names the old head; the program then starts the round again on the new head, printing WRITE-HAZARDS with the lane's `hazards` text kept.
- **Failed runs.** The program never reruns by itself, because only the lane can tell a transient fault from a defect.
- **Holds.** Holds come from the lane's review file, never from the program's own guess. While a hold is open, the queue line starts with a `HOLD-` prefix. The queue reader takes everything up to the first space as the prefix, so the program writes it as one word: `HOLD-` followed by each open hold's words joined by hyphens, with `+` between holds, such as `HOLD-user-approval+fast-read-messages`; it refuses a hold whose words contain `+`. When a hold clears, the lane runs `--hold-cleared <n> "<hold>"`. The program then appends the same line, with a `HOLD-` prefix naming the holds still open, or with none when none is left, and prints QUEUED with a SEND block to merge-lane-2 naming the holds left. A `<hold>` that names no open hold prints `FAILED` listing the open holds. It appends only when, under the queue file's lock, the pull request's last line in the queue file is this lane's `HOLD-` line on the same head, so it never revives a `MERGED`, `HELD` or `DROPPED-` pull request; otherwise it prints `FAILED` with that last line. The queue reader takes a pull request's last line as its state, so merge-lane-2 would no longer edit the prefix (open question 2). The appended line comes after other pull requests' lines, and the queue reader takes a waiting pull request's age from the place of its last line, so clearing a hold moves the pull request behind those queued meanwhile. A hold that waits on the user goes into the lane's own approval-walk, which is judgment.
- **The commissioned time.** The program takes it before the run, or at no-reviewer-tier before GRADE, so it is no later than the approval (PR 4925); the merge gate accepts a time equal to the approval's.
- **No posting after an approval.** When GitHub's review list shows that `ned-review-merge` has approved the head, the program does not post on it again, and prints `FAILED` naming that review. That does not stop a hand `gh` comment, which is what PR 4917 got. So the rule stays in the standing-agent-instructions: a correction goes to its reader by SendMessage, never as a comment on the pull request. A guard is not proposed: the failure happened once, and a further review repaired it.
- **A merge of main after an approval.** When the merge gate holds a pull request because it conflicts with main, the author makes a hand-merge. The new head shows as WAITS-FOR-VERDICT, and the plan reviews it whole. The program treats it as any other new head; it adds no round, because the round count counts only changes-requested reviews.
- **Lane ownership and replacements.** The watcher's assignment file must become the only place that says which lane a pull request belongs to, and the program reviews only pull requests that the listing gives its lane. Today a pull request that merge-lane-2 handed to a lane by hand, such as PR 5128, disagrees with the file, so a watcher pull request must land first, as a prerequisite. It does two things. A pull request whose `#replaces` lines, read by `scripts/pull-request-description-replaces-line-replaced-pull-request-chain-reader-common.py`, name one that is already assigned takes that one's lane. And merge-lane-2 gets a subcommand that records a hand-over in the file under the file's lock, so that the listing shows it; the hand-overs made so far are entered with it once. Once that lands, each assigned pull request has exactly one lane, and the first-job step "ask the other lanes which reviews they have running" is no longer needed (open question 4).

## Messages

The program does not call SendMessage itself (open question 6), so each SEND block names its recipient agent-seat, that agent-seat's current ListAgents ref and the message text, between a line `SEND` and a line `END-SEND`. The recipient is merge-lane-2, or the author agent-seat taken from the first commit's author name, as the watcher and the queue line take it. The program computes the ref when it prints the block, with `list_agents_tool_entry_ref_of_agent_seat_last_handoff_supervisor_launched_agent_session_find` in `scripts/agent-seat-idle-sweep-headless-judge-wake-messages-send-and-user-alerts-write.py`, and never reuses a ref from an earlier call. When the function finds no running agent-session for the recipient, or the first commit's author name is no agent-seat, the block says so in place of a ref, and the lane tells merge-lane-2, or, when merge-lane-2 is the recipient, the user in its approval-walk. The lane sends the text unchanged. A queue notice names every open hold, or says there is none.

## Steps that need judgment

1. Writing `hazards`, and adding tests the plan cannot find.
2. Grading each finding, including the regrade at the round limit and, for each cold-read-fast-read finding, deciding whether it is a misreading, which holds the merge, or a struggle, which merge-lane-2's seat-brief sends to the author as a follow-up.
3. Naming holds, deciding when one has cleared, and bringing to the user each hold that waits on him.
4. Acting on PLAN-REFUSED, RUN-FAILED, REVIEW-REFUSED and FAILED, including telling a transient fault from a defect.

## Left out

The program leaves these to the lane, as the seat-briefs already say: agent-arbitrators for declined findings, a silent author, findings that outlive a pull request and their GHIs, and adding fix-in-maintenance findings to GHI 1058, Regular maintenance. Merging, merge notices and the after-merge follow-up list stay with merge-lane-2. The program does not start the watcher's polling, which runs from cron; it only runs the watcher's listing. It does not judge the claims in a pull request's description; the programs it calls read the description as they already do.

## Open questions for the user

1. **Pull requests opened by `ned-review-merge`.** merge-lane-2's seat-brief keeps them with merge-lane-2, but the watcher assigns them to merge-lane-1 or merge-lane-3. Which rule holds? Recommendation: the watcher's, with merge-lane-2's seat-brief changed to match, so that the lane rules live in one place. On such a pull request the post program posts as COMMENT, because GitHub refuses an approval from a pull request's author, and `mac-claude` gives the approval the merge gate pins; at no-reviewer-tier no Claude reviewer runs, so the lane would have to ask for that approval.
2. **Who clears a `HOLD-` prefix.** May the lane append the unheld queue line itself, instead of asking merge-lane-2 to remove the prefix? This changes both lanes' seat-briefs and merge-lane-2's.
3. **Per-pull-request tasks.** May the state files and the watcher listing replace the review lanes' per-pull-request and round-2 tasks? Tasks for work the program does not do, such as a silent author or a finding that outlives the pull request, stay. This changes the seat-briefs.
4. **The first-job ask.** Once the watcher is the only source of lane ownership, may the step "ask merge-lane-2 and merge-lane-3 which reviews they have running" be dropped from merge-lane-1's seat-brief?
5. **Build order.** The watcher pull request, with the replacement rule and merge-lane-2's hand-over subcommand, lands before this program. Agree?
6. **Who sends the messages.** `scripts/agent-seat-idle-sweep-headless-judge-wake-messages-send-and-user-alerts-write.py` already sends a message through a headless agent-session and checks that the text it sent matches, apart from whitespace. May this program send its SEND blocks the same way, at the cost of one headless agent-session per message, printing `FAILED` with the block when a send fails? Recommendation: yes, for every SEND block: the lane sends each one unchanged anyway, a notice the lane never sends, because its agent-session ended after the program printed it, leaves merge-lane-2 or the author unaware, and the send happens at once, before the recipient's agent-session can change.

## Deferred-decisions

- What the program does when the review run's process is killed without writing its exit status, to be set from the first such case.
- The review run's time limit, after which `--wait-for-run` stops waiting and the program prints RUN-FAILED, to be set from the first runs' durations.
- Whether a `fast-read` hold clears itself once the cold-read-fast-read's cold-read-record is written, to be set once the first such holds are seen.
- Whether a RERUN of the same step on the same head is limited, to be set if a lane is seen rerunning a step that keeps failing.
- What the program does with a round whose pull request is closed, merged, made a draft or handed to the other lane while the round waits, to be set at build from the watcher's listing.
- In the watcher pull request: which lane a replacement takes when its `#replaces` lines name pull requests of different lanes, and what the watcher does with a `#replaces` line the reader cannot read.
- In the watcher pull request: what a hand-over does with a review that the earlier lane has running, and with that lane's state file and `HOLD-` line.
- How the program finds the agent-seat of an author whose first commit's author name is not the agent-seat that opened the pull request, to be set if such a pull request is seen.
