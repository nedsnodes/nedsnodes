## The problem

In this design a review lane is merge-lane-1 or merge-lane-3: an agent-seat on ned-box that manages the review of the pull requests the watcher, `scripts/merge-lane-open-prs-watch-and-reviewer-assign.py`, assigns it, and grades their findings. merge-lane-2 also manages reviews, of the pull requests its own seat-brief keeps, and it alone merges; this program is not for merge-lane-2. "The lane" below always means the review lane that runs the program. The three agent-seats' seat-briefs are `/home/nedlern/agents/<agent-seat name>/CLAUDE.local.md` on ned-box.

A review lane follows its seat-brief by hand for each pull request: it lists its assignments, runs `scripts/pull-request-review-plan.py`, writes the brief specifications file (a JSON list of one entry, which `scripts/merge-lane-pull-request-reviewer-brief-compose-with-facts.py` turns into the reviewer's brief), takes the commissioned time, starts the review run, grades, posts, writes the merge queue line and sends messages. The commissioned time is the UTC time taken just before the review run starts, or, at no-reviewer-tier, just before grading; merge-lane-1's seat-brief calls it the time the review was commissioned, and it is a field of the merge queue line. Of these steps, only the four kinds listed under "Steps that need judgment" need judgment; the program takes over the rest. Agents doing them by hand have made these mistakes:

## What the program is

The program is `scripts/merge-lane-pr-review-mechanical-steps-run-until-judgment-needed.py --agent-seat <merge-lane-1|merge-lane-3>`. It runs on ned-box, where every path below is a local path. Each call does every step the program takes over that is ready, then stops. The first line it prints is one output state from the table below, with that state's arguments on the same line. Under it come the files and text that the next step needs; any SEND block (see "Messages"); and then every open hold of the lane, each with what it waits for (its `waits_for`, see "What the review file holds") and the time it was opened. The lane, or a forked subagent of the lane's agent-session, acts on that state and calls the program again. The program never decides what code alone cannot decide. The lane never does a step that the program does.

**Calls.** `--agent-seat` is required on every call.
- With nothing else, a call first resumes the lane's round that has waited longest for the program, high-priority ones first, such as one whose review run has ended or whose author has posted a round record comment, the comment the fix-round author program posts when a round ends with no commit; then prints RUN-RUNNING when a review run holds the lane's run lock; and only then picks a new pull request, or prints NONE-WAITING. Whatever its first line, it lists below it the rounds that wait on the lane, with the state each waits in.
- `--pull-request <n>` acts on that pull request only, when the listing gives it to this lane, and otherwise prints REFUSED. When its round waits on the lane, it prints that round's state again; when its round is at FAILED, it tries the failed step again; when its review job is running, it prints RUN-RUNNING; and when its round waits for the author, or its head has a LEAVE-UNTIL-NEW-HEAD answer, or it is queued or closed, it prints that state again and does nothing.
- `--written <n>` tells the program that the lane has finished the file its round waits for: the brief specifications file at WRITE-HAZARDS, or the review file at GRADE, REVIEW-REFUSED or ROUND-LIMIT. The program cannot tell a finished file from its own skeleton by looking, so it waits for this call. It then checks the file: the brief specifications file must still be a JSON list of one entry, with the fields the program filled unchanged, except that the lane may add to `tests` and to `hazards`; the review file must be a JSON object of the shape "What the review file holds" gives. A file that fails prints the same state again with the reason.
- `--answer <n> RERUN` and `--answer <n> LEAVE-UNTIL-NEW-HEAD` answer RUN-FAILED for the pull request's current head. RERUN reruns what failed, as RUN-FAILED says; when another pull request's run holds the run lock, it prints RUN-RUNNING for that run and keeps the answer, and the first call that finds the lock free carries it out. LEAVE-UNTIL-NEW-HEAD prints the SEND block that reports the failure to merge-lane-2, then what a call with nothing else would print.
- `--hold-cleared <n> "<hold>"` clears one hold, named by its words as the review file gave them (see "Holds").
- `--wait-for-run <n>` blocks until the pull request's review job exits, then does what `--pull-request <n>` would. Called when the pull request has no review job, it does that at once.
- `--merge-queue-file <path>` names the queue file, when merge-lane-2 has named one other than `/home/nedlern/nedsnodes-logs/seats/merge-lane-2/merge-queue-2026-11-21.txt`. The program records the file in the round's state, so later calls on that round use it without the option.

A call the lane got wrong, such as a missing or unknown argument, a `--written` for a round that waits for no file, an `--answer` for a round not in RUN-FAILED, or a `--hold-cleared` naming no open hold, prints REFUSED with the reason and, where it helps, the usage or the open holds, and changes nothing. An exception the program did not foresee is caught at the top of the program and printed as `FAILED`, with the traceback and a SEND block to merge-lane-2, so the first line is always an output state. Every state exits 0 except FAILED and REFUSED, which exit 1.

**Two locks.** Every call holds the lane's call lock, `/home/nedlern/nedsnodes-logs/seats/<agent-seat name>/merge-lane-pr-review-mechanical-steps-call.lock`, with `flock` while it reads and writes the state file, the queue file and GitHub, because the lane, a forked subagent and a background `--wait-for-run` can call at the same time; `--wait-for-run` takes it only once the job has exited. Every `gh` and `git` call has a timeout, so a call cannot hold the lock indefinitely. A review job holds the lane's run lock, `/home/nedlern/nedsnodes-logs/seats/<agent-seat name>/review-run.lock`, the lock the lanes already take by hand, for as long as it lasts: the detached process that runs the job holds the lock with `flock`, so the lock is released when that process exits. A call that would start a review job while the run lock is held prints RUN-RUNNING for the job that holds it and starts nothing.

**What the program stores.** One JSON file per pull request, `/home/nedlern/nedsnodes-logs/seats/<agent-seat name>/merge-lane-pr-review-mechanical-steps-per-round-state/pr<number>.json`, holding, for each round, keyed by its head and round number, since a round the author ends with no commit is a second round on the same head: the output state last printed and when; the queue file; the commissioned time; the review job's log path and exit status, and the reruns of each step; the posted review id; and each open hold with the time it was opened. GitHub decides what has been posted; the state file only records where a round stands. The round number is 1 plus the count of `ned-review-merge`'s changes-requested reviews, counted as the fix-round author program, `scripts/pull-request-fix-round-author-brief-from-blocking-findings-and-one-commit-every-finding-answered-check.py`, counts them, including those of the pull requests this one replaces. The program uses that one number for the brief's tag, the queue line, the state file and the round limit. On every call the program reads afresh: the tier, the earlier reviewed head and the reviews from `scripts/pull-request-review-plan.py --json`; the assignment from the watcher's listing; and whether a review is already posted on the head from GitHub's review list. The lanes' hand-written `/home/nedlern/nedsnodes-logs/seats/<agent-seat name>/review-commissioned-<n>.txt` files stop being written, because the state file holds the commissioned time; no program reads them.

**What the review file holds.** It has the shape the post program already takes, `body`, `comments` and `merge_lane_codex_review_finding_grades`, without `verdict`, which the program sets from the comments, plus one key, `"holds"`: a list of `{"hold": "<a few words>", "waits_for": "user" | "author" | "cold-read-fast-read" | "reboot-test"}`. The program removes `holds` from the copy it posts. When a cold-read-fast-read or lint command failed, it appends to the copy's body a sentence naming each one that did not run. It refuses, as REVIEW-REFUSED, a `holds` that is not a list of such objects, a hold whose words are empty or contain `+`, and two holds whose words give the same word in the `HOLD-` prefix. When the review has comments and is not posted at CLOSED, the program also appends to the copy's body the three closing sentences that merge-lane-2's seat-brief gives a review with findings, word for word, so the lane does not type them; the program reads them from that seat-brief on each post, as the three sentences starting "For each finding you fix", so there is one copy, and prints `FAILED` when it cannot find them. At CLOSED they are left out, because they promise an after-merge list that a closed pull request never gets. The post program already checks every `finding_category` and a grade for every Codex finding, so this program repeats neither check.

## How each case is handled

- **Fix-rounds.** A fix-round push makes the watcher's listing show the pull request as WAITS-FOR-VERDICT again, and the plan gives the earlier reviewed head and whether the round is reviewed by its new commits alone or whole, and at which tier. The next call goes to WRITE-HAZARDS, or, when the round's tier is no-reviewer-tier, to GRADE. A round the author ends with no commit, with a round record comment on the same head, starts the next round on the program's next call, which reads that comment from GitHub. The program decides none of the plan's choices itself.
- **Changes requested.** The program posts the review, prints the author notice and keeps the round open until the head changes or a round record comment ends the round. The watcher listing, together with the state file, would replace the per-round task "Review PR <n> fix-round (round 2) when <author> reports it" (open question 3).
- **A head pushed during a round.** The review run reads the head once, from origin, and the post and the queue line name that head. The merge gate merges only the approved head. So a newer head is simply the next review of the pull request. A head that moves before the review job starts sends the round back through the plan, as RUN-RUNNING says. Before it posts, the program checks the head again; when the head has moved since the round's review job, or since GRADE at no-reviewer-tier, it posts nothing and sends the round back through the plan on the new head.
- **Failed runs.** The program never reruns by itself, because only the lane can tell a transient fault from a defect.
- **Holds.** Holds come from the lane's review file, never from the program's own guess, except the `bash-guard-check` hold WRITE-HAZARDS adds. Holds named in a review that requests changes stay open in the state file and appear in the next round's skeleton, where the lane keeps or removes them. While a hold is open on an approval, the queue line starts with a `HOLD-` prefix. The queue reader, `scripts/merge-lane-merge-queue-approved-lines-merge-in-order-until-none-left.py`, takes everything up to the first space as the prefix, so the program writes it as one word: `HOLD-` followed by each open hold's words joined by hyphens, with `+` between holds, such as `HOLD-user-approval+fast-read-messages`. When a hold clears, the lane runs `--hold-cleared <n> "<hold>"`. When the pull request is not yet queued, the program only removes the hold from the state file. Otherwise it appends the same line, with a `HOLD-` prefix naming the holds still open, or with none when none is left, and prints QUEUED with a SEND block to merge-lane-2 naming the holds left. It appends only when, under the queue file's lock, the pull request's last line in the queue file is this lane's `HOLD-` line on the same head, so it never revives a pull request whose last line, written by the queue reader's merge batch, is `MERGED` (merged), `DROPPED-` (taken out of the queue) or `HELD` (waiting for a new approved line); otherwise it prints `FAILED` with that last line. The queue reader takes a pull request's last line as its state, so merge-lane-2 would no longer edit the prefix (open question 2). The queue reader orders waiting pull requests by the place of their last line, after its own rules for high-priority and prose-only pull requests, so clearing a hold moves the pull request behind those queued meanwhile. A hold that merge-lane-2 or the user puts on a queued pull request stays merge-lane-2's to write by hand, as today. A hold that waits on the user goes into the lane's own approval-walk, which is judgment.
- **The commissioned time.** The program takes it before the review job, or at no-reviewer-tier before GRADE, so it is earlier than the approval it is queued with (PR 4925).
- **No posting after an approval.** When GitHub shows that the head is approved for the lane, by an APPROVED review of `ned-review-merge`, or, on a pull request `ned-review-merge` opened, by its COMMENT whose body starts with APPROVE, as the watcher reads it, the program does not post on that head again, and prints `FAILED` naming that review. That does not stop a hand `gh` comment, which is what PR 4917 got. The rule that a correction goes to its reader by SendMessage, never as a comment on the pull request, is written in no seat-brief today (open question 7). A guard is not proposed: the failure happened once, and a further review repaired it.
- **A merge of main after an approval.** When the merge gate holds a pull request because it conflicts with main, the author makes a hand-merge. The new head shows as WAITS-FOR-VERDICT, and the plan reviews it whole. The program treats it as any other new head; it adds no round, because the round number counts only changes-requested reviews.
- **Lane ownership and replacements.** The watcher's assignment file must become the only place that says which lane a pull request belongs to, and the program reviews only pull requests that the listing gives its lane. Today a pull request that merge-lane-2 handed to a lane by hand, such as PR 5128, disagrees with the file, so a watcher pull request must land first, as a prerequisite. It does two things. A pull request whose `#replaces` lines, read by `scripts/pull-request-description-replaces-line-replaced-pull-request-chain-reader-common.py`, name one that is already assigned takes that one's lane. And merge-lane-2 gets a subcommand that records a hand-over in the file under the file's lock, so that the listing shows it; merge-lane-2 enters the hand-overs made so far with it once. With that, and with merge-lane-2's seat-brief rules for lanes changed to the watcher's (open question 1), each assigned pull request has exactly one lane, and the first-job step "ask the other lanes which reviews they have running" is no longer needed (open question 4).

## Messages

The program does not call SendMessage itself (open question 6), so each SEND block names its recipient agent-seat, that agent-seat's current ListAgents ref and the message text, between a line `SEND` and a line `END-SEND`, with every line of the text indented by two spaces so that no line of it can be read as `END-SEND`. The ListAgents ref is the bracketed id in the entry that the ListAgents tool shows for an agent-session; the lane gives SendMessage that entry, as `scripts/agent-seat-idle-sweep-headless-judge-wake-messages-send-and-user-alerts-write.py` does. The recipient is merge-lane-2, reboot-test, or the author agent-seat taken from the first commit's author name, as the watcher and the queue line take it. The program computes the ref when it prints the block, with `list_agents_tool_entry_ref_of_agent_seat_last_handoff_supervisor_launched_agent_session_find` in `scripts/agent-seat-idle-sweep-headless-judge-wake-messages-send-and-user-alerts-write.py`, and never reuses a ref from an earlier call. When the function finds no ref for the recipient, or the first commit's author name is no agent-seat, the block says so in place of a ref, and the lane tells merge-lane-2, or, when merge-lane-2 is the recipient, the user in the lane's own approval-walk. The lane sends the text unchanged. A queue notice names every open hold, or says there is none.

## Steps that need judgment

1. Writing `hazards`, and adding test files the plan cannot find.
2. Grading each finding, including the regrade at the round limit and, for each cold-read-fast-read finding, deciding whether it is a misreading, which holds the merge, or a struggle, which goes to the author as a follow-up, by merge-lane-2's seat-brief's test: a misreading is the reader taking the message to say something it does not, or being unable to say what it says, and any other finding is a struggle.
3. Naming holds, deciding when one has cleared, and bringing to the user each hold that waits on him.
4. Acting on PLAN-REFUSED, RUN-FAILED, REVIEW-REFUSED and FAILED, including telling a transient fault from a defect.

## Left out

These stay with the lane, as the seat-briefs already say, and are not steps of the program: agent-arbitrators for declined findings; a silent author; findings that outlive a pull request and their GHIs; a task for each fix-next finding (one fixed in a follow-up pull request after the merge) and the filing of each file-for-later finding (an improvement filed as a task or a GHI); adding fix-in-maintenance findings, the grade for a nit or other maintenance work, to GHI 1058, Regular maintenance; and sending the cold-read-fast-read reports to the author. Merging, merge notices and the after-merge follow-up list stay with merge-lane-2. The program does not start the watcher's polling, which runs from cron; it only runs the watcher's listing. It does not judge the claims in a pull request's description; the programs it calls read the description as they already do.

## Open questions for the user

1. **merge-lane-2's lane rules.** merge-lane-2's seat-brief keeps pull requests opened by `ned-review-merge`, and those whose number leaves remainder 2 when divided by 3, with merge-lane-2, while the watcher assigns every pull request to merge-lane-1 or merge-lane-3 by load. Which rules hold? Recommendation: the watcher's, with merge-lane-2's seat-brief changed to match, so that the lane rules live in one place. On a pull request `ned-review-merge` opened, the post program posts as COMMENT, because GitHub refuses an approval from a pull request's author, and `mac-claude`, the GitHub account the Claude reviewer posts as, gives the approval the merge gate pins; at no-reviewer-tier no Claude reviewer runs, so such a pull request needs a `mac-claude` approval the program cannot give, and the program prints FAILED for it, as QUEUED says.
2. **Who clears a `HOLD-` prefix.** May the lane append the unheld queue line itself, instead of asking merge-lane-2 to remove the prefix? This design assumes yes; on no, `--hold-cleared` prints a SEND block asking merge-lane-2 to append the line instead. This changes both lanes' seat-briefs and merge-lane-2's.
3. **Per-pull-request tasks.** May the state files and the watcher listing replace the review lanes' per-pull-request and round-2 tasks? Tasks for work the program does not do, listed under "Left out", stay. This changes the seat-briefs.
4. **The first-job ask.** Once the watcher is the only source of lane ownership, may the step "ask merge-lane-2 and merge-lane-3 which reviews they have running" be dropped from merge-lane-1's seat-brief?
5. **Build order.** The watcher pull request, with the replacement rule and merge-lane-2's hand-over subcommand, lands before this program. Agree?
6. **Who sends the messages.** `scripts/agent-seat-idle-sweep-headless-judge-wake-messages-send-and-user-alerts-write.py` already sends a message through a headless agent-session and checks that the text it sent matches, apart from whitespace and a closing sentence it adds. May this program send its SEND blocks the same way, at the cost of one headless agent-session per message, recording each send in the state file and printing `FAILED` with the block when a send fails? Recommendation: yes, for every SEND block: the lane sends each one unchanged anyway, and a notice printed just before the lane's agent-session ended is never sent, which leaves merge-lane-2 unaware of a queued pull request or an author unaware of a review. The recipient can still change between the lookup and the send, as it can for the lane.
7. **The rule against correction comments.** May the review lanes' seat-briefs, and merge-lane-2's, say that a correction to a posted review goes to its reader by SendMessage, never as a comment on the pull request, since a comment after the approval makes the merge gate ask for a further review (PR 4917)?

## Deferred-decisions

- What the program does when the review job's process is killed without writing its exit status, to be set from the first such case.
- The review job's time limit, after which `--wait-for-run` stops waiting and the program prints RUN-FAILED, and the timeouts of the `gh` and `git` calls, to be set from the first runs' durations.
- Whether a `cold-read-fast-read` hold clears itself once the cold-read-fast-read's cold-read-record is written, to be set once the first such holds are seen.
- Whether a RERUN of the same step on the same head is limited, to be set if a lane is seen rerunning a step that keeps failing.
- How the program tells a head test step that broke from one that reports a failing suite, to be set at build from that step's output.
- What the program does with a round whose pull request is closed, merged, made a draft or handed to the other lane while the round waits, to be set at build from the watcher's listing.
- How a round the author ends with no commit, after declining findings, meets the agent-arbitrators the lane commissions, to be set at build from merge-lane-2's seat-brief section on declined findings.
- In the watcher pull request: which lane a replacement takes when its `#replaces` lines name pull requests of different lanes, or one that merge-lane-2 reviewed and the file does not list, and what the watcher does with a `#replaces` line the reader cannot read.
- In the watcher pull request: what a hand-over does with a review that the earlier lane has running, and with that lane's state file and `HOLD-` line.
- How the program finds the agent-seat of an author whose first commit's author name is not the agent-seat that opened the pull request, to be set if such a pull request is seen.
