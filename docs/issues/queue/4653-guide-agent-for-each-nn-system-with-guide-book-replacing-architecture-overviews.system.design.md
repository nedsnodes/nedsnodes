# A guide-agent and a guide-book for each nn-system, in place of the nn-architecture-overviews

This design builds what GHI-MD 4653, `docs/issues/4653-replace-every-architecture-overview-with-a-guide-agent-for-each-system-under-nn-systems-and-remove-the-overviews-and-everything-that-writes-checks-or-refreshes-them.md`, asks for. On 2026-11-28 at 05:36Z the user approved ("a") the outline of this design's five parts, as item 13.2 of 36 of ned-box-helper's approval-walk ned-box-helper-open-items-approval-walk-2026-11-26 (walk-minutes `nedlern@ned-box:/home/nedlern/agents/ned-box-helper/docs/walk/ned-box-helper-open-items-approval-walk-2026-11-26-minutes.md`, line 86; the item's text is in the walk-document beside them, § Item 13 of 36); the details below are this design's and wait for his approval of it. The overviews this design removes are the nn-architecture-overviews and the project's architecture page, `docs/nedsnodes-wiki/nedsnodes-project-architecture-overview.md`; "the overviews" means both.

Item 13.2 says "system-guide-agent"; the glossary's term is guide-agent, so this design says guide-agent, and names each one `<system>-guide-agent`, such as handoff-guide-agent. If [PR 4898](https://github.com/nedsnodes/nedsnodes/pull/4898), which renames each guide-agent `<domain>-guide`, merges before the ask script's pull request, each guide-agent's name, and the checkout and log file named after it, follow PR 4898; the names of programs, data files and fields in this design do not change.

Each guide-agent answers for one domain: an nn-system, as the glossary's entry nn-system names them, design-to-main included, or, under open question 1's recommendation, one skill or a piece split off a large nn-system. Where this design says a guide-agent's nn-system, it means that domain. A domain gets its guide-agent and guide-book only when someone first asks about it (Part 5).

A guide-agent's pieces that do not depend on its domain come from two designs: `docs/issues/46-ghi-guide-agent.system.design.md` § The ask path (ghi-guide-agent-ask), and GHI-MD 2266, `docs/issues/2266-two-more-guide-agents-wiki-guide-agent-for.md`, of GHI [Two more guide-agents: wiki-guide-agent for the wiki, and agent-instructions-and-hooks-guide-agent for how the project instructs and controls its agents](https://github.com/nedsnodes/nedsnodes/issues/2266), § What they share with ghi-guide-agent, and what each has of its own. Where the two differ, GHI-MD 2266 governs. This design states only what differs for an nn-system. GHI-MD 2266's shared module, `scripts/guide-agent-ask-scripts-common.py`, and its guide-agent table are not built yet. If they are not on main when this design's ask script is built, the ask script's pull request builds them, with what GHI-MD 2266 § Next action step 1 bundles with them other than wiki-guide-agent itself.

## Part 1. What a guide-book holds, and where it is kept

A guide-book explains what its nn-system's files leave unexplained or hard to extract, such as why the nn-system exists, what it is good and bad at, its limitations, and how it should be used. Where a file on main states something plainly, the guide-book points to that file instead of repeating it. A repeated copy drifts from the file, and that drift is why the overviews go.

Every guide-book lists each program of its nn-system that keeps running for more than an hour, and says how that program picks up a change to its code on main, such as restarting itself at each session-handoff, and what an agent that changes it must do when that is not enough; or it says the nn-system has none. A program that keeps running is one built to stay running, such as the handoff-supervisor, not a job that sometimes runs long. The list itself is the guide-book's own; where a file on main already says how one program picks up a change, that program's entry points to the file instead of repeating it.

Each guide-book is a wiki page, as the user ruled on 2026-11-23 (§ Item 13.1 of the same walk-document): `docs/nedsnodes-wiki/nedsnodes-<system>-guide-book.md`, where `<system>` is the name of an entry in the paths file of Part 3, such as `handoff`. The wording of the glossary entry for guide-book is the item "The glossary entry for guide-book" of the same approval-walk, which he has not answered yet; that item adds the entry in a glossary pull request of its own. A guide-book's pull request waits until that entry is on main, so until then the ask script adds no entry for a first guide-book (Part 5). The ask script's pull request adds a test that fails when a file `docs/nedsnodes-wiki/nedsnodes-*-guide-book.md` exists and the glossary has no entry guide-book.

A guide-book is a wiki page, so the instruction-file guard protects it, and `docs/nedsnodes-wiki/nedsnodes-which-changes-need-the-users-approval.md` lists creating one, and changing what one directs, among the changes that need the user's approval first. Part 2 has him review a guide-book change after it merges instead. So the ask script's pull request adds to that page's list of exceptions: "Creating a guide-book, `docs/nedsnodes-wiki/nedsnodes-<system>-guide-book.md`, or changing one; the user reviews the change after it merges, through the daily job of GHI 4653's design, Part 2."

## Part 2. How a guide-book changes, and how the user reviews it

A guide-book change merges through a pull request like any other. The user reviews it afterwards.

A daily maintenance-job, `nn-systems/general-tools/guide-book-changes-since-last-review-to-the-user.py`, runs on ned-box from `nn-systems/general-tools/scheduled-jobs-on-each-machine.json`. It is all code. It keeps one approval-state file per guide-book, `nedlern@ned-box:/home/nedlern/.local/state/nedsnodes/guide-book-user-approval-state/<guide-book file name>.json`, holding the last commit whose text the user approved, if any; the commit shown in an item he has not answered, if any; and the commit he last rejected, if any. The approval-state file is kept beside the user-alerts' state, not in the log-store, because it is state the job reads, and not in the guide-book, because a line in the guide-book would make each review a change that the job brings back to him.

1. It fetches origin/main and takes one commit of it, which every step of the run uses. It reviews each guide-book at that commit and each guide-book that has an approval-state file, so a guide-book that has an approval-state file but is no longer on main is reviewed too, as a deleted guide-book. A renamed guide-book is a deleted guide-book at the old path and a new one at the new path.
2. It skips a guide-book whose approval-state file shows an item the user has not answered, and one whose approval-state file shows a rejection when the guide-book has not changed on main since the rejected commit; the fix's merge is that change. Otherwise it diffs the last approved text, or an empty file when none was approved, against the guide-book at the run's commit, or an empty file for a deleted guide-book. An empty diff shows nothing, and clears a rejection, because the text is then the text he approved.
3. For the guide-books whose diff is not empty, it writes one user-alert naming the agent-seat that owns guide-agents, and records in each approval-state file the commit it showed. The user-alert carries one approval-walk item for each guide-book, written by the program: the diff, the commit on main it was taken at, and the two commands of step 4, one for each answer. The agent that claims the user-alert adds its items to the user's approval-walk, as for any user-alert. When the nightly overseer of GHI [Regular maintenance: the list of maintenance jobs, how often each runs, and how each reaches the user](https://github.com/nedsnodes/nedsnodes/issues/1058) is built, the job's items go to the overseer's approval-walk instead of a user-alert, as GHI-MD 1058, `docs/issues/1058-daily-maintenance-in-one-daily-step-starting-with.md`, § How the maintenance jobs run each night, and how often (decided), says for every maintenance-job; the approval-state files keep the state either way.
4. When the user approves an item, the agent runs the program's `--record-user-approval-of-shown-guide-book-change <guide-book path>`, with the guide-book's repository path, which records the shown commit as the last approved one and clears the unanswered item; for a deleted guide-book it deletes the approval-state file instead. Any other answer, such as an approval with a change, counts as a rejection with his words. When he rejects it, the agent runs `--record-user-rejection-of-shown-guide-book-change-and-add-fix-task <guide-book path> --user-words <his words>`, which records the shown commit as rejected, clears the unanswered item, and adds his words and the diff, as Part 3 adds an entry, to the task of the agent-seat that owns guide-agents for that guide-book. Each refuses a guide-book whose approval-state file shows no unanswered item. That task's subagent makes the change in a pull request, and the first run after it merges shows him the diff again, from the text he last approved, with the fix in it.

When an approval-state file cannot be read, a recorded commit cannot be found in git, or a git command fails, the job reports that guide-book's failure, goes on with the others, and exits nonzero, as a failed maintenance-job does.

## Part 3. Each guide-agent answers questions itself, and hands changes on

A guide-agent answers questions itself, from its nn-system's files and its guide-book, and changes no file. It hands every guide-book change to the agent-seat that owns guide-agents, and reports any other problem it notices as a find of GHI-MD 2266, so that its context stays on knowing the nn-system. This follows ghi-guide-agent's pattern of handing changes of substance to fixers (`docs/issues/46-ghi-guide-agent.system.design.md` § Maintenance and fixers). Like ghi-guide-agent, it may use Read, Grep and Glob, and its reply's schema allows file citations only, not web pages.

The ask script is `nn-systems/general-tools/nn-system-guide-agent-ask.py`, one program for every nn-system. It is called with exactly one of two options: `nn-system-guide-agent-ask.py --system <name> <question>`, where `<name>` is the name of the guide-agent's entry in the paths file, such as `handoff` or `walk-me-through`; or `nn-system-guide-agent-ask.py --path <repository path> <question>`. An unknown name gets exit 1 and a message listing the names in the paths file. It differs from GHI-MD 2266's ask scripts only in the following points, and in making its guide-agent's checkout on the first ask (Part 5).

- **Which guide-agent a path goes to.** The data file `nn-systems/general-tools/docs/nn-system-guide-agent-ask-repository-paths-each-guide-agent-covers.json`, which this design calls the paths file, has one entry for each guide-agent, holding its name, from which the guide-agent's own name is built, and listing the repository path prefixes of its nn-system's files. A path goes to the entry with the longest prefix that matches it, and a prefix matches only whole path components, so `nn-systems/handoff/` does not match `nn-systems/handoff-old/`. A path that matches no prefix, such as one under `nn-systems/general-tools/`, gets exit 1 and a message saying that no guide-agent covers it, so the asker reads the files itself. The ask script's pull request adds a test that fails when a prefix is in two entries, when a prefix matches no file on main, or when a guide-agent that the grouping of open question 1 requires has no entry. Where an nn-system's files are kept decides how the entries are written; see § Where an nn-system's files are kept.
- **The domain file list**, as GHI-MD 2266 uses the term. It is every file git tracks at the ask's commit under the guide-agent's entry, minus its nn-test-suites and every file under a `tests/` directory, plus the nn-system's guide-book when one exists. On 2026-11-27, `nn-systems/handoff/` held about 830,000 characters outside its tests, and `nn-systems/cold-read/` about 600,000. GHI-MD 2266 fails an ask whose domain file list exceeds its domain's size limit; here, only an nn-system whose list fits that limit is loaded whole at cold start. For a larger one, the cold start loads the nn-system's Markdown files, its guide-book, and the module docstring of each of its programs, and the guide-agent reads the rest when a question needs it. When even that exceeds the limit, the ask fails as GHI-MD 2266's does, and the ask script adds a task, as Part 3 adds an entry, asking the agent-seat that owns guide-agents to split the nn-system as open question 1 says. The cold-start prompt also carries the guide-agent's entry of the paths file, so the guide-book need not list the nn-system's files. GHI-MD 2266's freshness trigger applies over the whole domain file list and that entry.
- **The reply.** The reply is a JSON object, as GHI-MD 2266 § The reply, and how code validates it describes, and its citations are checked the same way. Its `kind` is one of `answer` or `out-of-scope`, and code reports any other value as a failed ask. Beside GHI-MD 2266's finds it has one more field, `guide_agent_reply_guide_book_proposed_changes`, for problems in the guide-book only; a problem in another file is a find. Each entry has a `guide_book_text_problem`, one of `guide-book-text-missing`, `guide-book-text-wrong` or `guide-book-text-duplicates-a-file-it-should-point-to`, which the schema enforces; for the last two, the guide-book's text it is about; for the first two, what is missing or what is wrong; and each file that shows it, with a quote from that file. Code checks each entry as it checks a citation: the guide-book's text, when the entry has one, is in the guide-book, and each quote is in its file at the commit the ask used. Code acts only on the entries that pass, in the reply the ask script returns after GHI-MD 2266's correction turn; it drops, with a note, an entry that fails, and every entry of an `out-of-scope` reply, as GHI-MD 2266 drops that reply's finds. A failed ask acts on none.
- **Handing a change on.** The program, not the guide-agent, acts on each entry of `guide_agent_reply_guide_book_proposed_changes`. It appends the entry to `nedlern@ned-box:/home/nedlern/nedsnodes-logs/guide-agent-finds/<guide-agent name>.md`, the log file of finds that GHI-MD 2266 names. Then it adds the entry to the agent-seat that owns guide-agents: to that agent-seat's pending task for the same guide-book when one exists, unless the task already holds the same entry, and otherwise in a new pending task written with `nn-systems/general-tools/agent-seat-task-list-new-pending-task-write-common.py`, whose subject names the guide-book. A task already in progress is left alone; the agent-seat starts the new task only after the earlier task's pull request has merged or closed. When appending or adding fails, the program prints the reply, then says what failed and exits nonzero. That agent-seat dispatches a subagent that writes the change and opens its pull request, or closes the task saying why, when the entry no longer applies; and that agent-seat is the pull request's author and runs its fix-rounds.

## Part 5. A guide-agent is made when someone first asks

An nn-system gets its guide-agent when someone first needs one, not all at once. Code detects "first": an ask for a guide-agent that has no checkout on ned-box. On that ask, the ask script makes the checkout `~/agents/<system>-guide-agent`, a linked worktree of `~/Projects/nedsnodes` at origin/main with a detached HEAD, as ghi-guide-agent's `~/agents/ghi-guide-agent` is, and cold-starts the guide-agent. When making the checkout fails, the program removes what it made and exits nonzero. On each ask while the nn-system has no guide-book on origin/main and the glossary on origin/main has the entry guide-book, the program itself adds a `guide-book-text-missing` entry for the whole guide-book; Part 3 adds it to the open task when there is one, so the first guide-book is asked for once. The new guide-book reaches the user by Part 2, compared with an empty file.

GHI 4653's work is done when the removal pull request, the ask script's pull request and the daily job have merged and the GHIs and pull requests of Part 4 are closed; each guide-agent made after that is its use, not its build.

## Where an nn-system's files are kept

The ask script's build waits on overall-cleanup's unanswered item "Keep each system's files together, and list the ones that cannot move, starting with the git rules" (walk-document `nedlern@ned-box:/home/nedlern/agents/overall-cleanup/docs/walk/overall-cleanup-refreshed-open-items-2026-11-26.md`).

- **If he approves it:** each nn-system's directory gets a list file naming its files kept elsewhere. A guide-agent's entry in the paths file is then the directory alone, and the ask script reads the list file for the rest: each path in it counts as a prefix of that entry, both for `--path` and for the domain file list. design-to-main's entry is its two directories until its files move. The guide-book points to the directory.
- **If he does not:** each entry lists every path prefix of the nn-system's files, such as `.claude/skills/walk-me-through/` beside `nn-systems/skills/walk-me-through/`. The guide-book need not list them, because the cold-start prompt carries the entry.

## Which steps need judgment

Only these steps need judgment, and each is done by a model or by the user:

1. Answering a question, as GHI-MD 2266 § Judgment and code lists for its guide-agents: choosing which passages answer it, writing the guidance, deciding whether the question is partly or wholly outside the domain and which other guide-agents to name, noticing finds, and correcting a reply whose citations failed (the guide-agent).
2. Noticing that the guide-book misses, misstates or repeats something (the guide-agent).
3. Writing a guide-book change: deciding what the files leave unexplained, and what to point to instead of repeating; or deciding that an entry no longer applies (the subagent of the agent-seat that owns guide-agents). Answering the review findings of its fix-rounds (that agent-seat).
4. Approving or rejecting a guide-book change (the user). The agent that presents the item runs the command his answer picks, which needs no judgment.
5. In the removal pull request, rewording each prose sentence that cites an overview, other than in the files left as they are (its author).
6. Splitting an nn-system into subsystem guide-agents, as open question 1 says (the agent-seat that owns guide-agents).

Everything else is code: mapping a path to a guide-agent, the checkout and its fast-forward, the domain file list and its size limit, the cold start, the reply's schema and its checks, the entry for a missing guide-book, the log file of finds, the task and adding to an open one, the daily diff against the last approved commit, the approval-state files, the user-alert and its items, the approval and the rejection's task, and the tests that keep the paths file whole, the overviews gone, and a glossary entry for guide-book present whenever a guide-book exists.

## Open questions

1. **How nn-systems are grouped under guide-agents.** Recommendation: one guide-agent per directory under `nn-systems/` other than `nn-systems/general-tools/` and `nn-systems/skills/`, plus one for design-to-main, whose files are still in `docs/design-to-main/` and `scripts/design-to-main/`. `nn-systems/skills/` holds skills that do unrelated jobs, so give each skill there its own guide-agent, covering its directory and its `.claude/skills/<skill>/`, such as walk-me-through-guide-agent for the approval-walk; and none for `nn-systems/skills/` as a whole. Split any other nn-system into subsystem guide-agents only when its Markdown files and docstrings alone exceed the size limit.
2. **Questions that span nn-systems.** Recommendation: no project-wide guide-agent. As in GHI-MD 2266 § What each guide-agent returns, a reply answers its own part and names the other guide-agents to ask, from GHI-MD 2266's guide-agent table, to which the ask script's pull request adds every guide-agent of the paths file, whether or not its checkout exists yet. The critical-component rules of the project's architecture page move to the new wiki page of Part 4.
3. **Which agent-seat builds, owns and maintains this.** Recommendation: ned-box-helper builds the removal pull request, the ask script, the paths file and the daily job. ned-box-helper is also the agent-seat that owns guide-agents: it receives each guide-agent's tasks, owns its guide-book pull requests, and is named in the daily job's user-alerts. Item 13.2's outline had each new guide-agent write its own guide-book; the alternative is that guide-agent dispatching its own subagent from inside the ask, but a guide-agent is not an agent-seat, so no agent-seat would then own that pull request's fix-rounds.
