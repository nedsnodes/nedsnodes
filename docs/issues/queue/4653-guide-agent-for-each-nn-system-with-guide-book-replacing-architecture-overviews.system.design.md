# A guide-agent and a guide-book for each nn-system, in place of the architecture overviews

This design builds what GHI-MD 4653, `docs/issues/4653-replace-every-architecture-overview-with-a-guide-agent-for-each-system-under-nn-systems-and-remove-the-overviews-and-everything-that-writes-checks-or-refreshes-them.md`, asks for. The user approved its five parts on 2026-11-27 ("a"), as item 13.2 of 36 of ned-box-helper's approval-walk ned-box-helper-open-items-approval-walk-2026-11-26 (walk-document `nedlern@ned-box:/home/nedlern/agents/ned-box-helper/docs/walk/ned-box-helper-open-items-approval-walk-2026-11-26.md`, § Item 13 of 36). Item 13.2 calls each guide-agent of this design a system-guide-agent; the glossary's term is guide-agent, so this design says guide-agent, and names each one `<system>-guide-agent`, such as handoff-guide-agent. If [PR 4898](https://github.com/nedsnodes/nedsnodes/pull/4898), which renames each guide-agent `<domain>-guide`, merges first, the names follow it.

A guide-agent's pieces that do not depend on its domain come from two designs: `docs/issues/46-ghi-guide-agent.system.design.md` § The ask path (ghi-guide-agent-ask), and GHI-MD 2266, `docs/issues/2266-two-more-guide-agents-wiki-guide-agent-for.md`, of GHI [Two more guide-agents: wiki-guide-agent for the wiki, and agent-instructions-and-hooks-guide-agent for how the project instructs and controls its agents](https://github.com/nedsnodes/nedsnodes/issues/2266), § What they share with ghi-guide-agent, and what each has of its own. This design states only what differs for an nn-system. GHI-MD 2266's shared module, `scripts/guide-agent-ask-scripts-common.py`, is not built yet. Whichever of the two GHIs builds first builds it.

## Part 1. What a guide-book holds, and where it is kept

A guide-book explains what its nn-system's files leave unexplained or hard to extract, such as why the system exists, what it is good and bad at, its limitations, and how it should be used. Where a file on main states something plainly, the guide-book points to that file instead of repeating it. A repeated copy drifts from the file, and that drift is why the overviews go.

Each guide-book is a wiki page, `docs/nedsnodes-wiki/nedsnodes-<system>-guide-book.md`, as the user decided on 2026-11-23 (§ Item 13.1 of the same walk-document). The glossary entry for guide-book is the item "The glossary entry for guide-book" of the same approval-walk. The first pull request that adds a guide-book adds that entry, in the wording the user approves there; he has not answered that item yet. A test fails when a file `docs/nedsnodes-wiki/nedsnodes-*-guide-book.md` exists and the glossary has no entry guide-book.

## Part 2. How a guide-book changes, and how the user reviews it

A guide-book change merges through a pull request like any other. The user reviews it afterwards.

A daily maintenance-job, `nn-systems/general-tools/guide-book-changes-since-last-review-to-the-user.py`, runs on ned-box from `nn-systems/general-tools/scheduled-jobs-on-each-machine.json`. It is all code:

1. For each guide-book on main, it reads the commit at which the user last reviewed that guide-book from `nedlern@ned-box:/home/nedlern/nedsnodes-logs/guide-book-last-reviewed-commit/<guide-book file name>.json`. A guide-book with no record has never been reviewed, and is compared with an empty file. A record whose guide-book is no longer on main is reported as a deleted guide-book, with its last reviewed text as the diff.
2. It diffs the guide-book on main against that commit. It does nothing for a guide-book whose diff is empty, or that an unanswered user-alert of this job already shows; the first run after his answer shows any later change.
3. For the guide-books that changed, it writes one user-alert naming ned-box-helper. The user-alert carries one approval-walk item for each guide-book, written by the program: the diff, the commit on main it was taken at, and the two commands of step 4. The agent that claims the user-alert presents the items: a single item when one guide-book changed, an approval-walk when more than one did. When the nightly overseer of GHI [Regular maintenance: the list of maintenance jobs, how often each runs, and how each reaches the user](https://github.com/nedsnodes/nedsnodes/issues/1058) is built, the job's questions go to the overseer's approval-walk instead, as GHI-MD 1058, `docs/issues/1058-daily-maintenance-in-one-daily-step-starting-with.md`, § How the maintenance jobs run each night, and how often (decided), says for every maintenance-job.
4. When the user approves an item, the agent runs the program's `--record-reviewed <guide-book path>`, which writes that guide-book's record with the commit the user-alert showed; it refuses a guide-book that no unanswered user-alert shows. When he rejects it, the agent runs `--rejected <guide-book path> --user-words <his words>`, which writes no record and adds a task, with his words, for the agent-seat that owns guide-agents (open question 3). That task's subagent makes the change in a pull request, and the first run after it merges shows him the diff again, with the fix in it.

The record is kept in the log-store, not in the guide-book, because a line in the guide-book would make each review a change that the job brings back to him.

## Part 3. Each guide-agent answers questions itself, and hands changes on

A guide-agent answers questions itself, from its nn-system's files and its guide-book. It hands every change to someone else, so that its context stays on knowing the system. This is ghi-guide-agent's pattern (`docs/issues/46-ghi-guide-agent.system.design.md` § Maintenance and fixers).

The ask program is `nn-systems/general-tools/nn-system-guide-agent-ask.py`, one program for every nn-system. It is called as `nn-system-guide-agent-ask.py --system <name> <question>` or `nn-system-guide-agent-ask.py --path <repository path> <question>`. It differs from GHI-MD 2266's ask scripts only in the following points.

- **Which nn-system covers a path.** The data file `nn-systems/general-tools/docs/nn-system-guide-agent-ask-repository-paths-each-guide-agent-covers.json` maps path prefixes to guide-agents; this design calls it the paths file. The longest matching prefix wins. A path that matches no row, such as one under `nn-systems/general-tools/`, gets exit 1 and a message saying that no guide-agent covers it, so the asker reads the files itself. A test fails when a guide-agent the paths file must have has no row: one for each directory under `nn-systems/` other than `nn-systems/general-tools/`, or, under open question 1's recommendation, one for each `nn-systems/skills/<skill>/` and one for design-to-main. Where a system's files are kept decides how the rows are written; see § Where a system's files are kept.
- **The domain file list**, as GHI-MD 2266 uses the term. It is every file the nn-system's row covers, minus its tests, plus the nn-system's guide-book when one exists. On 2026-11-27, `nn-systems/handoff/` held about 830,000 characters outside its tests, and `nn-systems/cold-read/` about 600,000. Only a system whose list fits GHI-MD 2266's size limit is loaded whole at cold start. For a larger one, the cold start loads the system's Markdown files, its guide-book, and the docstring of each of its programs, and the guide-agent reads the rest when a question needs it. The cold-start prompt also carries the system's row of the paths file, so the guide-book never has to list the system's files. GHI-MD 2266's freshness trigger applies unchanged, over the whole domain file list.
- **The reply.** The reply is a JSON object, as GHI-MD 2266 § The reply, and how code validates it describes, and its citations are checked the same way. Its `kind` is one of `answer` or `out-of-scope`, and code reports any other value as a failed ask. Beside GHI-MD 2266's field of finds it has one more field, `guide_book_proposed_changes`, which an `out-of-scope` reply leaves empty. Each entry has a `type`, one of `missing`, `wrong` or `repeats-a-file`, which the schema enforces; the guide-book's text, or, for `missing`, what is missing; and the files that show it. Code checks each entry as it checks a citation: the quoted text is in the guide-book, and each file exists at the commit the ask used. Only the final reply's entries are acted on, after any correction turn; a failed ask acts on none.
- **Handing a change on.** The program, not the guide-agent, acts on each entry of `guide_book_proposed_changes`. It appends the entry to `nedlern@ned-box:/home/nedlern/nedsnodes-logs/guide-agent-finds/<guide-agent name>.md`, the log file of finds that GHI-MD 2266 names. Then, with `nn-systems/general-tools/agent-seat-task-list-new-pending-task-write-common.py`, it adds a task holding the entry for the agent-seat that owns guide-agents (open question 3); when that agent-seat already has an open task for the guide-book, it adds the entry to that task instead. That agent-seat dispatches a subagent that writes the change and opens its pull request, and that agent-seat answers the pull request's fix-rounds.

## Part 5. A guide-agent is made when someone first asks

A system gets its guide-agent when someone first needs one, not all at once. Code detects "first": an ask for an nn-system whose guide-agent has no checkout on ned-box. On that ask, the ask program makes the checkout `~/agents/<system>-guide-agent`, the way ghi-guide-agent's was made, and cold-starts the guide-agent. When the system has no guide-book, the program itself adds a `missing` entry for the whole guide-book, and Part 3 hands the first guide-book to the agent-seat that owns guide-agents. The new guide-book reaches the user by Part 2, compared with an empty file.

## Where a system's files are kept

This waits on overall-cleanup's unanswered item "Keep each system's files together, and list the ones that cannot move, starting with the git rules" (walk-document `nedlern@ned-box:/home/nedlern/agents/overall-cleanup/docs/walk/overall-cleanup-refreshed-open-items-2026-11-26.md`).

- **If he approves it:** each nn-system's directory gets a list file naming its files kept elsewhere. A guide-agent's row in the paths file is then the directory alone, and the ask program reads the list file for the rest. The guide-book points to the directory.
- **If he does not:** each row lists every path prefix of the system's files. The guide-book names none of them, because the cold-start prompt carries the row.

## Which steps need judgment

Only these steps need judgment, and each is done by a model or by the user:

1. Answering a question: choosing which passages answer it, and writing the guidance (the guide-agent).
2. Noticing that the guide-book misses, misstates or repeats something (the guide-agent).
3. Writing a guide-book change: deciding what the files leave unexplained, and what to point to instead of repeating (the subagent of the agent-seat that owns guide-agents).
4. Approving or rejecting a guide-book change (the user).
5. In the removal pull request, rewording each prose sentence that cites an overview (its author).

Everything else is code: mapping a path to a guide-agent, the checkout and its fast-forward, the domain file list and its size limit, the cold start, the reply's schema and citation checks, the entry for a missing guide-book, the log file of finds, the task and its dedupe, the daily diff against the last reviewed commit, the user-alert and its items, the review record, the rejection's task, and the tests that keep the paths file whole, the overviews gone, and a glossary entry for guide-book present whenever a guide-book exists.

## Open questions

1. **How systems are grouped under guide-agents.** Recommendation: one guide-agent per directory under `nn-systems/`, plus one for design-to-main, whose files are still in `docs/design-to-main/` and `scripts/design-to-main/`. `nn-systems/skills/` holds skills that do unrelated jobs, so give each skill its own guide-agent, such as walk-me-through-guide-agent for the approval-walk. Split any other system into subsystem guide-agents only when its Markdown files and docstrings alone exceed the size limit. No guide-agent for "user-interface material" until a question shows one is needed.
2. **Questions that span systems.** Recommendation: no project-wide guide-agent. As in GHI-MD 2266 § What each guide-agent returns, a reply answers its own part and names the other guide-agents to ask, from the paths file. The rules that `docs/nedsnodes-wiki/nedsnodes-project-architecture-overview.md` held move to the new wiki page of Part 4.
3. **Which agent-seat builds, owns and maintains this.** Recommendation: ned-box-helper builds the removal pull request, the ask program, the paths file and the daily job. ned-box-helper is also the agent-seat that owns guide-agents: it receives each guide-agent's tasks and owns its guide-book pull requests. The alternative is a guide-agent that dispatches its own subagent from inside the ask; but a guide-agent is not an agent-seat, so nothing would then answer that pull request's fix-rounds.
4. **GHI [130](https://github.com/nedsnodes/nedsnodes/issues/130)**, the sanity-checker overview page, which the user wanted on 2026-08-22. It is a system map, not an nn-architecture-overview. Recommendation: close it in favour of the sanity-check system's guide-agent and guide-book, asking the user first, because he asked for it.
5. **PR [5181](https://github.com/nedsnodes/nedsnodes/pull/5181)**, which renames an overview-only commit in the fix-round check and also keeps binary changes in the saved diff. Recommendation: its author drops the overview part and merges the binary-diff fix. The removal pull request then deletes the rest of that code.
6. **Whether guide-books join the nightly refresh of designs of GHI [refresh-design: when a system's code lands, bring its design, build-slice plan and overview into line — removing, never revising](https://github.com/nedsnodes/nedsnodes/issues/670).** Recommendation: no. A guide-book holds what the code does not show, which GHI-MD 670's user-ruling of 2026-10-30 has that refresh fix rather than remove; the guide-agent's `guide_book_proposed_changes` (Part 3) already catches drift whenever a question touches it.
