# One problem-words system: a table of problem words and phrases, a checker that gives the reason for each hit, a promise check that reads the same table, and daily mining of transcripts for new rows

## Why

The user reads agents' messages cold, across many agents' terminals, and loses time to words he cannot pin down. On 2026-09-30, in the merge-lane-backlog agent-seat's approval-walk explain-skill-draft-2026-09-29-2, he directed a list of words agents should avoid, each with the reason and the word to write instead:

> "I have been thinking of having a 'bad' word list, an anti-glossary of sorts, words that should be avoided (and why). It, land, ... seem like good candidates"

He also named a second class, with a different reason and a different message to the agent:

> "agents saying they will remmember somethig, or will do something soon, but unless the todo soons are in a tasks list, or the remember somethings have some reminder or enforcmentt, those are 'bad' too - though for very different reasons - requiring very different 'error messages'."

He asked that the checker be mechanical and that each entry carry its replacement ("Is the style guide checker mechnical - if so good - I assume each word has the prefered alternative?"), and that the list be measured from the transcripts before the list is written ("we might want to review our jsonls for additional 'bad words'"). He approved filing the work ("y", 2026-09-30).

On 2026-10-05 he approved ("y") the design this GHI-MD now gives, at item 7 of the approval-walk cold-read-and-ask-the-user-rules-2026-10-05 (walk-minutes `nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/cold-read-and-ask-the-user-rules-2026-10-05-minutes.md`). He said the page `docs/nedschorus-wiki/nedschorus-style-guide.md` is misnamed, since it lists problem words rather than guiding style; that the two classes above are one system with two kinds of message, a vague word getting a clearer word suggested and a hollow promise getting the question whether a task backs the promise; that the reporter flags, says briefly why, and proposes, but never rewrites; that with code the list can be as long as needed; and that regular maintenance can look for more problem words: "maybe instead of a style guide this is really a guide to problem words and terms". The approved design: one problem-words system; the page renamed to `docs/nedschorus-wiki/nedschorus-problem-words-and-phrases.md`, with its checker, which reads the page by path, so the two change together; one table with a "Why it is flagged" column and a "Check" column; promise phrases and glossary-term rows in the same table; the checker reporting the reason with each hit, together with the suggestion or the task question; regular maintenance rerunning the transcript count and proposing new rows; a full cold read, then an approval-walk, before building; and the dead-links companion, md-drift-lint applying git's record of a file rename, filed as a GHI of its own, which GHI [A program that rewrites each Markdown citation of a renamed file to the file's new path, taking the new path from git's rename history](https://github.com/nedsnodes/nedsnodes/issues/3054) now carries. On 2026-10-08 he set the maintenance rerun to daily: "If it's automated it can be daily."

The legacy system's list failed as text alone. The legacy page records that "under heavy context ... the model falls back to training priors", and the one class the legacy system enforced at the moment of action, the postal softener guard, a reminder hook listed under Supporting documents, is the class that held (the legacy GitHub issue nedlern/nedlern#1513, cited by this GHI's first version; that GitHub issue's title is not readable from the agent-seats' GitHub account). So this GHI builds the list and its enforcement together.

## What to build

1. **The page `docs/nedschorus-wiki/nedschorus-problem-words-and-phrases.md`**, renamed from `docs/nedschorus-wiki/nedschorus-style-guide.md`, holding one table, the project's one list of problem words and phrases. The list is one for the whole project, not one per system as the glossaries are (user, 2026-10-01). The table's heading becomes "## Problem words and phrases", and its columns become:

   | Column | What the cell holds |
   |---|---|
   | Word or phrase | the row's name, as the Word column holds it today |
   | Forms flagged | the forms the checker finds, each in a code span; a promise row's forms are regular expressions, each in a code span that starts `re:`, because a promise such as "I'll … when <an event>" has words between its fixed parts |
   | Forms not flagged | the forms the checker skips, as today |
   | Why it is flagged | one sentence of reason, such as "carries five project meanings, so a reader cannot tell which one the writer meant", or "a promise to act later, which nothing makes happen unless a task names the event" |
   | Check | what the writer is asked to do: for a word row, `suggest:` followed by the row's Write instead text of today; for a promise row, `ask:` followed by the kind of sentence, one of `promise_after_event`, `standing_rule`, `hold` and `conditional_on_user`, and the question the idle sweep's judge puts, such as "does a task's `prerequisites` or `blockedBy` name the event?" |
   | Applies to | as today: files, messages to other agents, messages to the user; a document put to review, item 3's fourth place, counts as files; a promise row applies to messages to the user only |

   The table holds three kinds of row, each written in the same columns:
   - **Vague, overloaded or replaced words**, the rows the page has today, kept with their forms and their Write instead text, which moves into the Check column. Candidates already ruled or proposed, beyond the rows on the page: the legacy list's overloaded words and deceptive phrases, where the measurement shows agents still use them; and the status-inflation class, "a 100% fail indicator" (user-ruled 2026-07-22), phrases that declare a fresh thing established, such as "standing doctrine", whose siblings, such as "is now doctrine" and "established practice", the daily mining of item 6 looks for.
   - **Glossary-term rows**, as item 5 says.
   - **Promise phrases**, as item 4 says.

   The parser that reads the table rejects, as a malformed row, a Check that starts with neither `suggest:` nor `ask:`, an `ask:` kind outside the four above, a `re:` form that does not compile, a promise row whose Applies to is not messages to the user only, and every case today's parser rejects.

   Which rows are on the table is the user's decision, row by row, through the approval-walks of item 6; the build's first version carries the rows the page has today and the promise rows of item 4.

3. **The word checker**: a script holding no list of its own, with no model in the loop, that reports each hit with its line, the row's Why it is flagged text, and the row's Check text. The suggestion is a word ("merge" for "land"), the names to choose from ("nn-head-commit or `HEAD`" for "head"), or, where no single word fits, an instruction ("write the noun" for "it"). A script cannot tell every "that" used as a pronoun from a joining "that", so the checker flags candidates and the writer judges each one. Code and quoted text are exempt, as today. When the page is missing or a row is malformed, each hook prints the parser's error and lets the write or the send through, as the Markdown edit hook does today with any error, because a hook that blocked on a bad page would stop every agent's edits. The checker skips the rows whose Check starts `ask:`, because item 4's ruling puts the promise check in the idle sweep alone.

   **No model rewrites a flagged word; every hit goes back to the writer** (user-approved 2026-10-01, in the approval-walk glossary-names-for-ambiguous-project-words-2026-10-01; restated 2026-10-05). Only the writer knows which meaning it intended: bare "head" is an nn-head-commit or `HEAD`, and a rewriting model without the agent-session's context would guess. A guess shown to the user would also be text the writing agent never wrote and does not hold, so a sentence the user quotes back could not be found. The checker runs at four places, each through a Claude Code hook except the last:
   - **A Markdown file**: the PostToolUse hook on the Write and Edit tools, built today, checks the text just written and hands the agent each hit's line, reason and suggestion, while the file is open.
   - **A message to another agent**: a PreToolUse hook on the SendMessage tool stops the send until the agent rewrites the message, so the receiving agent never reads the listed word. A send the agent repeats unchanged passes, because the writer judges each candidate: a word used in its ordinary English meaning, or in quoted text, stays. The hook's refusal text tells the agent this outright, in one instruction line: when each flagged word is used in its ordinary English meaning or inside a quotation, send the same message again unchanged and it goes through (user-approved 2026-10-02; the line in the refusal text user-directed the same day). The hook keeps a hash of each message it refused in a state file of the agent-seat's own, so it can tell an identical second send.
   - **A message to the user**: a MessageDisplay hook marks the word on screen with its choices, such as "head (nn-head-commit or `HEAD`?)", without choosing one. The mark adds to the agent's words and removes none, so a sentence the user quotes back still holds the agent's own words. A Stop hook tells the writing agent which listed words its message used. No hook can make the agent rewrite a message before the user reads the message, because the message is the model's own output.
   - **A document put to review**: a section of the cold-read-fast-read report on every document the cold-read-fast-read reads, as a second pass, placed beside the section the report already adds for bare GHI numbers in walk-documents (`nn-systems/cold-read/cold-read-fast-read.py`).

   The text each hook hands the agent follows CLAUDE.md's bullet on the text a program hands an agent.

   **Checking further places is not pursued** (user-ruled 2026-10-02): program messages outside the registered hooks, prompts, and message texts written out in documents are not checked, by pattern or by a fast model, until a listed word in one of them is seen causing a mistake, because a trial the agent-seat MD-skills ran on 2026-10-02, a pattern for dates, rulings and GHI numbers over the module-level string constants of all 152 programs and tests on main, found 16 false hits in 26 outside the hooks, and each false hit sends an agent to change text that was right. A test that fails on citations in the registered hooks' messages is planned under GHI [Every refusal and warning a program hands an agent says why and what to do instead](https://github.com/nedsnodes/nedsnodes/issues/956).

   **The MessageDisplay hook, measured 2026-10-01 on Claude Code 2.1.287** (`nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/merge-lane-backlog/message-display-hook-live-test-2026-10-01.md`): the hook runs before the text is shown, once per batch of completed lines. The screen showed only the hook's replacement and never the raw text, in an interactive test and in a headless test. The transcript, and what the model sees, keep the original text. The display waits for the hook: a hook that slept 3 seconds delayed the text by about 3 seconds, so the hook must be fast. Claude Code's code also has a path that shows the raw text first and rewrites the text when the hook returns; that path did not run in the test, and what selects that path is not measured. If that path runs, the mark appears a moment after the word instead of with the word.

4. **The promise check, reading its phrases from the table.** The promise check is built as part of the idle sweep, a job that each minute looks for agent-seats that have stopped working and judges what to send them, of GHI [Tasks raise themselves when their due time passes or their prerequisite is met](https://github.com/nedsnodes/nedsnodes/issues/940), whose § Promises and announced actions says when the promise check runs, who judges and what message the agent gets; this item keeps what the promise check looks for and what backs each kind of sentence. A promise phrase in an agent's message (the measured forms: "I'll bring you X", "I'll report when…", "Noted", "I'll hold", "from now on", "going forward", "from here on", "I'll carry …", "I'll pick up …", "I won't … until …", "I'll … when/once <an event>" and "say the word and I'll …") passes only when the agent backed the promise with the trigger that will make it happen (user-approved 2026-10-02). The principle: a rule names the trigger that enforces it, because a rule with no trigger depends on an agent remembering it.
   - **A promise to act later, or after an event**: passes when a task's `prerequisites` or `blockedBy` name the event, so GHI 940's idle check raises the task when the event happens. A task with neither does not pass, because nothing makes it fire.
   - **A standing rule** ("from now on…", "going forward", "from here on", "Noted"): passes only when backed by the hook or test that enforces it, or by a task to build one together with a proposal to the user. A memory never passes: nothing forces an agent to read one.
   - **A hold** ("I'll hold"): passes with a task whose `prerequisites` name what releases the hold.
   - **An announced action**: a sentence saying the agent is doing, or is about to do, an action, such as "Next I'm starting the pull request" or "I'm starting the PR 1633 work now", found by the announced-action patterns of `scripts/agent-seat-idle-sweep-verdicts-print.py`, which began as the phrase set at the top of `nedlern@ned-box:/home/nedlern/nedschorus-logs/analysis/announced-action-not-executed-measurement-2026-10-19/measure_announced_actions.py`, or by the judge of GHI 940's idle sweep when the patterns miss the sentence. A sentence that is conditional, such as "I'll push once the tests pass", is a promise to act after an event, above; a negative one, such as "I won't push yet", is not an announced action. An announced action passes when a later tool call does the action or a background task the agent started is still running.

   The promise check runs on an agent-seat that GHI 940's idle sweep finds idle, over every message that ended one of its turns since the sweep last checked it, and raises each unbacked sentence once, with a message telling the agent to back the sentence or tell the user it takes the sentence back.

   **The table is the one list of promise phrases** (user-approved 2026-10-05). The four tagged entries of `PROMISE_PHRASES` become rows of the table, one row for each phrase those four expressions join with `|`, such as one row for "from now on" and another for "going forward", each with its `re:` forms and its kind in the Check column, and the idle sweep reads those rows from the page each time the job runs, instead of holding its own copy. A change to the promise phrases is then a change to a row, which the user approves like any other row and which item 6's daily mining can propose. The announced-action patterns stay in the idle sweep's code, and a sentence below the table names them and says why an announced action is flagged, with no row: the patterns are not phrases but a sentence grammar, lists of a hundred verbs and their "-ing" forms combined with subjects such as "I'll" and "let me" and with exclusion rules, which no row of fixed forms can hold. The rules that settle a sentence's kind stay in code too, such as that a sentence the user has the next move in is `conditional_on_user` whatever else it matches.

   Three constraints on how the idle sweep reads the table:
   - The idle sweep is not nice-but-dirty, and code that needs nice-but-dirty code is nice-but-dirty too, so the idle sweep does not import `scripts/problem-words-and-phrases-checker-nbd.py`. The table's parser moves into a module without the -nbd suffix, with its own tests, which the checker and the idle sweep both import.
   - When the page is missing or a row is malformed, the parser raises an error naming the row, as `StyleGuidePageError` does today. The idle sweep then skips the promise check for that run, writes the error where the job reports its failures, as GHI 940 says for the job's other failures, and runs its other rules, so a bad edit to the page never stops the wake of an idle agent-seat.
   - The build changes, in the same pull request as the move of the phrases, the comment above `PROMISE_PHRASES` in `scripts/agent-seat-idle-sweep-verdicts-print.py` and the sentence of GHI 940's § Promises and announced actions that says the job's module holds the one copy of each list, so that both name the table.

   Where the promise check runs is user-ruled 2026-11-01 (item 1.1 of reboot-test's approval-walk reboot-test-remote-control-never-connected-reconnect-2026-11-01, "A"; walk-minutes `nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/reboot-test-remote-control-never-connected-reconnect-2026-11-01-minutes.md`): only in GHI 940's idle sweep, with no Stop hook. This supersedes the Stop hook this item carried as approved on 2026-10-02, and items 8 and 10 of fleet-restart-at-login-every-open-question-combined-approval-walk-2026-10-22 (2026-10-23: the refusal line "Refused: you announced an action you have not done." and building the announced-action hook first); its item 9, that conditional and negative sentences are not raised, stands. The ruling of 2026-11-01 decided where the promise check runs, not where its phrases are kept; the sentence a later edit of this GHI-MD added on 2026-11-01, that the job's module holds the one copy of each phrase list, had no user-ruling behind it and is replaced by this item.

5. **Glossary-term rows as a class.** A word with several project meanings, each of which a glossary names, gets a row whose Check suggests the glossary's names, one for each meaning, such as the `seat` row today: agent-seat, agent-session, working directory, cold-read-cell. Such a row does not forbid the word: written bare, the word keeps only its ordinary English meaning, and the row reminds the writer which name each project meaning takes. The rows the user approved for six such words on 2026-10-01, in the approval-walk glossary-names-for-ambiguous-project-words-2026-10-01, are on the page today: home, draft, walk, seat, head and drain. Two things add a row. A test splits every hyphenated term in the glossaries into its words and fails when a word appears in two or more terms, as `seat` appears in agent-seat and seat-brief, and no row's Check names each of those terms; so a pull request that adds such a term adds the bare word's row, or the term to the existing row, in the same pull request. And item 6's daily mining proposes a row for a bare word it finds used for a glossary term's meaning.

6. **Daily mining of transcripts for new rows** (user-approved 2026-10-05; daily, 2026-10-08), as a job of GHI [Regular maintenance: the list of maintenance jobs, how often each runs, and how each reaches the user](https://github.com/nedsnodes/nedsnodes/issues/1058), run by `scripts/problem-words-and-phrases-daily-transcript-mining-new-row-proposals-nbd.py`. Its steps, divided by code-prompt-code:
   - **Code counts**, with no model, over the agent-session transcripts and cold-read-records written since the job's last run: the words and phrases the user asked the meaning of, or said confused him; the words cold-read-cells quoted as unclear; the sentences that hold a future or commitment marker, such as "I'll", "once" or "until", and match no promise row; and the bare words of glossary terms, as item 5 says. Code drops every candidate an existing row already flags or a row the user declined already names, and keeps a running count per candidate in the job's state file, so a word that recurs over days rises.
   - **A model judges** the candidates whose count passed a threshold that code applies: whether each is a problem word or phrase, and, for each that is, the row it proposes, with its forms, its Why it is flagged sentence and its Check.
   - **Code checks** each proposed row with the table's parser and drops a row the parser rejects or whose forms match none of the candidate's sentences the count found.
   - **The user decides** each proposed row in the approval-walk of GHI 1058's section "How a daily job is handed to the user and tracked (decided)". Code then writes each approved row into the page and opens its pull request, and records each declined row in the job's state file so that the row is not proposed again.

   The 2026-09-30 and 2026-10-02 measurement scripts under Supporting documents are where the counting code starts. GHI 1058's GHI-MD gains this job in an edit of its own.

7. **CLAUDE.md points to the page**, in its bullet `Read docs/nedschorus-wiki/nedschorus-style-guide.md.`, changed by item 2's pull request to the new path, so every agent reads the list before acting. CLAUDE.md's terms bullet already carries the rule this page backs: "Use a glossary's term, spelled as the glossary spells it".
