# Catch a guarded file changed without the user's approval, ask him, and keep every version

## What is wanted

One hook, registered under PostToolUse and PostToolUseFailure so that it runs after every tool call, that notices when a guarded file has changed without the user's approval, by any route, a shell command included. It copies the new version into the machine's backup directory and tells the agent to ask the user. The change stays in place while he is asked. The hook reminds the agent after every tool call until the change is settled: the user approved it, or the agent put the approved version back. Every version a run sees is kept, with the approved versions of each file named, in one backup directory per machine, both in the log-store on ned-box: ned-box's hook writes there directly, and the Mac's hook writes there over the Mac's mount of ned-box's home, `/Volumes/nedhome`. The routes it does not catch are listed under "Known gaps". The hook is built, and the quotation check, the backup search by file and the approval binding of § Approval binding are not; § What is built says what main's code does, where it differs from this design, and what is left.

A **guarded file** here is a file that `.claude/guard-hooks/instruction-file-guard.py` protects: `CLAUDE.md` and `CLAUDE.local.md`, everything under a `.claude/` directory apart from `worktrees/`, `jobs/` and `handoffs/`, a `-prompt.md` or `-instructions.md` file, and a reviewed document (a `.md` file under `docs/agents/`, `docs/nedsnodes-wiki/` or `nn-systems/skills/`, or a `.design.md` file), with the exceptions that guard makes; plus `~/.claude/CLAUDE.md` and `~/.claude/settings.json` (term approved by the user, 2026-10-12).

## Why

The instruction-file guard is a PreToolUse hook on Edit, Write and NotebookEdit. A write to a guarded file goes through only once the agent has written the user's approval words into a one-use marker file, `.walk-approved`; a write into a Claude Code memory directory is always refused. The guard does not see a shell command, and the files a shell command will write cannot, in general, be known before it runs. Two records:

- On 2026-08-24, about 60 lines of credential reference material built up in an agent-seat's `CLAUDE.local.md`, written by shell commands, before the user noticed (GHI [Review-system design requirements learned from the legacy gate — dormant until a class of work first requires review](https://github.com/nedsnodes/nedsnodes/issues/31), item 2 of its list "Guards").
- On 2026-09-13 the guard was fed two payloads naming the same `CLAUDE.md`: the Edit payload was refused, the Bash heredoc payload allowed (GHI [wiki-write skill, and the detect-set-aside-ask hook that enforces it — checking the file, not the tool call](https://github.com/nedsnodes/nedsnodes/issues/343)).

On 2026-10-03 the user designed the last layer of defence: "If we track SHAs - then we can easily add a backup directory to it when SHAs are updated." On 2026-10-12 he simplified it, in the approval-walk `unapproved-guarded-file-changes-set-aside-and-restore-the-approved-version-2026-10-11-2`: the hook does not put anything back by itself; it asks. "Why do we need more than one gate - if we check every post tool that's enough checking." The agents' failures are accidents between cooperative agents, so a reminder that does not stop until the change is settled is enough. This replaces two of his 2026-10-11 rulings, which he approved on 2026-10-12: asking first replaces putting the approved version back first, and stocking each machine's files once replaces the first copy taken per path. The term he approved for a saved-aside change, guarded-file-unapproved-change-set-aside-for-user-decision, is dropped with the saved-aside change itself (user-ruled 2026-10-12); a file waiting for the user is simply a file that is not settled.

## The design

§ Approval binding, below, records what an approval-walk decided from 2026-11-10 to 2026-11-12 about the approval line in `.walk-approved`, the instruction-file guard, `--approve`, the store's layout, and ways 1 and 4 of § The approved set. Where an entry there names a sentence of this section as replaced, read that sentence as replaced until the build rewrites it; an entry that names none adds a rule this section does not yet state.

### When it runs, and how fast

It is a hook for every tool, registered under PostToolUse and PostToolUseFailure, since PostToolUse runs only after a tool call that succeeds. It does not run at Stop (user-ruled 2026-10-11). When nothing has changed it takes under 100 ms per tool call on ned-box (user-ruled 2026-10-11): it compares the stat data it stored at its previous run (change time, modification time, size, inode) and hashes only a file whose stat data differs, as git hashes it (`git hash-object --path=<path> <file>`). A throwaway prototype took about 40 ms per run on ned-box on 2026-10-11.

### Which files it checks

- **In the checkout of the tool call's working directory:** every guarded file in it, tracked, untracked or ignored, decided with the guard's own functions, `is_protected`, `is_reusable_prompt` and `is_reviewed_document`, imported from `.claude/guard-hooks/instruction-file-guard.py`, so the two hooks cannot disagree. Ignored files are listed with `git ls-files --others --ignored --exclude-standard` restricted to `CLAUDE.local.md` and `.claude/settings.local.json` at any depth, the only ignored files that can hold instructions, so Claude Code's own ignored files under `.claude/`, which it rewrites itself, and the large ignored trees, such as `__pycache__/`, are never read.
- **Outside every checkout:** `~/.claude/CLAUDE.md`, `~/.claude/settings.json`, and, for each directory directly under `~/agents/`, the agent-seat files: its seat-brief, `~/agents/<agent-seat>/CLAUDE.local.md`, and its `~/agents/<agent-seat>/.claude/settings.local.json`, each when present. They are checked after every tool call from any working directory, one in no checkout included, where these are the only files checked and no git step runs. The agent-seat files were user-ruled 2026-11-25, item 66 of the approval-walk `reboot-test-undecided-items-carried-over-from-git-worktrees-redesign-approval-walk-2026-11-22`, whose walk-minutes are `nedlern@ned-box:/home/nedlern/agents/reboot-test/docs/walk/reboot-test-undecided-items-carried-over-from-git-worktrees-redesign-approval-walk-2026-11-22-minutes.md`. The checkout's list leaves out exactly these paths, so a change to either agent-seat file of the checkout the agent runs in is asked about once; a `CLAUDE.local.md` or `.claude/settings.local.json` at any other path, such as in a topic-worktree, stays in its checkout's list. Like every file outside a checkout, each version of an agent-seat file is copied into the store.

Apart from the agent-seat files above, a write a session makes into another checkout is noticed by the next session that runs in that checkout, not by the writer; a checkout in which no agent-session ever runs is never checked, as § Known gaps says.

Memory files are not checked: the guard refuses every Edit and Write into a memory directory, and on ned-box 731 memory directories held 3 files on 2026-10-12.

### The approved set

For each checked path, the hook keeps in the machine's backup directory the set of content hashes approved for that path. A file is **settled** when its current content's hash is in its path's approved set; otherwise it is waiting for the user. Nothing else records that a question is open: the reminder is derived from the content, so it survives a handoff, a crash and the removal of a worktree. A hash enters the set in six ways:

1. **Git's own work.** When a run sees HEAD moved by a branch switch, a reset, a merge, a pull, a rebase, a cherry-pick or a revert since its previous run in this checkout, the versions HEAD then holds are added. A `git commit`, `--amend` and a squash merge included, adds nothing: it commits the agent's own content. The hook finds what happened from the reflog entries newer than the newest entry it saw at its previous run, identified by that entry's whole reflog line: old and new commit, time and subject. Commit and time alone can repeat within one second, and neither the reflog's length nor the entry's index identifies an entry, because expiry can keep the length constant and shift the index. A position an earlier version of the hook stored, the entry's commit and time alone, is still read by those two fields. Each hook run then stores the newest reflog entry as its new position, whether or not the stored position matched, except while a rebase, merge, cherry-pick or revert is in progress, when it keeps its previous position. When no entry, or more than one, matches the stored position, the hook run does not know what happened, approves nothing as git's own work, and asks about every changed version that no other way in this list approves. A commit that finishes a merge, cherry-pick or revert that a previous run saw stopped on a conflict counts as git's own work, and the run records in the checkout's stored state, beside its reflog position, that it saw the checkout stopped. That commit approves only versions no run saw before it: a resolution a run saw before the commit stays unapproved under this item's rule that only the user's yes approves a version the hook has seen, so the user is asked about it. The rule has no exception for hand-merges (user-ruled 2026-10-13), since hand-merges of guarded files are rare and an exception would add a waiting state to the hook. Because the set is kept, a version added once stays approved: a `git stash apply` that brings back an approved version is settled. A version the log records as seen and not approved for that path enters the set only by the user's yes, by origin/main, item 5, or as a deletion, item 6, never by git's own work: not by a commit, a branch switch, a checkout, a merge or any other git operation (user-ruled 2026-10-13). Without this rule, an agent that commits an unapproved version, switches to another branch and switches back would have the version approved by the second switch, though the user never saw it.
2. **A successful Edit, Write or NotebookEdit,** while the instruction-file guard refuses every such call that has no approval marker (user-ruled 2026-10-12): the version the call wrote is added by the hook run after it, when the version the hook's previous run saw was approved, or the previous run saw no version or a deletion. The guard's marker file approves only the call's own change, so a call made on a version the user has not approved, such as a shell edit's, adds nothing: its version is asked about, and the ask says why.
3. **The user's yes,** recorded by the hook's approve command (below), which adds the one hash the user was shown.
4. **Stocking:** the first run on a machine adds the current version of each file outside every checkout, the agent-seat files included (user-ruled 2026-10-12). On a machine whose runs checked `~/.claude/CLAUDE.md` and `~/.claude/settings.json` before the agent-seat files joined them, the first run that checks the agent-seat files, once per machine, adds the current version of each one whose path has no approved version yet, so only a later change is asked about; an agent-seat file that appears after that run, such as a new agent-seat's, is asked about as any new version is. What a checkout holds at its first run still counts as approved, but the hook records only the commit the worktree started from, in the worktree, in the checkout's stored state in its git directory. When a guarded file first changes, the hook copies that file's version at the recorded commit, from git, into the log-store, before its check for an edit made on a version the user had not approved; it copies the version at that commit, not at HEAD, so an unapproved edit an agent commits before any run sees it is still asked about. A file that differs from that commit at the first run is copied and approved as it is then. A new worktree, whose files match the commit it started from, then writes nothing to the log-store at its first run (user-ruled 2026-10-30, item 11 of the approval-walk `prime-intellect-handed-over-items-2026-10-29`, whose walk-minutes are `nedlern@ned-box:/home/nedlern/agents/prime-intellect/docs/walk/prime-intellect-handed-over-items-2026-10-29-minutes.md`).
5. **origin/main:** a version that the checkout's local `refs/remotes/origin/main` holds at the same path is added, even one a run saw unapproved, such as during a rebase stopped on a conflict, because every version on main came through a reviewed pull request. The hook reads the local ref and never fetches. When git cannot read the ref, the run reports the failure and settles nothing.
6. **A deletion:** the reserved hash `deleted` is added whenever a run sees a guarded file absent, wherever the deletion came from, a shell command, git's own work or a merge stopped on a conflict included, and is logged as approved with `deletion` as its way of approval, because deleting a guarded-file needs no approval from the user; every other change, a rename or move included, is handled as the rest of this section says (user-ruled 2026-11-05, item 8 of the approval-walk `ned-box-helper-push-program-design-points-2026-11-03`, whose walk-minutes are `nedlern@ned-box:/home/nedlern/agents/ned-box-helper/docs/walk/ned-box-helper-push-program-design-points-2026-11-03-minutes.md`).

While a rebase, merge, cherry-pick or revert is in progress, the hook still copies every new version, so no intermediate resolution is lost, but asks nothing, using the check the function `git_operation_in_progress` in `.claude/guard-hooks/session-location-write-guard.py` already makes. A rename that leaves the content unchanged is settled (user-ruled 2026-10-12): when one run sees a path disappear and a new path appear with the same content, and that content was in the old path's approved set, it adds that hash to the new path's approved set, and the old path's disappearance is settled. A rename of content that was not approved is a change to ask about at its new path, so a `mv` cannot approve a version; the old path's disappearance is settled as a deletion, item 6. Approval is per path: approving a version under one path does not settle another path holding the same content. A deleted file's content is recorded as the reserved hash `deleted`, in `approved` and `log` only, with no copy, which the approve and restore commands accept like any other: `--restore` of a deletion puts back the newest approved content. A file deleted and then written again is compared with, and restored to, the newest approved content from before the deletion, every `deleted` passed over: written again as it was, it is settled; written again differently, it is asked about against that content, unless another way of approval in this section settles it (user-ruled 2026-11-05, item 10 of the approval-walk `ned-box-helper-push-program-design-points-2026-11-03`). Declining a new file whose path has no approved content copies the new file into the backup directory and then deletes it. Every deletion of a guarded file is settled, item 6. When a conflicted operation is aborted, the files return to versions already approved, so they are settled, and the copies made during the conflict stay in the backup directory.

### What it does when a file changes

At every run, for each checked file whose content differs from its content at the previous run:

1. It copies the new version into the backup directory, whether or not the version is approved, so that every version a run sees is kept, approved uncommitted Edits included.
2. If the new version's hash is not in the path's approved set, it tells the agent, through `additionalContext`, in one message for all the files one tool call changed, which file changed and that the user has not approved it, and, each on its own line with its condition:
   - show the user the change (the hook gives the diff against the newest approved version, at most 40 lines and 4,000 characters, and the version's hash) and ask him;
   - if he approves, write his words into the marker file `.walk-approved` at the top of the session's checkout, as the instruction-file guard's marker is written, and run `python3 <the hook program> --approve <path> <hash> [<path> <hash> ...]`, with the hook program's full path as the message gives it, so the command works from any directory of the session's checkout, where it reads the marker file, once, naming every file he approved, which adds each hash to its path's approved set and then spends the marker file by deleting it; each `<hash>` is the one the hook's message gives, the hash the approved set holds, which for a file under a line-ending filter is git's blob id, not the hash of the file's bytes; a file he declined goes to `--restore` below, which needs no marker file; it refuses when the file's content is no longer that hash, so a version he was not shown is never approved, refuses an obvious-fix marker written after the hook first saw the version, as the paragraph after this list says, and refuses when it cannot write to the backup directory;
   - if the agent wrote an obvious-fix marker before making the change, run `--approve` without asking the user, as the project glossary's entry obvious-error-fix says;
   - if he declines, run the same program with `--restore <path> <hash> [<path> <hash> ...]`, which for each file first copies the file's current content into the backup directory, refuses unless that content is still the hash he declined, and then puts back the newest approved version from the backup directory, or, when the path has no approved version, deletes the file and records its deletion as approved; and, if the declined version is in a commit, the agent adds a commit on top that holds what `--restore` left, with the command the hook's message gives and `--restore` prints again when HEAD holds the declined version, `git commit --only -m "Put back the approved <file name>" -- <path>`, with the file's name in the message and its full path after `--`, which commits that one path whatever else is staged or changed;
   - for each file whose path has no approved version, that origin/main does not hold in any version, and whose version the backup directory holds a copy of (it holds none of a version that HEAD's commit held when the hook first saw it, as § What is built says of PR [Guarded-file store keeps only versions git does not hold, and the daily prune deletes copies a commit holds](https://github.com/nedsnodes/nedsnodes/pull/1707)), the hook offers `rm -- <path>` with that file's path, in its ask and in each reminder, on a line above the one that tells a subagent to stop: any agent, a subagent included, deletes a file that should not exist, such as one it made by mistake or only for its own notes, without asking anyone and with none of the other steps, since deleting it loses no version the user approved and needs no approval, and the hook records the deletion after the `rm`'s own tool call;
   - a subagent that does not delete the file as the item above offers, because the hook offers no `rm` for it or because the file should exist, reports the change to the agent that dispatched it instead of asking the user.
3. The session whose run first saw the version is named in the backup directory's log as the one to ask. After every later tool call in that session, while the file is not settled, the hook repeats a one-line reminder naming the file. Any other session that checks the file gets the reminder once, and the log records each session reminded. A subagent's tool calls name its parent's session as the asking session, since the subagent reports to the agent that dispatched it; the build confirms that the hook's input carries the parent's session for a subagent's call. A successor after a handoff is a new session in the same checkout; when the log's asking session has ended, the first session to see the unsettled file is logged as the new asking session, asks, and is reminded after every tool call from then on. How the hook tells that a session has ended is chosen in the build.

**An obvious-fix marker approves only a change it came before** (user-ruled 2026-10-14, item 7 of the approval-walk `open-decisions-unpushed-branches-memory-claude-md-root-cause-and-cold-read-2026-10-14`). `CLAUDE.md` lets an agent fix an obvious error in a guarded file without asking the user, after writing an obvious-fix marker. `--approve` accepts an obvious-fix marker only when the marker was written before the change it approves; a change the hook found before the marker was written goes to the user, and `--approve` refuses, telling the agent to show him the change and ask him. Without this rule, an agent whose shell command changed `CLAUDE.md` by accident could write an obvious-fix marker after the hook caught the change and approve the accident, and no question would reach the user. The hook compares two times: the marker's modification time, and the time in the first line of the path's `log` that records the version's hash, which is when a run first saw that version. It accepts the marker only when the marker's modification time is the earlier of the two; equal times count as the marker coming after, so the change goes to the user. Both times come from the clock of the machine the session runs on: the marker is in the session's checkout, and the hook writes the time into each `log` line itself, on the Mac as on ned-box.

The user's own edit in an editor is handled the same way (user-ruled 2026-10-11): the hook cannot tell his editor from an agent's `sed`; since nothing is put back without his no, his edit is not lost.

`~/.claude/settings.json` is written by Claude Code itself when the user picks a model with `/model` or changes a setting with `/config`, outside any tool call. The hook compares only its keys that change what hooks and tools may do, `hooks`, `disableAllHooks`, `permissions` and `env`: for this file the hash in the approved set is the hash of those four keys, so a model choice is not asked about; every version of the whole file is still copied (user-ruled 2026-10-12).

### The backup directory

Each machine has one backup directory, and both are in the log-store on ned-box, in its kind `guarded-file-backups/`, laid out as `transcripts/` is, one subdirectory per machine (user-ruled 2026-10-12: "we use ned-box as the backup drive"; the backups follow the log-store mirror's layout):

```
/home/nedlern/nedsnodes-logs/guarded-file-backups/mac/<full path on the Mac, without its leading slash>/<hash>
/home/nedlern/nedsnodes-logs/guarded-file-backups/ned-box/<full path on ned-box, without its leading slash>/<hash>
```

ned-box's hook writes to `guarded-file-backups/ned-box/` directly. The Mac's hook writes to `guarded-file-backups/mac/` over the mount, as `/Volumes/nedhome/nedsnodes-logs/guarded-file-backups/mac/`, at the moment it sees a change; there is no copy on the Mac, no queue and no copier (user-ruled 2026-10-13). The machine name is taken from the transcript mirror's function `this_machine_name`. The directory mirrors each file's full path as that machine sees it, since every `CLAUDE.local.md` has the same name, so the Mac's own `~/.claude/CLAUDE.md` and ned-box's never collide. Under each path's directory:

- one copy of each version, named by its content hash and created with `O_CREAT|O_EXCL` and mode `0600`, so a copy that exists is never replaced, even by an identical one; because the name is the hash, a reader checks a copy against its name, and a copy that does not match, left by a write cut off part way, counts as missing and is the one file the hook may replace; copies are never otherwise changed or deleted by the hook, and how long they are kept is decided in the build (user-ruled 2026-10-11);
- `approved`, the path's approved set, one hash per line, appended to and never rewritten;
- `log`, one appended line per version seen: the time, the session, the hash, and how it entered the approved set, if it did; one line per other session reminded; and one line naming each new asking session after a handoff.

Nothing in the directory is ever rewritten, only added to. A line is appended to `approved` or `log` in one write with `O_APPEND`, and each line ends with a checksum of the line, so a line a cut-off write left incomplete is recognised: a reader skips it, never reads it as an approval, and a writer that finds the file not ending in a newline writes a newline first. The hook checks that each write wrote every byte, and treats a short write as a failure. Two sessions on ned-box append to a local file, where each `O_APPEND` write lands whole at the end; two sessions on one Mac append through the same mount, whose client orders appends to one file; sessions on different machines write different subdirectories.

**When the Mac cannot reach the store.** Before it touches the store, the Mac's hook checks that `/Volumes/nedhome` is an SMB mount of ned-box's home share and that `/Volumes/nedhome/nedsnodes-logs/guarded-file-backups/mac/` exists, then opens that directory and does every later read and write relative to the open directory, so that a mount that disappears part way makes the operation fail instead of landing on the Mac's own disk under an empty `/Volumes/nedhome`; it creates directories only below `mac/`. A mount that is still listed while ned-box has gone can make a read or write wait for SMB to reconnect, so the hook does every operation on the store in a child process with a deadline shorter than the hook's timeout in `.claude/settings.json`; at the deadline the hook kills the child and reports the failure, and the child records an approval or puts a version back only as its last step, after checking the deadline has not passed.

When a check fails, an operation fails, or the deadline passes, the hook tells the agent through `additionalContext` that the backup failed and that the change could not be checked against the approved set, with a remedy the user can act on, such as checking that ned-box is up and that the Mac has mounted its share, which `CLAUDE.md` asks the agent to pass on to him, and exits 0. Nothing is queued and nothing is reverted, so the file stays as it is. The hook advances a file's stored stat data, and a checkout's stored reflog position, only after every step for that file or checkout has succeeded: the copy, the approval check, the log line and the naming of the asking session. A run that fails part way therefore leaves the file looking changed, and the next run that reaches the store does the whole check on the file's content then, whether or not the file has changed again. `--approve` and `--restore` read and write the store too, and refuse while it cannot be reached.

What an outage loses, as the user's ruling to keep no copy on the Mac accepts (user-ruled 2026-10-13):

- a version that came and went while the store could not be reached is never copied: if a file goes from A to B to C during the outage, only C is copied, once the store is back;
- while the store cannot be reached, the user's yes cannot be recorded and no version can be put back, even one backed up before the outage;
- the reminder for each unsettled file is replaced by one warning that the store cannot be reached, since the approved sets are in the store;
- an Edit approved through the instruction-file guard during the outage is not recorded as approved, because its approval is recorded only by the hook run straight after it; its version is asked about once the store is back.

How long versions are kept is decided in the build (user-ruled 2026-10-11).

The directory is outside every checkout and outside `~/.claude/`, where the guard would protect its files. A checkout's own stored stat data and reflog position are kept in that checkout's git directory (`git rev-parse --git-dir`), and the stat data of the files outside every checkout in `~/.cache/guarded-file-change-without-approval-backup-and-ask-hook/` on each machine.

### When something fails

If the hook cannot write a copy, read the backup directory or run git, it exits 0 and tells the agent through `additionalContext` what failed and that the change is not backed up; `--restore` refuses while the current version cannot be copied. On the Mac, an unreachable ned-box is one such failure, handled as "When the Mac cannot reach the store" above says.

### How this sits beside the existing backups

The fleet already keeps histories that `scripts/find-deleted-path-across-backups.py` searches: git, including the work-snapshot refs, Timeshift snapshots of ned-box (hourly, daily, weekly and monthly, per `/etc/timeshift/timeshift.json`), and Time Machine on the Mac. A work-snapshot (`nn-systems/handoff/uncommitted-work-snapshots.py`, written after every Edit, Write, NotebookEdit and Bash call by `scripts/uncommitted-work-snapshot-hook.py`) is a git commit under `refs/work-snapshots/<owner>/<worktree>` holding the latest uncommitted changes of one worktree for one `claude` process, so that they outlive a crash.

`scripts/transcript-mirror-to-log-store.py` copies, every minute on each machine, the latest version of each agent-seat's seat-brief (`~/agents/<seat>/CLAUDE.local.md`) and of `~/.claude/CLAUDE.md` to `transcripts/<machine>/seat-briefs/<seat>/CLAUDE.local.md` and `transcripts/<machine>/CLAUDE.md` in the log-store, and never deletes there.

None of them can be the backup directory:

- Timeshift and Time Machine copy on a timer, so a version that lived for ten minutes may be in neither; they record no approval; and agents may not write backup state (`.claude/guard-hooks/backup-and-snapshot-write-guard.py`).
- A work-snapshot keeps only the latest uncommitted state per process and worktree, leaves out files git ignores, `CLAUDE.local.md` among them, and covers no file outside a checkout.
- The mirror keeps only the latest version of two of the guarded files, a minute late, so a version can be overwritten before it is copied; and it records no approval.

The backup directory is the same idea at a finer grain: a copy at each change of a guarded file, with the approved versions named. ## Known gaps

- **A background write after the last tool call** is not noticed until the next tool call that checks the file.
- **Versions overwritten within one tool call:** only the last version is copied.
- **An unapproved change in effect while the user is asked:** an agent follows a changed skill or `CLAUDE.local.md` until the user answers; a change to `.claude/settings.json` made by a shell command can switch hooks off, this one included.
- **An unrelated change staged during a conflicted merge** is committed with the resolution and approved as git's own work, when no run saw the change before the commit.
- **A conflict resolved inside one shell command** leaves no stopped state for a run to see, so its merge commit is asked about.
- **An unapproved commit rebased over a main that changed the same file** can come out as a version that git's own work then approves.
- **A new worktree created from a branch holding an unapproved commit** stocks that commit's versions as approved.
- **A write into another checkout** is noticed only when an agent-session runs there, unless it is an agent-seat file of § Which files it checks, which every hook run checks. A subagent's worktree under `.claude/worktrees/` may never have an agent-session of its own: the hook checks the checkout of the hook payload's `cwd`, and a subagent whose `cwd` is its agent-seat's agent-home reaches the worktree only by `cd` inside each shell command, so no run of the hook checks that worktree. This happened on 2026-11-21, as the provisional addition of that date by ned-box-helper says.
- **A Codex session** runs no Claude Code hooks; its write is noticed at the next tool call of a Claude Code session that checks the file.
- **A push before the user answers** sends the unapproved version to other machines and merge-lane-2 as git's own work.
- **User-level files under `~/.claude/`** other than the two listed are not checked.
- **A ned-box file reached from the Mac through `/Volumes/nedhome`** by a Mac session is kept in the Mac's backup directory under its `/Volumes/nedhome` path, with its own approved set, so a version approved on ned-box is asked about again there. Mac sessions work in the Mac's own clones, so this is rare.
- **An obvious-fix marker written after a change in the same tool call** counts as written before the change, since the hook first sees the version at the end of that tool call.
- **The hook's own file:** a shell command that deletes or breaks the hook stops it.
