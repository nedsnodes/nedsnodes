# Move six steps the terminology cold-read-cell's reviewer does by judgment into the program that runs it

The terminology cold-read-cell is the reviewer, in a cold-read-full-run, that reports the terms a document uses that no glossary lists, or uses in a sense other than the one its glossary gives. Its prompt is `.claude/skills/cold-read/prompts/terminology-prompt.md`. In this GHI-MD, the terminology runner is the code that launches that reviewer and checks its answer: on main, `nn-systems/cold-read/cold-read-claude-cell.py` and `nn-systems/cold-read/cold-read-codex-cell.py`, with what they share in `nn-systems/cold-read/cold-read-cell-common.py`. Pull request [The terminology cold-read-cell answers in JSON, and the runner checks the answer against its schema and rules and makes the glossary lookups](https://github.com/nedsnodes/nedsnodes/pull/3957) adds to the terminology runner the module `nn-systems/cold-read/cold-read-terminology-answer-rules-check-glossary-lookups-and-report-render-common.py` and the page of rules it checks, `nn-systems/cold-read/cold-read-terminology-answer-rules-the-runner-validates-beyond-the-schema.md`. On 2026-11-22 that pull request was open and approved, at nn-head-commit a4eec4181, and not yet merged; neither file is on main until it merges.

Six steps that the prompt leaves to the reviewer need no judgment. Each is a list, a lookup or a string match, so under code-prompt-code, as `CLAUDE.md` and the project glossary define it, each moves into the terminology runner. Pull request 3957 does none of the six: its terminology runner looks glossary entries up after the review, not before it, and checks only what the reviewer chose to report.

## The six steps

1. **Code lists the candidate terms, and the reviewer judges each.** Before the review, the terminology runner lists the frozen-copy's headings, its table header cells, its hyphenated phrases, and every glossary term it uses, and gives the list to the reviewer, whose answer gives each candidate a verdict: flagged, or kept, which means not flagged, ordinary words included. A candidate with no verdict is a missing verdict, which the terminology runner reports. The reviewer may still flag a term the list lacks, such as an ordinary word made quietly technical in the body text, since no list of headings and phrases finds those. Today the prompt tells the reviewer to find the terms itself ("Look where the document sorts things, in column and heading names, in a rule's condition"), so a term the reviewer misses leaves no trace in the answer. In pull request 3957, `key_terms` is still the reviewer's own list.
2. **The terminology runner searches for a name a proposed project-term would clash with.** When the reviewer proposes a new project-term, as fix (d), the terminology runner searches the checkout and origin/main for that name, as the searches of `docs/nedsnodes-wiki/nedsnodes-how-to-choose-a-name-for-files-code-and-glossary-terms.md` do, and marks the proposal as clear or as clashing with the match it names; a clash is marked under the flag, as the terminology runner marks a broken rule, and does not reject the answer. The naming page gives those searches only as commands in prose, so one shared program that runs them for a name, called by the terminology runner, keeps the two from drifting apart. Pull request 3957's prompt tells the reviewer to build the name "without running that page's searches", and its terminology runner checks a fix (d) only for a hyphen and against the glossaries; a search of its added lines for `git grep`, `ls-tree` and `origin/main` finds none in that check.
3. **Code confirms a better term the reviewer says the document uses elsewhere.** When the reviewer gives fix (c), a term the document already uses elsewhere, the terminology runner confirms that the term occurs in the frozen-copy, and marks the flag when it does not. Pull request 3957 confirms that a fix (a) names a glossary term and that each quotation is found in the frozen-copy; none of its rules, and none of its added lines, test the words of a fix (c).
4. **Code rejects a finding that proposes renaming a glossary term.** The prompt says "do not propose a new name for one, since renaming a glossary term is the user's decision, made in the glossary", and no rule of pull request 3957 enforces that sentence. A flag on a glossary term that a passage misuses may rightly propose other words for that passage, which renames nothing, so code cannot tell the two apart from the fix's words alone. One way: the answer schema gives each fix on a glossary term a required field whose value is either that it rewords this passage or that it renames the term, and the terminology runner treats every fix that renames the term as a broken rule, as its rules page treats the others: marked under the flag, and counted toward rejecting the whole answer.
5. **The terminology runner pastes the glossaries into the prompt.** The terminology runner puts the text of the project glossary, and of every system glossary it lists at its top, into the prompt, so the reviewer cannot skip reading them. Today, and in pull request 3957, the prompt only tells the reviewer to read them before the document.
6. **The terminology runner runs `git ls-files` for each bare file name.** For each bare file name in the frozen-copy, such as a name in backquotes that holds no `/` and ends in a file extension, which the pull request that builds this step defines exactly, the terminology runner runs `git ls-files` and gives the reviewer the result: no tracked file, the one tracked path, or the several. A bare `git ls-files <name>` matches only at the top of the repository; `git ls-files ':(glob)**/<name>'` matches at any depth, as `git ls-files ':(glob)**/cold-read-grid.py'` prints `nn-systems/cold-read/cold-read-grid.py` where `git ls-files cold-read-grid.py` prints nothing. Pull request 3957's prompt tells the reviewer it "may search for with `git ls-files`" a bare file name, which leaves both the search and the pathspec to the reviewer.

Steps 1, 4 and 6 change what the reviewer is given or answers, so the pull request that builds each also changes `terminology-answer-schema.json`, which pull request 3957 adds under `.claude/skills/cold-read/prompts/`, and the prompt's description of the answer.

The cold-read-cell that proposed the six, described under "Where the six come from", also proposed catching near-miss spellings by edit distance, and other word forms such as tenses. Neither is in this GHI: no miss of either kind has been recorded.

## Why

A step left to the prompt can be skipped without trace: the reviewer's answer looks the same whether or not it read the glossaries, searched for a clashing name, or looked at every heading. A step in code runs the same way each time and can be tested. `CLAUDE.md` says: "a step that needs no judgment, such as sequencing, state, validation or a retry, goes in code, never in a prompt." With the six in code, the reviewer's judgment goes only to what needs it: whether a candidate is a term, what it means, and which fix fits.
