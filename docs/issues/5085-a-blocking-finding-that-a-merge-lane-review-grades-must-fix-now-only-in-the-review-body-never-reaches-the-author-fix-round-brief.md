# A blocking finding that a merge-lane review grades must-fix-now only in the review's body never reaches the author's fix-round brief

## What happened

On PR [Merge queue: the dead-batch check is made under its lock and keeps the merge program's stop file, failed stop writes exit 1, and the resume command names the directories in use](https://github.com/nedsnodes/nedsnodes/pull/4988), the commissioned Claude reviewer, mac-claude, posted round 1's review [6069321503](https://github.com/nedsnodes/nedsnodes/pull/4988#pullrequestreview-6069321503) with one finding: "The FAILED line says something false when the stop file is written but the stopped notice is not", because `stopped()` removes the in-progress file before it writes the notice. Its inline comment does not open with the mark `**Blocks**`. merge-lane-1's round 1 review [6069428694](https://github.com/nedsnodes/nedsnodes/pull/4988#pullrequestreview-6069428694) graded that finding must-fix-now, the one of the four finding categories in `docs/agents/pr-reviewer-instructions.md` that blocks the merge, in its body only: the body says "Three findings block: the head test run fails on Ruff F541, mac-claude's finding on the FAILED line, and Codex 7c142b4392b0", and the count line above the body, which `scripts/merge-lane-pull-request-reviewer-review-post-and-read-back.py` writes from the comments, says `**Blocking: 1**`. The one inline comment that opens with `**Blocks**` is Codex finding 7c142b4392b0's. merge-lane-1's review file, `nedlern@ned-box:/home/nedlern/nedsnodes-logs/seats/merge-lane-1/review-4988-r1.json`, has seven comments, one of them must-fix-now, and none for mac-claude's finding or for the Ruff F541 failure. The author's fix-round did not answer mac-claude's finding. merge-lane-1's round 2 review [6071010042](https://github.com/nedsnodes/nedsnodes/pull/4988#pullrequestreview-6071010042) found the defect still unfixed, posted it inline as must-fix-now, and says: "Round 1 graded mac-claude's finding on the in-progress file (review 6069321503) must-fix-now in the review body, but posted no inline comment for it, so the fix-round brief did not list it." The same round 1 body graded the Ruff F541 head test run failure must-fix-now with no comment either; the author fixed that one anyway, and round 2 records it fixed. The missed finding cost one fix-round and a second full review round, Codex review cell, mac-claude and head test run, before the defect could be fixed.

## What is wrong

The fix-round program, `scripts/pull-request-fix-round-author-brief-from-blocking-findings-and-one-commit-every-finding-answered-check.py`, builds the author's brief only from the round's inline comments that open with a match of its `BLOCKING_MARKER_PATTERN`, and from the comments the posting program moved into a review's body under `OUTSIDE_THE_DIFF_HEADING`. Its docstring says "the bodies' other free text is never parsed for findings". When a merge-lane review in the round has its own marked comments and states a `**Blocking: N**` count, only that merge-lane's marked comments block, so a commissioned reviewer's comment would not reach the brief even if it carried the mark. Reading findings only from marked comments is the program's rule, and it is the right one; the defect is upstream of it.

The posting program, run with `--github-account ned-review-merge`, which every merge-lane uses to post its verdict review, takes the merge-lane's review file, which its docstring calls merge-lane-2's review file, "which restates every finding the round's reviewers raised", as its docstring says, and enforces that restatement for Codex findings only: the file's `merge_lane_codex_review_finding_grades` must grade every Codex finding on the commit, and the program refuses any grade other than does-not-hold when no comment whose `finding_category` is that grade names the finding, with the message `CODEX_GRADE_WITH_NO_COMMENT`, because "the programs that act on such findings ... read findings only from comments". Nothing in the posting program reads the commissioned Claude reviewer's findings or the head test run's outcome, so a grade of either can be written in the body alone, and the review posts with a count that leaves it out. A search of the posting program on origin/main `e8acdd275d6c` for `mac-claude`, `commissioned` and `head test` finds only the code that posts mac-claude's own review and reads mac-claude's token.

ghi-guide-agent, asked with `--include-closed` on 2026-11-26, found no open or closed GHI that covers this. Neighbouring GHIs: [Post every merge-lane-2 review through one program, and refuse a merge whose verdict review lacks that program's marks](https://github.com/nedsnodes/nedsnodes/issues/3891), about reviews posted without the posting program at all; [Pull requests, their reviews and approval-walks held as one state machine over one schema and one store](https://github.com/nedsnodes/nedsnodes/issues/2505), which would hold each review's findings as fields; and [One shared list of the kinds of check failure, used by reviewers, authors and test writers, and a daily check that each kind is handled the same way](https://github.com/nedsnodes/nedsnodes/issues/3968), which makes a failing test case in the head test run a must-fix-now finding and changes the marks the posting program writes.

## What to do

The cause is that the review file can state a blocking finding in the body's prose, which no program reads, and the posting program requires a comment only for Codex findings. The agent-seat overall-cleanup, which wrote the posting program's Codex grade check in commit `ff9a6b261`, makes the posting program require a comment for every blocking finding it can find for itself:

- The commissioned Claude reviewer's findings. When the review plan's tier for `--head-commit` runs the Claude reviewer, the posting program refuses until the Claude reviewer's review of that commit exists, as the Codex check refuses until the Codex review cell has run, and reads its findings: the inline comments of every such review, including any the posting program moved into its body. The review file grades each in a new list, such as `merge_lane_claude_review_finding_grades`, built like `merge_lane_codex_review_finding_grades`; the program refuses a finding with no grade, a grade for no finding, and any grade other than does-not-hold when no comment whose `finding_category` is that grade names the finding. The builder chooses how a comment names a Claude reviewer's finding, such as by its GitHub comment id. The refusal messages say what to add, as `CODEX_FINDINGS_NOT_GRADED` does, so no instruction file needs to change.
- A failing head test run. When the tier runs the head test run and that run failed on `--head-commit`, the posting program refuses a review file with no must-fix-now comment naming the failure. The Ruff F541 failure above was such a case. Where the posting program reads the head test run's outcome is for the builder to find (unverified that a record it can read exists). GHI 3968 classifies failing test cases into kinds; this check needs no classification, and GHI 3968 may later narrow it.

Reuse the Codex check's code and messages, and add no second reader of findings to the fix-round program. Add test cases to `scripts/merge-lane-pull-request-reviewer-review-post-and-read-back-test.py` for: a Claude reviewer finding with no grade; one graded must-fix-now with no comment naming it; one graded does-not-hold with no comment, which posts; one graded and named by a comment, which posts; no Claude reviewer review on the commit at a tier that runs one; and a failed head test run with no must-fix-now comment.
