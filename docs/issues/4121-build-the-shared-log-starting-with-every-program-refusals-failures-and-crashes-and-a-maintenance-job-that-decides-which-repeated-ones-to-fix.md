# Build the shared-log, starting with every program's refusals, failures and crashes, and a maintenance-job that decides which repeated ones to fix

Build the shared-log, which the project glossary defines as "the one log that every program on a machine writes to through Python's logging, one JSON line per event, copied to the log-store". The first events it carries are the mistakes programs already see: each time a Python program in this repository refuses an agent's action, prints FAILED, or crashes, it sends one log event. A new maintenance-job of GHI [Regular maintenance: the list of maintenance jobs, how often each runs, and how each reaches the user](https://github.com/nedsnodes/nedsnodes/issues/1058) reads those events, groups them by program and reason name, and decides for each group: do nothing, fix, or cause not found. A fix reaches the user only when `docs/nedsnodes-wiki/nedsnodes-which-changes-need-the-users-approval.md`, the approvals page, says the change needs his approval. The next action is the comparison with existing logging tools under "Next action", which the first build-slice waits for.

## Why

Today a program that sees a mistake handles that one instance, and no record collects such mistakes in one place. A hook refuses an agent's misstep, such as committing with uncommitted changes left behind, and its tool-message-to-agent tells the agent how to correct it; a program prints FAILED for a failure outside the agent, which the agent reports; a program with a defect crashes. Some programs append them to a log file of their own, and GHI 1058's section "How scheduled jobs report failures (decided)" has a maintenance-job read the logs of scheduled jobs; but most refusals are written nowhere, and no maintenance-job reads all three kinds together, so nobody sees which mistakes keep happening, or what causes them.

Either agent instructions are not timely or not clear or should be, should use more code prompt code and less prompt to make them reliable. ... And in the case of mistakes, we need a primary correction mechanism." He then approved item 2.6.1 with "a": write this GHI-MD now, and continue that approval-walk. ## What to build

### 1. The event format

Each event is one JSON line holding: a UTC timestamp to the microsecond; the machine; the agent-seat and the agent-session, where the program knows them; the program's path in the repository; the kind of event; a reason name; its tags, as hashtags with underscores; and the message. The kinds this GHI adds are `#refused`, `#failed` and `#crashed`. The reason name is fixed text chosen once at each place in the code that refuses or fails, such as `#uncommitted_changes_left_behind`, so that two events from the same cause carry the same reason name whatever paths or names fill the message. A long document is never put in an event: the event holds the document's path.

### 2. One listener per machine, writing only to its own disk

Each machine's listener writes the machine's daily file on that machine's local disk, never over the SMB share through which the Mac mounts ned-box's home directory at `/Volumes/nedhome`. On ned-box the daily file is written inside the log-store. On the Mac it is written on the Mac, and a scheduled job copies it to the log-store, as `scripts/transcript-mirror-to-log-store.py` copies transcripts. So no program on the Mac ever needs ned-box to log an event: when ned-box cannot be reached, events go on being written to the Mac's file, and the next copy that reaches ned-box carries them. The listener alone formats JSON with python-json-logger, which joins `nn-systems/general-tools/python-libraries-pinned-requirements.txt`. Programs send events through the standard library's `logging.handlers.SocketHandler`, which is in the standard library of every Python the hooks may run under, the Mac's system Python 3.9 among them, so a program needs no extra library to log. `SocketHandler` drops an event without a word when it cannot connect, and after a failed connection it does not try again for up to 30 seconds, so the module of step 3 detects the failed send itself and prints the one stderr line the user decided on; the listener is on the same machine, so a connection it refuses fails at once and does not hold the program up.

### 3. One module that sends an event, and prints the message with it

A new -common module, named at build by the naming page, `docs/nedsnodes-wiki/nedsnodes-how-to-choose-a-name-for-files-code-and-glossary-terms.md`, gives programs one call that puts the tool-message-to-agent where the agent reads it, such as a hook's `deny` JSON or a script's printed lines, and sends the matching event, so that the message and the event cannot drift apart. A second call writes a long record as a file and sends its "report written" event, for step 6. Loading the module also installs a `sys.excepthook` that sends a `#crashed` event, with the exception and the file and line it was raised at, before Python prints the traceback; it catches only programs that load the module, which step 4's nn-test-suite makes every Python program with a `__main__` entry do. How this crash event fits the top-level catch the exit-code page requires is Deferred-decisions item 8.

### 4. Every refusal, FAILED and crash sends an event

Each Python program is moved to the module: every refusal and every FAILED line goes through the module's call, and every program loads the module, so its crashes send events. Shell scripts follow once Deferred-decisions item 1 is settled. An nn-test-suite reads the source of every Python program git tracks and fails when one of three things holds: the program holds the text REFUSED or FAILED, a `deny` decision, a Stop hook's `block` decision, or a hook's exit 2, outside the module's call; the program has a `__main__` entry and does not load the module; or a reason name passed to the call is not a fixed string of the form `#lowercase_words_with_underscores`, such as an f-string, which would split one cause into many groups.

### 5. The maintenance-job that decides on the groups

A new daily maintenance-job of GHI 1058. As GHI 1058's section "How the maintenance jobs run each night, and how often (decided)" requires, the job's program does every step that needs no judgment, and starts a model only for the one step that needs judgment, called the model step below.

Code:

1. Reads every daily shared-log file of both machines in the log-store that the job has not yet read, so a Mac file copied late, after the Mac slept, is read on the next day's job. When yesterday's file of a machine is missing, the job says that machine was not checked that day, because either no program sent an event or the listener or the Mac's copy did not run, and never reports it as a day with no mistakes, as GHI 1058's section "How a daily job reads the Mac (decided)" requires.
2. Groups the `#refused`, `#failed` and `#crashed` events by program and reason name, and counts each group by day. For each group it also works out whether the count over the last 7 days is higher than over the 7 days before, and how often the same agent-session met the same group again within an hour, a sign that the tool-message-to-agent did not help the agent correct the mistake.
3. Lists each group not yet decided. A decided group is listed again only when one of these holds: its count over the last 7 days is higher than its 7-day count recorded at its latest decision; it was decided "fix" and its fix's pull request closed without merging, or it had an event in the 14 days after its fix merged; it was decided "cause not found" 7 days ago or more; or 8 weeks have passed since its latest decision and it had an event in those 8 weeks, in which case the listing carries its 8-week total. The job writes the listed groups, with the figures of step 2, in its report file in the maintenance report directory of GHI 1058.
4. For each listed group, picks a sample of its events and copies, from each event's agent-session transcript, the lines around the event's time, for the model step to read.
5. Reads the time of the shared-log's earliest event. On the job's first day 30 or more days after that time, it queues, once, the question "Should agents also log mistakes that no program catches?" for the nightly overseer's approval-walk, and keeps a mark in the file of decided groups, so that the job never queues it again.
6. When no group is listed, writes the report file and stops: no model step starts and no question is queued.

The model step, for each listed group: read the sample and the transcript excerpts, find the cause, and answer "do nothing", with the reason; "fix", with the cause and the change that fixes it, as a diff; or "cause not found", with what was looked at. The model step returns its answer to the job's code and opens no pull request itself. Code checks the answer for one of the three forms before it uses the answer, and refuses "do nothing" for a group of `#crashed` events.

Code again: it records each decision with the group's program, reason name, 7-day count and date, and for a fix the pull request, in the file of decided groups the job keeps in the log-store, so that code step 3 knows when to list the group again. The three answers:

- **Do nothing:** the program caught what it exists to catch, the agent corrected it, and the count is not rising; for example, a guard that refuses a hand-typed command and names the program to run instead.
- **Fix:** code commits the change on an nn-topic-branch and opens a pull request, whose description carries a `#root_cause` line built from the answer's cause. When the approvals page lists the change as needing the user's approval, code opens the pull request as a draft whose description asks the question, as the approvals page's section "How to ask, and how to make a change" requires, and queues the question, linking the draft, for the nightly overseer's approval-walk.
- **Cause not found:** recorded and listed again by code step 3; not shown to the user.

When the cause is an instruction an agent missed, the fix follows the user's words above: give the agent the instruction at the moment it acts, by the rule of GHI [Save each lesson where agents meet it at the moment it applies, and decide whether a store that recalls lessons by subject is worth building](https://github.com/nedsnodes/nedsnodes/issues/1349), or move the step into code, as code-prompt-code.

### 6. Existing logs and records become events

As the first design of 2026-10-16 proposed, each existing log in the supporting document's table moves to the shared-log, one program per pull request, and each record the log-store keeps as a file gets a "report written" event through the module's second call. An nn-test-suite holds the list of programs that still write a log file of their own and fails for a program not on the list; each pull request of this step removes its program from the list.

## Deferred-decisions

1. **Shell scripts.** How a `.sh` program sends an event, such as through a small command the module provides; decided at build.
2. **How the agent-seat and the agent-session reach the event.** A hook receives the agent-session's identifier in its input; how a script run by an agent learns them is decided at build.
3. **How many events the job's code samples per group, and how far back the job reads** when a group's count rises; set on the first weeks of reports.
4. **How long daily files are kept** on each machine after they are copied, and in the log-store.
5. **Threads.** `sys.excepthook` catches only a crash on a program's main thread; whether a program that runs threads also needs `threading.excepthook`, decided at build.
6. **When a `#refused` group is first listed.** A `#crashed` or `#failed` group is listed from its first event; whether a `#refused` group waits for a few events before it is listed, set from the first weeks of reports.
7. **Where the file of decided groups lives** in the log-store, named at build by the naming page; and the cases item 2.7.4's fast reads left to this GHI-MD: a fix whose pull request is still open, which 7-day count a group is compared with after it is listed again, and where each window of 7 days, 14 days and 8 weeks starts and ends.
8. **The crash event and the exit-code page's top-level catch.** A program that follows the exit-code page catches its own crash, so `sys.excepthook` never sees it. Open: whether the shared top-level catch of GHI 2476 sends the `#crashed` event through this GHI's module, with `sys.excepthook` kept only for a program that has no such catch.
9. **The reason name of a crash event,** which `sys.excepthook` cannot be given at a call site, such as one built from the exception's type and the function it was raised in; decided at build.
10. **How programs reach the listener and where the files are:** the listener's address and port, the text of the one stderr line, and the directory and file names of each machine's daily files; named at build by the naming page.
11. **What step 4's nn-test-suite leaves out and adds:** test suites, docstrings and the module itself, which hold REFUSED and FAILED without refusing; a reason name kept in a module-level constant; whether one reason name passed at two call sites of one program fails the test; and the list of programs not yet moved, which only shrinks while step 4 is built.
12. **How step 6's nn-test-suite recognises a program that writes a log file of its own,** and which build-slice sends an event for each walk-minutes row, from which program.
13. **How the job remembers what it has read, and what code does after a refusal:** whether it reads a file that is still growing from a line offset; where it keeps the counts the 7-day, 14-day and 8-week tests need; and what code does after it refuses an answer, such as "do nothing" for a crash group, and when it records the user's answer to the 30-day question.
