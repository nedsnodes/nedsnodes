# The GHI-MD whole-file replacement soft-block lets a replacement through when main has not changed the GHI-MD since the merge-base

## What happens today

`.claude/guard-hooks/ghi-md-whole-file-replacement-soft-block.py` refuses a Write tool call, or a Bash `cp`, `mv`, `tee` or truncating redirection, that writes over an existing GHI-MD, a `docs/issues/<number>-*.md` file, with the refusal `[rule bash-guard-ghi-md-whole-file-replacement]`. The agent clears the refusal by writing a reason into the marker file `.ghi-md-whole-file-replacement-reason` at the root of its checkout and running the command again. The refusal exists because a whole-file replacement puts the agent's copy over every change merged into the GHI-MD on `main` after that copy was written; PR [Soft-block whole-file replacement of an existing GHI-MD; /ghi-write says to carry over only your own changes](https://github.com/nedsnodes/nedsnodes/pull/2196) added it after an agent, on 2026-10-27, copied a GHI-MD it had drafted in a separate file days earlier over the GHI-MD, undoing four changes `main` had made meanwhile.

A search of the last 30 days of transcripts found the refusal in 14 transcripts on ned-box and 5 on the Mac, and in the firings read, the agent compared its file with `main` by hand before writing its reason (unverified here: the count and the reading come from the approval-walk item cited under Approval, and were not rerun when this GHI-MD was written). One firing was checked for this GHI-MD: on ned-box on 2026-11-21, a subagent of the agent-seat agent-instructions-editor ran `cp` from a draft in its scratchpad over `docs/issues/2266-two-more-guide-agents-wiki-guide-agent-for.md` and was refused at line 150 of `nedlern@ned-box:/home/nedlern/.claude/projects/-home-nedlern-agents-agent-instructions-editor/399eddce-f2fc-4d59-9b77-c951df160e96/subagents/agent-aaa762a32cafd4ef1.jsonl`. At line 155 it wrote as its reason that `git diff 1c64cdc25 origin/main` on that file showed that `main`'s only change since its draft's base was a renamed link, which its command reapplied with `sed`.

No work was lost in those firings. This is not a new guard: the soft-block exists, and the change moves into it a check the agents in the firings read made by hand, a step that needs no judgment, which the code-prompt-code rule in `CLAUDE.md` puts in code.

## The change the user approved

When the soft-block finds a Write tool call or Bash command that replaces a whole GHI-MD, it checks whether `main` has changed that GHI-MD since the merge-base, the output of `git merge-base HEAD origin/main` in the checkout, which is the newest commit of `main` the checkout already contains, whether or not the checkout is on a named branch:

- When `main` has not changed the GHI-MD since the merge-base, the soft-block lets the replacement through without a reason, and leaves any reason marker unread.
- When `main` has changed it in any way, deletion and renaming included, the soft-block refuses as it does today, and a reason marker clears the refusal as it does today.

## Open questions to settle before building

1. The merge-base can be later than the commit the agent's copy was drafted from, and then the approved check lets through exactly the replacement the soft-block was added to stop. The firing above shows the shape: the draft's base was commit 1c64cdc25, and `main` changed the file after it, in the merge of PR [A design's name ends .tool.design.md or .system.design.md; rename the 16 existing designs](https://github.com/nedsnodes/nedsnodes/pull/3907) (verified with `git log --first-parent 1c64cdc25..origin/main` on that file: the only merge that changed it before the refusal at 2026-11-21 00:56Z). If the subagent's worktree, `/home/nedlern/Projects/nedsnodes/.claude/worktrees/worktree-agent-aaa762a32cafd4ef1`, contained that merge, as a worktree cut or reset from a freshly fetched `main` would, `main` had not changed the file since the merge-base, the approved check would have let the `cp` through without a reason, and the renamed link would have been undone had the agent not reapplied it on its own (unverified: the worktree no longer exists, so its merge-base could not be read). The 2026-10-27 incident had the same shape: a copy drafted in a separate file, then copied over the GHI-MD. So the merge-base check is sound only when the agent's copy was drafted in the checkout itself. Two ways forward, for the user to choose between, since either narrows what he approved:
   - Let the replacement through only when its source cannot be older than the merge-base, such as a Write tool call or a `cp` from a file the checkout's own commits changed after the merge-base, and refuse as today for any other source.
   - Keep refusing as today, and have the refusal print the hunks of `git diff <merge-base> origin/main -- <GHI-MD>` and of the replacement against `main`'s version, so the agent reads the changes it would undo instead of finding them by hand.
2. The check must read a current `main`: a local `origin/main` that has not been fetched can be stale, which is the case the soft-block guards against. Fetching inside a PreToolUse hook adds a network call, with its delay and its failure when offline, to every replacement the soft-block finds. Whether the soft-block fetches `main` itself, or refuses as today when its `origin/main` is older than some limit, is the builder's to decide; either way, when the check cannot give an answer, such as when there is no merge-base or a git command fails or runs out of time, the soft-block refuses as it does today.

## Constraints from related issues

- `scripts/branch-conflict-check.py` already fetches `main` and compares a branch with it using `git merge-tree`; GHI [The checkout-freshness hook's advice for a branch cut at a pull request's pushed head forbids a rebase, then sends the agent to `scripts/branch-conflict-check.py`, which orders one](https://github.com/nedsnodes/nedsnodes/issues/2988) is open on it. It is a script, not a module a hook can load, so move the fetch and git code the soft-block needs into a shared module both use, rather than writing a second copy inside the hook.
- GHI [Bash guards give every program they start a time limit of their own, so a program that never exits cannot hold up `nn-systems/general-tools/bash-guards-verdict-changes-between-git-refs-on-recorded-commands-check.py` for hours](https://github.com/nedsnodes/nedsnodes/issues/1983), closed, requires that every program a Bash guard starts, each git command included, has a time limit of its own.
- GHI [`nn-systems/general-tools/bash-guards-verdict-changes-between-git-refs-on-recorded-commands-check.py` reads a stored file of distinct recorded command pairs, reuses main's readings and reads many commands in each new process](https://github.com/nedsnodes/nedsnodes/issues/1571) replays every Bash guard's verdict on recorded commands at two git refs, through the soft-block's function `ghi_md_replaced_by_command`. Keep the new check out of that function, so a replay neither fetches nor reads the state of the replay's own checkout.
