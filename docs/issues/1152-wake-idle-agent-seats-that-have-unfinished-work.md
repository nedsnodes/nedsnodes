# Wake an agent-seat when its 5-hour session limit resets

An agent-seat that hits a Claude usage limit, such as the 5-hour session limit, stops mid-work, and after the limit ends it stays idle until something prompts it, usually the user typing to it. The idle sweep of GHI [Tasks raise themselves when their prerequisites are met, and agent-seats left idle with something to do are woken](https://github.com/nedsnodes/nedsnodes/issues/940), § The idle sweep, wakes it: a scheduled job on ned-box finds, every minute, the agent-seats that are idle; when the last record of an agent-seat's transcript is Claude's usage-limit record, a headless agent-session sends it one short cross-session message, with Claude Code's SendMessage tool, at the job's first run after the limit has ended. If the agent-seat is still idle 5 minutes after that message, rules 2 to 5 of GHI 940 § Who decides, and what is sent, decide the case at the job's next run. The idle sweep types nothing into a terminal or a tmux pane. The idle sweep is built under GHI 940; this GHI-MD records its usage-limit case and whether that message resumes an agent-seat. ned-box's agent-seats come first; the Mac's need a job running on the Mac.

## Why

An agent-seat between turns acts only when something reaches it: a prompt from the user, a message from another agent-session, a prompt from a job scheduled inside its agent-session, or the end of a watch or a background command it started. An agent-seat stopped at a usage limit with none of these on the way waits without limit, and the user does not watch every window. Most pull requests merge fast: of the 306 merged from 2026-09-29 to 2026-10-07, 184 were open for under half an hour, and the median was 20 minutes (`gh pr list --state merged --search "merged:2026-09-29..2026-10-07" --limit 1000 --json createdAt,mergedAt`, measured 2026-10-09). A pull request that needs its author's next step, when that author sleeps through a reset, can wait until the user notices.

## Decided

1. **What wakes an agent-seat**: the idle sweep of GHI 940, which also wakes an agent-seat stopped at its session limit, just after the reset (user-ruled 2026-10-30). The 3-hourly in-session job of 2026-10-18 is not built. A later ruling widens this wake from the session limit to every usage limit: one wake rule, with no 5-hour or weekly case, wakes the agent-seat when the limit's reset time passes or the logged-in account changes, as GHI 940 § The idle sweep says under its step **a usage limit**, which covers every limit (user-ruled 2026-11-01, item 1.2 of approval-walk reboot-test-remote-control-never-connected-reconnect-2026-11-01, minutes `nedlern@ned-box:/home/nedlern/nedsnodes-logs/walk/reboot-test-remote-control-never-connected-reconnect-2026-11-01-minutes.md`).
2. **How the wake is sent after a usage limit**: as GHI 940 § The idle sweep says under its step **a usage limit**: at the job's first run after the limit has ended, the headless agent-session sends one short message that code wrote, and is asked for no judgment. If the agent-seat is still idle 5 minutes after that message, code skips rule 1 for that limit record, and rules 2 to 5 decide the case at the next run; they may or may not end in a user-alert. Nothing is set up inside an agent-session, so a replacement agent-session needs no wake job installed.
3. **Both machines**: a cross-session message reaches the other machine only while the receiving agent-session's Remote Control is connected, so the Mac's agent-seats need the job running on the Mac, as GHI 940 § How the message reaches the agent-seat says; ned-box comes first.
4. **Considered and not chosen**: a timer outside Claude typing "." and Enter into each agent-seat's tmux pane, which the user ruled less simple and safe than a wake inside the session (2026-10-18); and that wake inside the session, a recurring CronCreate job set up by a SessionStart hook, which the idle sweep replaced (2026-10-30).
5. **Which entry the wake is sent to**: the ListAgents entry of the agent-seat's current agent-session, found through that agent-session's id, not by the agent-seat's name or tmux session, as GHI 940 § The idle sweep, Decided point 14, says (user-ruled 2026-11-23 02:34Z, item 11.2 of 12 of MD-skills's approval-walk nodes-design-forks-2026-11-21, "A"; walk-minutes `nedlern@ned-box:/home/nedlern/agents/MD-skills/docs/walk/nodes-design-forks-2026-11-21-minutes.md`, the line beginning "item 11.2 of 12: the user answered"). The user accepted that an update of Claude Code can change how ListAgents computes the ref, which the sweep computes as Claude Code 2.1.330 does; a wake whose ref then matches no entry sends nothing and is reported as a failure, by a task for reboot-test, or a user-alert when that task cannot be written, and the agent-seat stays idle until something else prompts it. Pull request 4187, cited under § Related GHIs, builds it; until it merges, the sweep on main still finds the entry by the agent-seat's name and tmux session.
