# Ask for the root cause at the moments a defect is fixed: fix pull requests, review fix-rounds, and causes left in place

## Problem

When an agent fixes a defect it usually fixes the case in front of it, and the same kind of defect returns elsewhere. CLAUDE.md now says to look for the root cause, but a standing instruction among many is easily lost in the middle of a fix, and no phrase reliably marks the moment: agents seldom write "root cause", and a defect can be fixed without the word "bug". The question has to arrive from outside the agent's memory, at the moment of the fix: from a program, or from the review every pull request already gets.

## The design

Three moments, each where the work happens: item 1 asks the author for the root cause, item 2 asks whether a finding is one case of a wider pattern, and item 4 asks the author to work on a cause left in place and shows the user a follow-up closed without being done. Item 3 is dropped; the items keep their numbers because GHI [Regular maintenance: the list of maintenance jobs, how often each runs, and how each reaches the user](https://github.com/nedsnodes/nedsnodes/issues/1058) cites item 4 by number.

1. **A pull request that fixes a defect.** Whether a pull request fixes a defect is a judgement: a test that fails on main and passes on the pull request's head commit marks a feature as often as a fix. So the judgement goes to the agent that already reads every pull request: the pull request reviewer instructions, `docs/agents/pr-reviewer.prompt.md`, ask whether the pull request fixes a defect, and if so whether its description carries, for each defect it fixes, a line, either `#root_cause <the reason the defect could happen at all, and what removes it>` or `#root_cause_not_fixed <why, and what the root cause is or that it was not found>`; the `#root_cause_not_fixed` line also carries `#follow_up` and a link, as item 4 says. A fix whose description lacks the line gets a finding that blocks the merge until the author adds it. The section "A pull request that fixes a defect" in `docs/agents/pr-reviewer.prompt.md` carries this; CLAUDE.md has no copy of the section, and CLAUDE.md's root-cause sentence tells authors where the line goes. Adding the line to the description settles the blocking finding without a new commit. Whether the reason given is the real root cause is the reviewer's to judge, not the program's.

   A root cause that lies in agent-instructions, such as a prompt, or in a design gets no blocking finding: the reviewer reports a finding that does not block and names that file as where the cause sits, and says nothing about its English. 2. **A review that carries findings.** The review that merge-lane-2 posts on a pull request with findings ends with one sentence asking the author, for each finding the author fixes, whether the finding is one case of a wider pattern, and to name the pattern in the fix commit's message. The author's forked subagent reads that review when it starts the fix-round, so the question arrives with the findings. A finding answered as not holding needs no such line.

4. **A cause left in place, after the merge.** A `#root_cause_not_fixed` line carries `#follow_up` and the full link to its follow-up: the issue or pull request that will fix the cause, or, when the cause is not known, an open issue that looks for it. `scripts/merge-gate.sh` refuses the line without that link, and refuses a link to an issue closed as not planned or a pull request closed without merging. After the merge, only the reviewer's brief reads the line again, `scripts/merge-lane-pull-request-reviewer-brief-compose-with-facts.py` listing a merged pull request whose not-fixed line links to an issue that a later pull request closes; nothing makes anyone work the follow-up. Of the 27 not-fixed lines merged by 2026-10-15, written before a link was required, none linked work that would remove its cause, and twice an open issue for the cause existed and the fix still took five pull requests. Two things follow:
   - **The author is asked to fix the cause next.** `scripts/merge-gate.sh` prints, in its pass output, each `#follow_up` link to an issue in this repository that is still open. A link to an open pull request is not printed, because that work is already under way, and a link to another project is not printed, because that work is not ours. merge-lane-2 adds each printed issue to the message it sends the author when the pull request merges, and the author answers with one of: the pull request that fixes the cause; the agent-seat that will; "blocked on <link>"; or "needs the user: <why>". Only the last reaches the user.
   - **A follow-up closed without being done reaches the user.** A daily maintenance-job of GHI [Regular maintenance: the list of maintenance jobs, how often each runs, and how each reaches the user](https://github.com/nedsnodes/nedsnodes/issues/1058), the daily list of root-cause follow-ups closed without being done, reads the `#root_cause_not_fixed … #follow_up <link>` lines of merged pull requests' descriptions, and lists each follow-up they name that was closed without being done: an issue closed as not planned, or a pull request closed without merging. Nothing is posted on the follow-up. The not-fixed lines merged before the link was required carry no link, so the job cannot find their causes; the agent-seat cold-read-improvement checks them once, and brings those whose cause is still in the code to the user in one approval-walk.

## Not in scope

A root-cause analysis document, a template beyond the one line, or a separate reviewer. The line is the whole record; the commit message and the pull request carry any detail.

## Deferred-decisions

The full cold read of the edit that dropped item 3 found these problems in text that edit did not change. Each needs its own decision or check, and none blocks the work in Next action.

- Item 2 says the author names the wider pattern in the fix commit's message; item 12 of the approval-walk pr-1636-reviewer-rule-on-workarounds-the-root-cause-fix-makes-useless-2026-10-19 (its walk-minutes, line 35) says "the pattern answer lives in the answers-file entry, quoted by merge-lane-2's review". Check which is current, and correct item 2 if it is the one out of date.
- Item 2 does not say what the author writes for a fixed finding that is not part of a wider pattern, what "no such line" refers to, or which program or instruction adds the review's closing sentence.
- Item 1 does not mention `#no_defect_fixed`, and does not say whether a defect that a pull request's own earlier commit introduced needs a line.
- Item 4 does not say where the author's answer is sent or recorded, what happens when no answer arrives, or how "needs the user" reaches the user; a program could record and route the four answers.
- Item 4's daily job does not say what it does when GitHub cannot answer for a link, and it misses a follow-up closed as completed or as a duplicate without its cause being fixed.
- Item 4's one check of the older not-fixed lines has no date marking when the link became required, no completion record, and no rule for a cause outside the code.
- This GHI-MD uses several words the glossary spells differently or does not define, such as "head commit", "ruling", "not-fixed line" and "/advisor".
