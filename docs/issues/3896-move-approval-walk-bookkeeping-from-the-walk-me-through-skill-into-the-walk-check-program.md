# Move approval-walk bookkeeping from the walk-me-through skill into the walk check program

The walk-me-through skill still has the agent do by hand some approval-walk bookkeeping that needs no judgment: it writes some state lines of the walk-minutes itself, classifies some answers, and lists the approval-walk's loose-ends at close. The cold-read of the skill's rewrite asked its reviewers which of the skill's instructions should be code, and they proposed moving these steps into the walk check program, `nn-systems/skills/walk-me-through/walk-me-through-answer-added-texts-cold-read-fast-read-check-and-close.py`. This GHI-MD lists those proposals, deduplicated across the three runs that made them, so that each can be built or dropped later. Nothing is built under this GHI yet, and nothing is to be built under it while it waits on approval-walks moving onto the runner, as the section "Waits on the runner" says.

## Why

CLAUDE.md's code-prompt-code bullet says a step that needs no judgment, such as sequencing, state or validation, goes in code, and that a skill's ordered steps, with the record of which are done, belong in a program the agent asks for its next step. Today the walk check program writes the answer, outcome and `#next_to_present` lines after each answer, but the agent writes the start, pause and resume lines and the `#item_page` lines by hand. An agent that gets one of them wrong leaves the walk check program and the walk-me-through hooks reading the wrong item.

## Waits on the runner

The walk check program gains no step chain, meaning no chain of steps each refusing until the previous one is recorded, while approval-walks are not on the runner. [The nodes design](https://github.com/nedsnodes/nedsnodes/blob/nodes-and-state-machines-project-wide-design-for-user-review-topic-branch/docs/nedsnodes-wiki/queue/nedsnodes-moving-the-project-to-nodes-and-state-machines.md), on its topic branch and filed as [GHI 5227, Move the whole project to nodes and state machines](https://github.com/nedsnodes/nedsnodes/issues/5227), has one program, the runner, execute each workflow, and its `next` command hands out each step and records it. When approval-walks move onto the runner, `next` hands out the steps these proposals describe, so a step chain built in the walk check program first would be built twice. The approval-walk's bookkeeping moves into code, and out of `/walk-me-through`, at that move. Until then this GHI stays open, and its proposals list the steps the runner must take over. If the nodes design is not approved, this GHI can still be built as it stands.

## The proposals

Each line names the by-hand step, the code proposed for it, and the findings that proposed it, as run and finding number.

1. **Start.** A `start <name>` step refuses an approval-walk name that `docs/walk/<name>*` already uses, counts the walk-document's items, and writes `#next_to_present item 1 of M`; it could also check that the opening's first sentence is under 30 words, and list each hyphenated term or `-suffix` in the walk-document that no glossary defines, as candidate key-terms for the agent to judge (R5 2, R5 5, R6 2, R7 4, R7 6, R7 12).
2. **Pause, resume and status.** A `pause "<his words>"` step writes the `#approval_walk_paused` line, and a `resume` step writes the `#next_to_present` line after it, each in the form the hooks read; `resume`, or a `status` step, prints the last item the close step recorded and the item to resume at, and cross-checks the item numbers in the walk-minutes against the walk-document's headings; a `replan` step writes the `#next_to_present` line when the agent re-plans the approval-walk, and a `finish` step writes `#next_to_present none, closed` at the approval-walk's close and then runs `nn-systems/skills/walk-me-through/walk-files-ship.py` (R5 9, R6 2, R6 12, R7 14).
3. **Approved as revised.** The close step writes the `<approved as revised>` classification when the user approves an item whose text changed after it was first shown, which main's skill, section "Capturing the approval-walk", has the agent write by hand (R5 12, R7 13).
4. **Item page record.** An `item-page-record` step, R6's name for it, writes the `#item_page` line for the waiting item from the link the agent passes it, or, when the publish failed, the form that records the error, counts the item's earlier `#item_page` lines and prints the page title with its version number; the Artifact tool call stays with the agent; the read step could also refuse to clear an item that has no `#item_page` line (R5 7, R6 4, R7 10). GHI [Approval-walk item page publisher copying linked files into the page as timestamped copies, so short repository and log-store paths open on the iPad](https://github.com/nedsnodes/nedsnodes/issues/2168) builds the page itself and does not write this line (searched `item_page` in `docs/issues/2168-approval-walk-item-page-publisher-copying-linked-files.md`: no match).
5. **Loose-ends at close.** A step lists every item with no close line, every item recorded `<open>`, deferred or held, and every `Open Walk <walk name> Question:` task, so the agent adds only the commitments made in conversation; it could refuse to run `nn-systems/skills/walk-me-through/walk-files-ship.py` while the summary item has no close line (R5 8, R6 6, R7 2).
6. **Merge approval-walks.** A `merge-walks` step copies each other open approval-walk's unanswered items, with their category, waits-on and first-entered lines, into the kept walk-document, writes `#next_to_present none, closed` in the other walk-minutes and runs `nn-systems/skills/walk-me-through/walk-files-ship.py`; the agent keeps only the judgment of which items are related (R5 6, R6 8, R7 15).
7. **Advisor prompt before the summary item.** When the next item is the summary item, the close step prints the advisor question and the six questions of the skill's section "Advisor", as the short-answer hook already hands over its text for Aa, the answer that approves an item after an advisor check (R5 11, R6 10, R7 16).
8. **Order of approved work on one file.** When an approved item's touched files overlap work still running, the program prints that the second must wait (R5 13, R6 9, R7 11). Part 1 of GHI [Three mechanical checks agents keep forgetting to run: file-overlap before work starts, exit status through a pipe, and the settled-decision list](https://github.com/nedsnodes/nedsnodes/issues/216) proposes a file-overlap check for all work; build this one only if that one does not cover it.
9. **Reference and hashtag form.** The read step flags a bare GHI or pull request number or a file name outside a Markdown link, and a `#old` or `#new` hashtag that is misspelled or not at the start of its line, before the cold-read-fast-read runs (R7 9).
10. **The user's words outside an item.** A UserPromptSubmit hook appends each prompt the user types while an approval-walk is open to the walk-minutes, word for word with the time (R5 4). GHI [ruling-agent keeps user-rulings, checks approval-walk items against them](https://github.com/nedsnodes/nedsnodes/issues/2118) designs a store of every user turn from the transcripts, and its program `scripts/standing-user-rulings-store-add-from-transcripts-and-walk-minutes-then-index-file-and-anchor-list-for-hooks-write.py` is on main; build this only if that store does not serve the approval-walk.
11. **The item shown word for word.** On the message that first presents an item, a Stop hook checks that the item's lines from the walk-document appear in the reply before the closing line, as `nn-systems/skills/walk-me-through/walk-me-through-agent-question-to-user-outside-approval-walk-items-refusal-stop-hook.py` already matches the reply's lines against the walk-document's (R5 10, R6 5, R7 8); R6 10 adds a Stop hook that checks the advisor was called before item 1 and before the final item.

Each refusal or check these proposals add is a guard: the refusals in proposals 1, 4 and 5, the wait in proposal 8, and proposals 9 and 11. Before building one, apply CLAUDE.md's bullet on when to propose a guard: build it only when the failure it stops has happened, or is foreseeable within 30 days, and would lose or damage work, stop other work, or go unnoticed. Part 5 of the same item 62.3, which the user approved, says to add no rules for failures that have never happened.
