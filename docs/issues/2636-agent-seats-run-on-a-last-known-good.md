## The two commits

- **last known good commit**: the commit the branch `last-known-good` on origin points to. The program of part 1 moves the branch, only forward, to a commit of main on which ned-box's full test run, every nn-test-suite, passed. The agent-homes, the reference-checkouts and merge-lane-2's review tools follow it, except the canary's agent-home; part 2 says which checkouts still run newer code, and why.
- **release candidate**: main's newest commit, `origin/main`. Every merge moves it. The next full test run tests the commit that is main's newest when that test run starts, and when that test run passes, the program of part 1 moves `last-known-good` to that commit, even if main has moved on.

This design uses both as SDLC-terms, in plain words, and neither becomes a project-term, as the user decided in item 25. Neither is in `docs/nedsnodes-wiki/nedsnodes-sdlc-terms.md` today. Search receipt: `git grep -l -i "last-known-good\|last known good\|release candidate\|release-candidate"` over `scripts`, `nn-systems`, `.claude` and `docs` on origin/main 45e082bc0, 2026-11-04, found only `docs/cross-project/nedsnodes-ai-native-software-development-notes.md`, which uses "release candidate" in its general sense, and ghi-guide-agent, asked 2026-11-04, found no GHI that names either.

The release candidate is not a branch of its own. Main already moves only forward, one merge at a time, so "the failed one plus the fix" is main's next commit after the fix merges. No branch or checkout that holds work moves backwards; a fix may still be a `git revert` of the breaking pull request, merged as a pull request of its own. Only the promotion in part 1 is meant to move `last-known-good`; what GitHub can refuse is under Deferred-decisions.

## Design

### 1. The last known good commit, and how it moves

The last known good commit is the commit the branch `last-known-good` on origin points to, so that an ordinary `git fetch origin` brings the branch to every clone whose fetch refspec is `+refs/heads/*:refs/remotes/origin/*`, as the reference-checkout's on ned-box is, and git shows it as `origin/last-known-good`; the user chose the branch over a ref outside `refs/heads/` in item 18. Only one program moves it, by a fast-forward push, and only after a passing full test run on ned-box.

A new program, the promotion program, `scripts/full-test-run-of-main-in-a-quiet-gap-and-last-known-good-promotion.py`, runs on ned-box under cron every 5 minutes. This name and the names of its state file and output file are working names from before part 3 dropped the quiet test; the build chooses the final names, as item 25 says of this design's other new names, and none of them names a quiet gap. Its entry in `nn-systems/general-tools/scheduled-jobs-on-each-machine.json` replaces ned-box's entry for `scripts/scheduled-full-test-run-of-main.py`; the Mac's entry stays. The build's pull request only deletes that entry's ned-box placement, as the docstring of the installer, `nn-systems/general-tools/install-scheduled-jobs-on-this-machine.py`, says under "RETIRING A JOB". At the next pull into ned-box's reference-checkout, the post-merge hook then runs `--install`, then `--remove-not-in-table`, which takes the old daily run off ned-box, so cron does not start both. Running `--remove --job scheduled-full-test-run-of-main` by hand first would not hold, because any merge before the pull request's own reinstalls the job from its entry. After that pull, the build's author runs the installer's `--check` on ned-box. A job still reported NOT IN THE TABLE is one whose cron line also runs another job, which `--remove-not-in-table` reports as KEPT; the author edits that cron line by hand. Each invocation, in order:

1. Takes the program's own lock, a lock file beside its state file. A scheduled invocation takes it without waiting and exits 0 when another invocation holds it; a `--start-now` invocation waits for it.
2. Reads its state file, `~/.local/state/nedsnodes/full-test-run-of-main-in-a-quiet-gap-and-last-known-good-promotion.json`: for the last full test run, its commit, start, end, exit code, record path and failing nn-test-suites; how many full test runs in a row failed at that commit; the last scheduled start time used up, as part 3 says, by its date and time, such as 2026-11-22 06:00; a passing commit not yet promoted, with the time and reason its push last failed; the time `last-known-good` last moved; the last commit the fast check of part 4 checked, with its result; and the time a follow-up was recorded as sent, as part 6 says. A missing file counts as empty, as on the first invocation after the build. A file that exists but cannot be read or parsed is reported, and the invocation exits nonzero without changing it, because treating it as empty would forget the last scheduled start time used up and the failure count.
3. Fetches origin.
4. When the state file holds a passing commit not yet promoted: when `origin/last-known-good` already holds that commit, clears the passing commit from the state file; otherwise retries its push as in step 8. A failed retry is recorded, and the invocation goes on to step 5, so a push that keeps failing does not stop later full test runs; the invocation still exits nonzero at its end.
5. Decides, as part 3 says, whether a scheduled start time has come that is not yet used up, and if so whether a full test run is due at it; records that scheduled start time in the state file as used up; when no full test run is due, ends the invocation, exiting 0 unless step 4's retry failed. A `--start-now` invocation skips this step.
6. Records in the state file that a full test run has started, with its start time.
7. Runs `scripts/scheduled-full-test-run-of-main.py`, changed as listed below, which fetches origin, tests origin/main's newest commit in a detached worktree, and writes its record.
8. Writes the full test run's result to the state file. When that program exited 0 and its record names commit C, C is the passing commit not yet promoted, and the program pushes C to `refs/heads/last-known-good` without force: it creates the branch at C when origin has none, and otherwise pushes only when `origin/last-known-good` is an ancestor of C. C is promoted even when main has moved past C during the full test run; the full test run of the next scheduled start time tests main's newer commit. The push fails, rather than moving the branch backwards, when the branch moved to a later commit in the meantime, which only a push from outside this program can do. When the push fails, the program records C and the push's error in the state file, then exits nonzero. After a push that worked, it clears the passing commit not yet promoted and records the time `last-known-good` moved.

Every failure to fetch, push, or read or write the state file, and every failure to take the lock other than finding it held, prints its reason and exits nonzero, so cron's output file, `~/.claude/full-test-run-of-main-in-a-quiet-gap-and-last-known-good-promotion.log` on ned-box, where the other cron jobs' output files are, keeps it. A push that has failed is also in the state file, so the notice of part 5 names it.

**Changes to `scripts/scheduled-full-test-run-of-main.py`.** It gains an option, named in the build as item 25 says, that leaves `--record-inputs-with-strace` out, for part 3. On both machines, its record's name becomes `<YYYY-MM-DD>-<HHMMSS>.txt`, from the Los Angeles date and time the full test run started, so that each full test run, a `--start-now` one included, keeps a record of its own. For each failing nn-test-suite it copies the log to the log-store beside the record, so the notice of part 5 can name a log the next full test run does not delete.

**The user's own start.** The same program with `--start-now` waits for the program's lock instead of exiting, skips step 5's decision whether a full test run is due, tests origin/main's newest commit even when the last full test run passed or failed twice at that commit, and promotes as in step 8 when the full test run passes. When a scheduled full test run is already going, the `--start-now` invocation waits for it to end and then starts its own. A scheduled full test run of 06:00, 12:00 or 18:00 after a `--start-now` full test run that passed is skipped as part 3 says, when main has not moved since; the full test run of 00:00 runs regardless. A `--start-now` invocation uses up no scheduled start time. He runs it from his Mac as `ssh nedlern@ned-box 'python3 ~/Projects/nedsnodes/scripts/full-test-run-of-main-in-a-quiet-gap-and-last-known-good-promotion.py --start-now'`, or tells an agent to.

Only ned-box's full test run promotes. The Mac's full test run stays daily, with the record name and log copy above, and promotes nothing: the Mac sleeps, so a promotion that waited for it could wait for days, and the test cases that run only on macOS are few (on 2026-11-04 ned-box's record skipped 4 test cases as macOS only, 3 in `scripts/recover-crashed-seats-test.py` and 1 in `scripts/run-all-test-suites-signal-sandbox-test.py`, of 10 test cases it skipped in all).

The promotion push of `refs/heads/last-known-good` goes through the pre-push hook like any other branch push; its conflict check and revert check find it clean, because the commit it pushes is already on main.

### 2. Which commit agent-seats run on, and which commit they start branches from (question 1)

**Branches start from origin/main, the release candidate, as today.** Work changes the candidate: a fix for a failed candidate must be built on it, since the next candidate is "the failed one plus the fix". The head test run tests a branch merged with main wherever the branch was cut, so starting from the last known good commit would save no testing. The checkout-freshness hook keeps rebasing a never-pushed nn-topic-branch onto origin/main.

**What an agent runs comes from the last known good commit.** Three checkout-sync steps change their target from origin/main to origin/last-known-good, for checkouts that hold no commits that origin/main lacks:

- `launch_time_git_sync` fast-forwards a strictly behind agent-home to origin/last-known-good before an agent-session starts, and fast-forwards the reference-checkout to origin/last-known-good before the handoff-supervisor restarts itself.
- The checkout-freshness hook's step 5b fast-forwards a detached checkout with no commits that origin/main lacks to origin/last-known-good. ### 3. When a full test run starts: four scheduled start times a day (question 2)
