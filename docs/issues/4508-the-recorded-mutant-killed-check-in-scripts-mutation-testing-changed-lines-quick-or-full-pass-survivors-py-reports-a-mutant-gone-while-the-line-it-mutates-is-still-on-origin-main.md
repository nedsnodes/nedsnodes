# The recorded mutant killed check in scripts/mutation-testing-changed-lines-quick-or-full-pass-survivors.py reports a mutant gone while the line it mutates is still on origin/main

## Reproductions

Each case below makes `--recorded-mutant-killed-check` print MUTANT NO LONGER EXISTS and exit 0, or makes its function `recorded_mutant_lines_on_main` return `gone`, while the line the recorded mutant replaces is still on origin/main. Each was reproduced on ned-box on 2026-11-24 (UTC) by the Claude reviewer of [PR 4504, Mutation recheck reports a mutant gone only when git history shows its line ended](https://github.com/nedsnodes/nedsnodes/pull/4504), on both main at the merge base 72717eca7cb9 and PR 4504's head 47876db7b22b, in scratch repositories and scratch clones, with no suite run and no task completed. Cases 1 and 2 were first found by the Codex review cell on the same pull request. The reviewer's records are `nedlern@ned-box:/home/nedlern/nedsnodes-logs/seats/merge-lane-2/merge-helpers/claude-reviews/pr4504-47876db7b22b52174c212a8e838cc1ab613b2145/` (the inline comments at `:1630` and `:1659` in `nedlern@ned-box:/home/nedlern/nedsnodes-logs/seats/merge-lane-2/merge-helpers/claude-reviews/pr4504-47876db7b22b52174c212a8e838cc1ab613b2145/review.json`, and that directory's `codex-findings-answer.txt`), and Codex's report is `nedlern@ned-box:/home/nedlern/nedsnodes-logs/seats/merge-lane-2/merge-helpers/cx/pr4504-72717eca/codex-code-review-report.md`.

1. **A short line moved unchanged to another file.** In a scratch history, commit 1 has a function `alpha()` in `scripts/a.py` ending in `        return True`; commit 2 moves the function to the kept file `scripts/lib.py` (`git diff --name-status -M` prints `M a.py` and `M lib.py`; `git grep` finds `lib.py:79: return True`). The check reports the mutant on that line gone, and does the same when `a.py` is deleted in the move. `git blame -C` follows a moved block only when it scores at least 40 alphanumeric characters, so a short line is never followed; `git blame --reverse --first-parent -w -M -C1 -L 6,6` does follow it to `scripts/lib.py:79`. Two real lines of this repository behave the same way:
   - `return projects_root / mangled`, across merge commit 0e176ef31: reported gone, while the line is on main at `scripts/claude-code-session-transcript-lookup-and-text-search-common.py:14`. `git blame -w -M20 -C20` follows it.
   - `tool_result = {}`, moved and re-indented within `scripts/handoff-context-threshold-hook.py` in merge commit c9c8855ec: reported gone, while the line is on main at `scripts/handoff-context-threshold-hook.py:379`. Here even `-M20 -C20` ends the line, so lowering blame's threshold does not fix the case.
2. **Two replaced lines removed and one restored.** A mutant replaces `seen = set()` and `count = 0`. One commit removes both lines, and a later commit puts back `count = 0`. The check reports gone while `count = 0` is in the file on main, because the fallback that looks for the replaced text on main searches for the replaced lines as one block, not each line on its own.
3. **A re-wrapped line.** A mutant replaces `return compute_a_long_descriptive_result_value(total, x, default=True)`; on main the same call is split, with `total, x, default=True)` on the next line. The check reports gone, though the mutated code (`default=True`) is on main.

## Why it matters

The scheduled full mutation pass, `scripts/scheduled-full-mutation-pass-of-merged-pull-requests-and-survivor-tasks-open.py`, rechecks each open survivor task on main and completes the task when the check says the mutant no longer exists, as GHI [The scheduled full mutation pass rechecks a surviving mutant on main before it stops tracking it](https://github.com/nedsnodes/nedsnodes/issues/2846) designed. A wrong gone verdict therefore completes a survivor task while the untested line stays on main, and nothing tells anyone. The task can be reopened by hand, but only by someone who notices. PR 4504's description measured 285 of 835 such verdicts as wrong on main before its fix (unverified here); its fix removes the rename and context-rule cases it measured, but not the three cases above.

## What to do

Change the check so that it reports gone only when it finds no copy of any replaced line on main, and reports MUTANT COULD NOT BE JUDGED otherwise, with a test that reproduces each case above. What counts as a copy is the owner's design, below. The scheduled full mutation pass already leaves a task open when the check reports MUTANT COULD NOT BE JUDGED (`scripts/scheduled-full-mutation-pass-of-merged-pull-requests-and-survivor-tasks-open.py`, read by the reviewer at PR 4504's head), so the pass needs no change for that verdict.

The Claude reviewer prototyped one rule on these fixtures and on the two real lines; it is a proposal the user has not approved. The rule runs after reverse blame, as PR 4504's check does, and applies only when blame ends every replaced line before main: report gone only when no replaced line, with indentation stripped and each line searched on its own, matches a line of the file on main or of any file changed between the newest commit on main that holds the recorded hunk (PR 4504's `commit_on_main_holding_recorded_hunk` finds it) and origin/main. The reviewer reports:

- It fixes cases 1 and 2, and both real lines, which it reports as could not be judged, naming the file that holds the copy.
- It does not fix case 3. Searching with all whitespace removed across the whole file, line breaks included, would also catch case 3.
- Short and common lines, such as `return True`, `continue`, `pass` or `else:`, are then almost never judged gone: the two real commit ranges changed 1009 and 906 files, so a `return True` or `continue` that really was removed is reported could not be judged whenever any of those files gains an unrelated copy.
- More survivor tasks stay open, each costing an agent time to close by hand; nothing is lost, and the result can be undone.
- A line whose code is unchanged but whose comment was edited still counts as gone, so that case would still complete a task silently.

The reviewer recommends that trade, because, apart from the edited-comment case and case 3, every wrong outcome under the rule is an open task an agent can close rather than a silently completed one. A change to which survivor tasks stay open is a design choice for the user. Before putting it to him, the owner can replay the current check and the proposed rule over the recorded survivor diffs in the log-store and count, for each, the verdicts of gone, of could not be judged, and of gone while the line is on main, so that he decides on counts rather than on the reviewer's estimate. Two further options the owner may weigh: the check could apply the recorded mutant to the copy it found on main and run the tests, completing the task when a test kills it; and the scheduled pass could search main again, on later runs, for the replaced lines of each task it completed as gone, and reopen or report any it finds.

The owner is fleet-restart-at-login, which wrote the check on main and is PR 4504's author.
