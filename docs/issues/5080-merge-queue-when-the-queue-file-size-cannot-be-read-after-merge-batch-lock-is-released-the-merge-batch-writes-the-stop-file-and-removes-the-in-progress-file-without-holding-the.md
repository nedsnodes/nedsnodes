## What is wrong

`run_in_queue_order()` releases `merge-batch.lock` and then reads the queue file's size, to find lines appended meanwhile, and then tries to take the lock again with `fcntl.flock(lock, fcntl.LOCK_EX | fcntl.LOCK_NB)`; an `OSError` other than `BlockingIOError` from that second call is in the same window. An `OSError` from that read reaches the handler `except (ReadOrWriteFailed, OSError)`, which calls `stopped()` as for a failure inside the lock: `stopped()` writes the stop file and removes the in-progress file. Batch A no longer holds the lock there, so it changes files that batch B, which does hold the lock, owns:

- batch B's in-progress file, the record that a merge is under way, is removed while batch B's merge runs. GHI [Merge queue: the dead-batch check is made without holding merge-batch.lock, so a healthy merge batch can be stopped and a dead one missed](https://github.com/nedsnodes/nedsnodes/issues/4977), which PR 4988 fixes, makes the dead-batch check and the removal of the in-progress file happen only while holding `merge-batch.lock`; this path is one more removal outside the lock, which PR 4988 leaves in place. Today no program reads the removed file while the stop file exists, as the control run shows, so the removal alone loses nothing yet; a change to that order, or a stop file removed by anything other than `merge-batch-resume`, would make batch B's death mid-merge go unreported.
- batch B, a healthy merge batch, is stopped at its next check of the stop file, by a failure that was batch A's own read and touched none of batch B's work.

Codex's round 2 finding judges that this reports no false success. No record shows the read failing, and the merge queue program is not in use yet: on 2026-11-26 ned-box had no directory `/home/nedlern/nedsnodes-logs/seats/merge-lane-2/merge-queue-merge-batches`, the program's default merge batches directory, and no crontab line names the program; `ssh nedlern@ned-box 'ls -d /home/nedlern/nedsnodes-logs/seats/merge-lane-2/merge-queue-merge-batches; crontab -l | grep merge-lane-merge-queue'` checks this again.

## What to do

After PR 4988 merges, the agent-seat overall-cleanup, which wrote this program in PR [Merge queue program merges approved lines in order until none is left](https://github.com/nedsnodes/nedsnodes/pull/4893) and wrote PR 4988, fixes this. merge-lane-1 reports that overall-cleanup has a task "Fix GHI 4985" (unverified), for GHI [The merge queue program merges a pull request over a `HOLD-` line appended after it read the queue file and before the merge program merges](https://github.com/nedsnodes/nedsnodes/issues/4985), which changes the same file, so both fixes go together; if overall-cleanup has no such task, this fix is still overall-cleanup's.

The cause is that whether the batch holds `merge-batch.lock` is known only from where the code is, so `stopped()` cannot tell whether it may change the shared files. The fix records it: the runner sets a flag when it takes the lock and clears it at `LOCK_UN`, and while the flag is clear `stopped()` neither writes the stop file nor removes the in-progress file. It still writes the stopped notice, whose file name is its own, so merge-lane-2 learns of the failure even when no other batch runs, and the exit code stays 1. The next batch to take the lock meets the same unreadable queue file and stops under the lock. Add a test case to `scripts/merge-lane-merge-queue-approved-lines-merge-in-order-until-none-left-test.py` that injects the failure as the reproduction does, after `LOCK_UN` and while a second batch holds the lock, and asserts that the first batch exits 1 and writes a stopped notice, and that the second batch's in-progress file and the stop file are left as they were.
