# Review the whole project for fixed markers that would be clearer as hashtags

## Why

Agents and programs in this project look for fixed words in documents and output: a line in a pull request's description that began `Root cause:` before it became the hashtag `#root_cause`, the line `VERDICT: CONFLICT` that `scripts/branch-conflict-check.py` prints, the first line `Report complete: no findings.` of an empty cold-read report, the walk-minutes classes such as `<approved as revised>`. Each is written in its own style, and a reader cannot always tell a fixed marker from ordinary prose, nor search for one without knowing its exact spelling and punctuation.

A hashtag, such as `#not_in_this_run`, in the form the section "The hashtag form the user ruled on 2026-11-25" below sets, stands out to a reader, and a program or an agent finds it with one exact search. Underscores keep it apart from project-terms, which are hyphenated. `#` with no space after it does not make a Markdown heading.

- `#revisit_before` names the event after which a deferred decision becomes expensive to change, and `#revisit_after` names the event the deferred work waits on; either is left off when no such event can be named.

Item 32, approved 2026-11-25 06:22Z in his words "A I think we should have a wiki page with all the hashtags and their definitions. A grep should be able to find them. If not we should figure out their format so they are grep able. I guess this will be a new glossary page the hashtag glossary. What do you think", adopted four texts:

- Part 1, the term: "**hashtag** — a fixed marker that a program, an agent or a person looks for in output, in a document or in a JSON value, written `#` and then two or more lowercase words joined by underscores, in the order Step 2 of [the naming page](https://github.com/nedsnodes/nedsnodes/blob/main/docs/nedsnodes-wiki/nedsnodes-how-to-choose-a-name-for-files-code-and-glossary-terms.md) gives a name: the system it belongs to, if any, its hyphens made underscores, then what it concerns, then what it marks, usually a state, such as `#cold_read_target_changed_during_run` or, for a program of no system, `#branch_conflicts_with_main`." Each hashtag is a constant in its system's `-common.py`, checked by a test, or, as item 33.2's Part 2 adds, in the program itself for a program in no system; existing hashtags keep their spelling, even one-word ones such as `#new`.
- Part 2, warning lines, printed by one shared function: "A line that reports a warning or a failure carries its state's hashtag right after the program's name and a colon, then the warning's text, and each instruction for it goes on a line of its own after it, opening with the program's name and a colon, `#next_step`, the condition it applies under and a colon if it has a condition, and then the instruction, each part after the first preceded by one space, so that a filter for Claude Code's Monitor tool that matches hashtags shows the warning with every instruction for it."
- Part 3, JSON: "A JSON value that holds a state is the state's hashtag, `#` included, such as `{"outcome": "#main_gatekeeper_checked_in"}`."
- Part 4, earlier forms: "A value that an outside program defines or reads keeps that program's spelling, such as GitHub's review event `APPROVE`. For a state of its own, a program writes the hashtag, never the earlier form, and a reader also accepts that earlier form only until a one-time conversion program has rewritten the stored records holding that form, or for good where they cannot be rewritten, such as merged pull requests' descriptions."

Item 33.2, approved 2026-11-25 15:29Z in his words "A", amended Part 1 and added the hashtag glossary:

- Part 1: "Every hashtag ends with a `#`, such as `#branch_conflicts_with_main#`. A one-word hashtag in use today keeps its one word and gains the closing `#`, such as `#new#`; no new hashtag is one word."
- Part 2: "The hashtag glossary, `docs/nedsnodes-wiki/nedsnodes-hashtag-glossary.md`, lists every hashtag in alphabetical order, each as one bullet written `` - `#<name>#` — <definition> ``. It is the one place a hashtag is defined, including a hashtag only one system uses. A program that prints or reads a hashtag holds it as a constant in its system's `-common.py`, as item 32's Part 1 says, or, for a program in no system, in the program itself, and the constant's comment points to the hashtag glossary instead of defining it again."
- Part 3: a test searches the repository for `#[a-z][a-z0-9_]*#`, skipping the hashtag glossary and the files in `docs/walk/` and `cold-read-records/`, and fails, naming the hashtag, when one is used but not listed, or listed but used nowhere else. A pull request that adds a hashtag adds its bullet in the same commit, and the project glossary lists the hashtag glossary beside the system glossaries.
- Part 4: the one-time conversion that item 32's Part 4 calls for adds the closing `#` to every hashtag in use, about 2,600 uses of about 180 hashtags in about 140 files, in the same pull request as the hashtag glossary and its test, before this GHI's sweep, so that the sweep writes each new hashtag with its closing `#` and adds it to the hashtag glossary.

This GHI-MD and its supporting list still write hashtags without the closing `#`, such as `#next_step` for `#next_step#`, as main does until that conversion, which rewrites them too, lands.

#open_question The hashtag glossary's pull request settles three points the rulings leave to its build: how its test refuses a new one-word hashtag while it accepts those in use today, since its search pattern matches both; where a hashtag that more than one system uses is held as a constant; and how its test tells a hashtag from other text between two `#` characters, such as a test of a malformed hashtag.

## The work

1. List every fixed marker the project uses that an agent or a program looks for, from agent-instructions, skills and their prompts, GHI-MDs, designs, hooks, and the scripts that parse or print markers. Starting points, each found on main: `#root_cause`, `#root_cause_not_fixed` and `#no_defect_fixed`, already hashtags (`CLAUDE.md` tells an author to write one in each pull request's description, `scripts/ghi-issue-write.py` writes `#no_defect_fixed` in the descriptions of the pull requests it opens, and `scripts/merge-gate.sh` checks them); `VERDICT: CONFLICT` (printed by `scripts/branch-conflict-check.py`, quoted by `docs/nedsnodes-wiki/nedsnodes-how-a-program-reports-success-failure-and-findings-with-its-exit-code.md` and read by programs such as `scripts/git-client-side-hooks-pre-push-conflict-check.py`); `Report complete: no findings.` and `clean sections:` (`.claude/skills/cold-read/prompts/defect-hunt-prompt.md`); the walk-minutes classes `<accepted>`, `<approved as revised>`, `<revised, awaiting ruling>`, `<moved on, no decision>` (`.claude/skills/walk-me-through/SKILL.md`).
2. For each, record where it is written, which programs or agents read it, and what changing it would break: the parsing code, its tests, and the documents that quote it.
3. Recommend, for each, to keep it or to make it a hashtag, with the reason. A marker a program prints for a person, or one that an outside tool fixes (such as a git trailer), likely stays.
4. Bring the recommendations to the user in an approval-walk. Nothing changes without his ruling; each approved change is its own pull request, with its parser and tests.
5. Build a maintenance-job that keeps the list from drifting, because new programs and prompts keep adding fixed markers after the sweep. The job renames nothing: a conversion is still put to the user under step 4 and made in its own pull request. Its design, for its build:
   - **What it reads.** The files under `scripts/`, `nn-systems/`, `.claude/guard-hooks/` and `.claude/skills/`, and the standing instruction files (`CLAUDE.md`, `AGENTS.md`, every seat-brief and every `-instructions.md` and `-prompt.md` file), changed on main since the job's last run, and main's copy of the supporting list, `docs/issues/1518-fixed-markers-list-every-literal-string-programs-and-prompts-match-with-its-readers-and-proposed-hashtag.md`.
   - **The program part.** A program, with no model, lists the candidates in the lines changed since the last run: a string literal that a program compares, searches for or splits text on, such as the argument of `in`, `startswith`, `re.search` or `grep`; and a backquoted literal that agent-instructions tell an agent to write or look for. For each candidate it says whether the supporting list already holds it, and whether it is a hashtag. A candidate is judged once: the next run reads only the lines changed after this one.
   - **The agent part.** For each candidate the supporting list does not hold, a model that the job's program starts for this step judges whether it is a fixed marker by the list's own definition, text that crosses a boundary between programs or agents, and for each that is one, writes a row in the list's table format, with a recommendation to keep it or make it a hashtag.
   - **How often.** Weekly. Fixed markers enter only through merged pull requests, a few in a week, and a marker that waits up to a week to be listed costs nothing, because none is converted before the user rules on it under step 4; a daily run would mostly report nothing. No single moment marks the change either, so the job stays weekly for the reason GHI [Regular maintenance: the list of maintenance jobs, how often each runs, and how each reaches the user](https://github.com/nedsnodes/nedsnodes/issues/1058) gives for its weekly hook and program measurement.
   - **What it reports, and where.** One line per fixed marker, added since the last run, that the supporting list does not hold, with its proposed row; and one line per place, added since the last run, that writes or reads a fixed marker in a form the user has ruled replaced by a hashtag, such as a new `Root cause:` line. The report is one file per run in the maintenance report directory in the log-store that GHI 1058's section "How the maintenance jobs resume, pace their work and file their reports (decided)" sets, whose name its build chooses. A week with no finding says so in one line; a file the job could not read is named, with the reason, and never reported as clean.
   - **How it reaches the user.** As every maintenance-job does, by the route GHI 1058 decides in its sections "How the maintenance jobs run each night, and how often (decided)" and "How a daily job is handed to the user and tracked (decided)": a scheduled program on ned-box runs the job's program part, and one nightly overseer agent-session, which the handoff-supervisor starts under a fixed name so that the user reaches it through Remote Control, puts the questions of every due job to him in one approval-walk, and shows him each job's report with a link to its file; a question he has not answered stays queued for the next night.
   - **What becomes of its rows.** The agent-session adds the rows the user accepts to the supporting list as an edit of that file through the ghi-write-tool; the user's ruling on each recommendation still waits for step 4's approval-walk.
