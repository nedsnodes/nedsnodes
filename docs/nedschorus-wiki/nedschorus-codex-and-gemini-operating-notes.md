# Notes on using the Codex and Gemini (Antigravity) agents from an agent-seat

This page tells an agent-seat how to run Codex and Gemini, and what to expect from them. Facts about an installed program say which machine and date they were checked on, because the programs update often. Measurements the cold-read-research agent-seat made from 2026-09-03 to 2026-09-07 are in their own section near the end, and the campaign's data is in the record `nedlern@ned-box:/home/nedlern/nedschorus-logs/cold-read-records/2026-09-03-cold-read-tier-roster-campaign/`. Claude Code, the program the agent-seats themselves run in, is covered elsewhere; it appears here only where it was measured beside the other two or where it broke their runs.

## Run them through the project's programs

- To give Codex a task, run `scripts/run-codex-task-from-brief.py -C <checkout> --brief <file> -o <report>`; the program saves Codex's last message at `<report>`, unless Codex wrote a file there itself, as a brief may tell it to, in which case that file is kept and the last message goes to `<report>.last-message`. Never start `codex exec` yourself, by hand or from a script: started that way, Codex waits forever on an open stdin, nothing stops a run that hangs, and nothing keeps Codex out of credential files; this program and the reviewing programs named in the next section each take care of all three. The program's own options cover what a task needs: `--sandbox`, which takes `read-only` (the default) or `workspace-write` to let Codex edit, `-m <model>`, `--effort <effort>`, `--writable-root <folder>` for each further folder Codex may write with `--sandbox workspace-write`, `--outside-git-checkout` for a folder that is not a git checkout, `--prefetch-github '<gh arguments>'`, which runs a `gh` command that only reads before Codex starts and gives Codex its output as a file, `--no-network`, which keeps the commands Codex runs off the network and turns off its web search, both of which every other run has, and `--deadline-minutes` (default 60). Run it with `--help` for the rest.
- To run one reviewer on a document, use the cold-read-cell launchers: `nc-systems/cold-read/cold-read-claude-cell.py`, `nc-systems/cold-read/cold-read-codex-cell.py` and `nc-systems/cold-read/cold-read-agy-cell.py`. Each takes `--cell`, which names the reviewer prompt under `.claude/skills/cold-read/prompts/` (`defect-hunt`, `fast-clarify` or `terminology`), `--tier`, `--target` and `--report`. The Codex launcher takes `--tier deep` or `--tier second-strongest-model`; the Claude launcher takes those two and also `--tier fast`, the tier the cold-read-fast-read's backup runs when Gemini fails; the Gemini launcher takes only `--tier fast`. To use a prompt of your own, add `--prompt-file <path>`; `--cell` is then a label of your choosing, lowercase letters and digits joined by single hyphens, recorded in the report's provenance stamp.
- To give Gemini a task, run `scripts/run-gemini-task-from-brief.py -C <checkout> --brief <file> -o <report>`. It takes `--sandbox` and `--deadline-minutes` as the Codex task program does; `-m <model>`, which defaults to `gemini-4-argon-high` and must be an id that `agy models` lists; `--effort <effort>`, which it refuses with a model id that carries an effort, as the default does; and `--writable-root <folder>`, which it refuses without `--sandbox workspace-write`. It tells Gemini to write its report at `<report>`. Run it with `--help` for the rest.
- Never give `agy` a prompt outside `scripts/run-gemini-task-from-brief.py`, the Gemini cold-read launcher `nc-systems/cold-read/cold-read-agy-cell.py`, or `nc-systems/general-tools/agy-print-prompt-run-in-empty-home-sandbox.py --model <id> "<prompt>"`, which runs one prompt and prints the answer; `agy update`, `agy --version` and `agy models`, which send no prompt, you run yourself. With `--dangerously-skip-permissions`, which the first two programs pass so that `agy` can write its report, `agy` reads credential files, and its own `--sandbox` switch does not stop it; those two programs run it inside `bwrap` on Linux or `sandbox-exec` on macOS, and refuse to run without one. Without that flag, `agy` still reads files in its working directory and runs the commands its settings allow, as point 3 of "What a new runner must handle" below says; so `agy-print-prompt-run-in-empty-home-sandbox.py` runs it without the flag, in an empty working directory, inside `bwrap` with a home that holds only `~/.gemini` on Linux, and inside the `sandbox-exec` profile that the Gemini cold-read launcher builds, on macOS.

## What each kind of task may read, reach and write

The program that starts a run decides its access. The reviewing programs are the cold-read-cell launchers for Codex and Gemini, `scripts/code-review-codex-cell.py`, and the Codex sanity-check-cells of `scripts/sanity-check-adversarial-prompts.py`, which the /sanity-check skill runs. The task programs, `scripts/run-codex-task-from-brief.py` and `scripts/run-gemini-task-from-brief.py`, run research and trawls, and run code-writing when given `--sandbox workspace-write`. The table gives each kind of task's defaults; the bullets after it say what changes them.

| Kind of task | Reads | Network | Writes |
|---|---|---|---|
| Reviewing a document or a pull request | everything but credential files, as the first bullet below defines them | the web, web search, and GitHub through a token that can only read public repositories | its report. A Codex cold-read-cell can also write in the checkout that `nc-systems/cold-read/cold-read-codex-cell.py` belongs to, which need not be the one holding the document it reviews; a Codex sanity-check-cell in the copy of the reviewed commit that `scripts/sanity-check-adversarial-prompts.py` makes under `~/.cache/nedschorus-sanity-check-review-copies/`; and the Gemini cold-read-cell anywhere outside credential files, because it runs agy with the whole file system writable but for them. `scripts/code-review-codex-cell.py` lets Codex write nothing: the program saves Codex's last message as the report. |
| Research and trawls | the same | the same | its report and, on ned-box, its folder in the shared writable folder, which the bullets below describe |
| Writing code | the same | the same | its topic-worktree, its report, each `--writable-root` folder, and, on ned-box, its folder in the shared writable folder. The task program never pushes. |

- Credential files are the folders `~/.ssh`, `~/.config/gh`, `~/.config/nedschorus`, `~/.steam` and `~/nedsmessenger`; Claude's and Codex's login files, `~/.claude/.credentials.json` and `~/.codex/auth.json`; agy's login files, `~/.gemini/jetski-standalone-oauth-token`, `~/.gemini/oauth_creds.json` and `~/.gemini/antigravity-cli/antigravity-oauth-token`, which Claude and Codex runs are denied but agy runs are not, since agy needs its own login, so every command agy starts in a run can read them; and, on macOS only, files named `*.token` or `.env`, wherever they are. On Linux the sandboxes deny no file by its name: a `.env` or `*.token` file outside those folders is readable.
- Codex and Gemini runs reach the network and may search the web. Give `scripts/run-codex-task-from-brief.py` the option `--no-network` for a run that must do neither; its `--prefetch-github` commands still reach GitHub, because they run outside the sandbox before Codex starts. `scripts/run-gemini-task-from-brief.py` has no such option: the Codex CLI talks to its model outside the sandbox, but agy runs whole inside it, and no proxy separates agy's model traffic from its tools' traffic.
- None of the reviewing or task programs gives Codex or Gemini the agent-seat's GitHub token, which can push and merge. Each puts in its place, as `GH_TOKEN`, a token that can only read public repositories, such as nedschorus/nedschorus, kept at `~/.config/nedschorus-sandboxed-models/github-public-repositories-read-only-token`, so that `gh` works inside the sandbox. When that file is missing, empty or unreadable, the run goes ahead without a token: `git fetch` over https still works, `gh` does not, and the run log, or the cell's stderr, says so. A token GitHub refuses, such as an expired one, is not caught before the run: `gh` fails inside it with HTTP 401, and after the run the program prints `read-only GitHub token refused` on stderr, with the line `gh` printed, and says to tell the user that the token needs replacing; its exit status does not change. The token expires on 2027-10-22.
- On ned-box, a run of either task program may write in its own numbered folder, `/home/nedlern/nedschorus-logs/codex-and-gemini-sandboxed-task-runs-shared-writable-folder/<agent-seat>/<brief file name without its extension>/<number>/`, in the shared writable folder. The program creates the folder, prints its path and names it in the brief. `<agent-seat>` is the agent-seat's name, taken from `CLAUDE_CODE_TASK_LIST_ID` when that variable reads `nedschorus-<agent-seat>-tasks`, and `no-agent-seat-name` otherwise. `<number>` is `1` for the first run of a brief file name and one more than the highest number already there for each later run, so two brief files of the same name without its extension, in different folders, share one numbering; two runs started together never get the same number. The first run of a brief file named `loose-ends-trawl-2026-10-22.md` by prime-intellect writes in `prime-intellect/loose-ends-trawl-2026-10-22/1/`, and its second run in `prime-intellect/loose-ends-trawl-2026-10-22/2/`. Where the log-store is absent, as on the Mac, there is no shared writable folder, and a run writes only what the table's other entries list.
- #open_question Whether, when and by whom the numbered run folders in the shared writable folder are removed.
- Codex runs under a permission profile: the read, write and network rules the starting program gives Codex, built on Codex's own `:read-only` or `:workspace` profile, with credential files denied. On Linux the profile keeps `/tmp` itself and `$TMPDIR` read-only, because a Codex sandbox with `/tmp` writable creates `/tmp/.git`, `/tmp/.codex` and `/tmp/.agents`, and `/tmp/.git` makes git take everything under `/tmp` for one repository. A folder under `/tmp` given to Codex as a writable folder, such as the one in which the Codex cold-read-cell has Codex write a report bound for outside its checkout, stays writable. On macOS a profile built on `:workspace` leaves `/tmp` and `$TMPDIR` writable, so there a Codex cold-read-cell, a Codex sanity-check-cell and a `workspace-write` Codex task can also write in them.
- Codex and Gemini write code only in a topic-worktree the dispatching agent-seat made, given as `-C` with `--sandbox workspace-write`. Commit or remove your own changes in the topic-worktree before the run starts: when the run succeeds, the program commits every change it finds there, yours included, and discarding a failed run's changes discards yours too. They commit there through the task program, which then runs the nc-test-suites the change touches and exits nonzero, naming them, when any fail: they cannot run `git commit` themselves, because a topic-worktree's git data lives in the `.git` folder of the checkout it was made from, which is not among the folders they may write. So the program tells them to write their commit message in `commit-message.txt` at the top of the topic-worktree and, when the run ends without error or timeout, stages every change in the topic-worktree and commits it with that message, under the git identity the agent-seat has there, and deletes the file; a `commit-message.txt` already there when the run starts is deleted first, so that an earlier run's message is never used. When the run changed nothing, it commits nothing, deletes any `commit-message.txt` the run wrote, and exits 0. When the run changed files but the file is missing or empty, it commits nothing, lists the uncommitted changes and exits nonzero. When `git add` or `git commit` fails, as when a pre-commit hook refuses the commit, it leaves the changes and `commit-message.txt` in place, says what git said and how to commit by hand, and exits nonzero. The program runs those nc-test-suites with `scripts/run-all-test-suites.py --only-suites-whose-recorded-inputs-changed-since <the commit HEAD was at when the run started> --leave-recorded-inputs-and-failure-history-unchanged` in the topic-worktree, outside the run's deadline, and prints the runner's output; it also exits nonzero, saying so, when the runner cannot be started or ends without judging every suite, and it keeps the commit in every case. A run that commits nothing runs no nc-test-suite. When `-C` is not the top folder of a git worktree, the program neither asks for a commit message nor commits, and exits 0 with the changes left in place. Give `-o` outside the topic-worktree, or the report and run log are committed with the change. The agent-seat reviews the commit, pushes it and opens the pull request. A run that fails or passes its deadline leaves its changes uncommitted in the topic-worktree, for the agent-seat to keep or discard.

## Codex (`codex`, OpenAI)

**Install and update.** Codex is installed through npm, not Homebrew: on ned-box `/usr/local/bin/codex` is a symlink into `/usr/local/lib/node_modules/@openai/codex`, and on the Mac `/opt/homebrew/bin/codex` is a symlink into npm's `node_modules/@openai/codex`, so `brew upgrade codex` fails. Update with `codex update`, which runs `npm install -g @openai/codex`, and check with `codex --version` (codex-cli 0.159.3 on ned-box on 2026-10-17). Every agent-seat on a machine shares the one binary, so before you update, check with `pgrep -af codex` that no Codex run is in progress; if one is, wait for it to finish. Running Codex tasks side by side is fine; only the update must wait.

**Model ids.** The CLI has no command that lists models. It caches the list it knows in `~/.codex/models_cache.json`, refreshed on each run; the ids are the `slug` fields. A model appears there only once the CLI is new enough for it: the Codex launcher's `gpt-6.1-sol` needs codex-cli 0.159.1 or later. A model id the CLI does not know makes the run hang instead of failing (measured: eight minutes with no output, then killed), so take the id from the cache; `scripts/run-codex-task-from-brief.py` stops such a run at its deadline. The model cannot tell you its own id.

**Effort.** Effort is set per run, with `--effort`, not in the model id.

**At capacity.** When a run on `gpt-6-astra` prints "Selected model is at capacity. Please try a different model.", which means OpenAI has no room on that model at that moment rather than that the user's plan is used up, run the task again with `-m gpt-6.1-sol --effort xhigh`.

**Project rules.** Codex reads the repository's `AGENTS.md`, which tells it to read `CLAUDE.md` and follow it. Measured with a canary on 2026-08-22 and 2026-09-04: Codex reads `CLAUDE.md` when it may read files.

## Gemini via Antigravity (`agy`, Google)

**What it is.** Gemini runs through the Antigravity CLI, `agy`, the agent behind the Antigravity IDE; there is no `gemini` command. On ned-box `agy` is `~/.local/bin/agy` and its configuration is under `~/.gemini/antigravity-cli/` (version 1.4.0 on 2026-10-17). `agy update` updates it and `agy --version` reports it.

**Model ids carry the effort.** `agy models` lists them: `gemini-3.8-flash-high`, `gemini-3.8-flash-medium`, `gemini-3.8-flash-low`, `gemini-4-argon-high`, `gemini-4-argon-medium` and `gemini-4-argon-low` (ned-box, 2026-10-17). The cold-read-fast-read runs on `gemini-3.8-flash-medium`, and on `claude-sonnet-5-5` at low effort when Gemini fails. `scripts/run-gemini-task-from-brief.py` refuses `--effort` with a model id that carries one; pass it only with an id such as `gemini-pro-orchestrator`.

**What a new runner must handle.** The Gemini cold-read launcher, `nc-systems/cold-read/cold-read-agy-cell.py`, handles all of these, and `scripts/run-gemini-task-from-brief.py` all but point 4. They matter to someone changing either program or writing a new one, and point 4 also to anyone reading a failed Gemini task run.

1. The prompt is the value of `--print`. In `agy --print --model X "prompt"`, agy takes `--model` as the prompt and ignores yours. Put every other option first and `--print` last, with the prompt as its value.
2. Pass the repository with `--add-dir <repo>`, or nothing from the repository loads, `AGENTS.md` included.
3. Without `--dangerously-skip-permissions`, a headless run still reads files in its working directory, and runs the commands an allow-rule under `permissions.allow` in `~/.gemini/antigravity-cli/settings.json` permits: under the rule `command(agy)` it ran `agy --version` and `agy --help`. It was denied every other file read, in the home and in `/etc` included, and every other command it tried; a denied run ends with "no output produced — a tool required the X permission that headless mode cannot prompt for" (agy 1.4.12 on ned-box, 2026-10-31). `scripts/run-gemini-task-from-brief.py` and `nc-systems/cold-read/cold-read-agy-cell.py` pass the flag so that agy can write its report, and the flag is why they run agy inside the operating system's sandbox; `agy-print-prompt-run-in-empty-home-sandbox.py` runs agy inside it too, without the flag, for the reads and commands this point describes.
4. Gemini sometimes writes its whole report as its chat answer instead of into the report file. When agy ends without error, the Gemini cold-read launcher then takes the answer as the report when it is at least 120 words; a shorter answer with no report file counts as a failed run. `scripts/run-gemini-task-from-brief.py` does not take the answer: it exits 1 saying `agy exited 0 but wrote no report`, commits nothing, and the answer is in the run log.
5. `--print-timeout` defaults to `0s`, no limit, and agy does not always stop at it. The Gemini cold-read launcher sets `30m` and kills agy's process group 60 seconds after that; `scripts/run-gemini-task-from-brief.py` sets it to its own deadline and kills the process group at that deadline.
6. agy often does not exit after it has finished: it prints its result, then hangs for minutes, and ignores SIGTERM. The Gemini cold-read launcher and `scripts/run-gemini-task-from-brief.py` ask for `--output-format stream-json`, end the run at the line whose `event` is `result`, and kill agy's process group if agy has not exited a few seconds later; the task program uses the cold-read launcher's code for this. The result's `status` decides whether the task run succeeded: `SUCCESS` succeeds and any other status fails. A task run with no result line ends when agy exits, or fails with `deadline passed` at its deadline, its changes left uncommitted.

**Its own documentation.** On ned-box, agy's customization guide is `~/.gemini/antigravity-cli/builtin/skills/agy-customizations/SKILL.md`, with the rule-loading details in `~/.gemini/antigravity-cli/builtin/skills/agy-customizations/docs/rules.md`. Read it before asking agy about itself: asked about itself, agy may spend its whole run on experiments and time out.

## Measured from 2026-09-03 to 2026-09-07

These are the cold-read-research agent-seat's results, on the models and CLI versions of those days; the campaign record above holds the data for all but the result of 2026-09-07.

- A Codex run at `max` effort on a document of 1,500 to 2,300 words took 13 to 32 minutes (`gpt-6-astra` and `gpt-5.6-sol`).
- Codex hit no account limit in the campaign; Claude hit its limit three times in one day.
- `gemini-3.8-flash-low` read a 700 to 1,500-word skill in 21 to 31 seconds, found as many of the known defects as `gpt-5.6-terra` at low effort in a quarter of the time, and found no defect that no other reviewer found. Measured on 2026-09-07, as `nc-systems/cold-read/cold-read-agy-cell.py` records: on one defect list, `gemini-3.8-flash-medium` found 42% and low 19%, which is why the cold-read-fast-read runs on medium.

## Things that went wrong once and will again

- In a scratch directory several agents shared, one agent ran another's script because both used a generic name, `build_clusters.py`. Put the name of the document you are working on and your agent-seat's name in a scratch file's name.
- Give a shared file one writer. Each run writes its own record file, and one program builds any summary from the records; for a log, use one writer process that the others send to, as Python's `logging` documents.
- `/login` in an agent-seat's terminal kills that agent-seat's running subagents and its background `claude -p` runs with an authentication error. A Claude login once expired overnight and left a run hanging for six hours. Give a long batch of runs a deadline per run, and make it able to start again without redoing the runs whose reports are complete.
